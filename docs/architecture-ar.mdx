# بنية Postext

إن كنت قد عملت مع React من قبل، فأنت تفهم الحيلة الأساسية. يبني React نموذج DOM افتراضيًا في الذاكرة، ويقارنه بالنسخة السابقة، ولا يلمس DOM الحقيقي في المتصفح إلا بعد ذلك. ويفعل Postext الشيء نفسه، لكنه بدلًا من مكوّنات واجهة المستخدم يبني شجرة من **الصفحات والأعمدة والكتل النصية والمربعات المحيطة**. الهندسة الكاملة لمستند متعدد الصفحات ومتعدد الأعمدة، محسوبةً قبل رسم بكسل واحد. كل فقرة وعنوان وصورة وحاشية سفلية واقتباس بارز موضوع عند إحداثيات دقيقة، مع احترام قواعد تنضيد عمرها قرون لا تستطيع CSS التعبير عنها.

كل هذا ممكن بفضل [`@chenglou/pretext`](https://github.com/chenglou/pretext)، وهي مكتبة لقياس النص لا تعتمد على DOM، وأسرع بما بين 300 و600 مرة من إعادة حساب التخطيط (reflow) في المتصفح. ولقصة المشروع (عقد من المحاولات الفاشلة، وعنق الزجاجة الذي أوقفها كلها، والمكتبة التي أزالته أخيرًا)، راجع [مدخل](/ar/docs/introduction).

## الفكرة الأساسية

تخيّل مستندًا من 74 صفحة بعمودين: تقريرًا سنويًا لشركة مثلًا، أو كتابًا مدرسيًا كثيف الرسوم. تسلّمه إلى Postext، فيبني المحرّك الإخراج كاملًا في الذاكرة: كل صفحة، وكل عمود، والموضع الدقيق لكل فقرة وأبعادها بالبكسل. تريد أن تعرف ما في الصفحة 72، العمود 2؟ الجواب موجود مسبقًا، دون أي رسم. فقد قرّر المحرّك أين يكسر كل فقرة، وأين يضع كل صورة، وكيف يتجنّب الأرامل والأسطر اليتيمة (widows and orphans)، وكيف يحاذي خطوط الأساس بين الأعمدة المتجاورة.

وإليك سبب أهمية ذلك.

قواعد التنضيد مترابطة ترابطًا عميقًا ومرهقًا. تعالج أرملة في الصفحة 5 (سطرًا أخيرًا وحيدًا عالقًا أسفل عمود) بسحبها إلى العمود السابق. حسنًا. لكن هذا التغيير يقصّر عمود الصفحة 5، فيُزيح المحتوى إلى الأمام، وقد ينشأ عن ذلك سطر يتيم في الصفحة 6: سطر أول وحيد دُفع إلى عمود جديد منفصلًا عن فقرته. وحتى *تكتشف* أنك أحدثت مشكلة جديدة، تحتاج إلى أن يكون إخراج المستند كله متاحًا للفحص. ولكي *تعالجها* دون أن تُحدث مشكلة أخرى في مكان آخر، تحتاج إلى أن تستطيع تعديل الكل وإعادة قياسه وإعادة فحصه.

هذه هي فلسفة «احسب كل شيء أولًا، وارسم لاحقًا». ليست حيلة لتحسين الأداء، بل الطريقة الوحيدة لتطبيق عشرات القواعد التنضيدية المترابطة التي استعملها المنضّدون المحترفون منذ قرون.

**هذا هو المسار الذي يسلكه محتواك داخل المحرّك:**

1. يقرأ **المحلّل** (parser) ملف markdown المُثرى ويحوّله إلى قائمة مسطّحة من كتل المحتوى المصنّفة: محتوى وبنية، بلا مواضع بعد
2. تمرّ **تمريرة توزيع** على تلك القائمة مرة واحدة وتبني VDT. تقيس كل كتلة عبر Pretext بعرض العمود الذي توشك الكتلة أن تدخله، وتضع النص والعناصر العائمة والإطارات في الصفحات والأعمدة، وتطبّق قواعد الكسر والإبقاء معًا في أثناء مرورها
3. يعيد **المشغّل** (driver)، وهو `buildDocument`، تشغيل التمريرة حين يحتاج قرار إلى نتيجة إخراج كامل: جدول محتويات يطبع أرقام الصفحات، أو إطار ممتد على عرض الصفحة عليه أن يقطع الأعمدة التي فوقه قطعًا مستويًا، أو عمود انتهى قصيرًا. تأخذ كل إعادة تشغيل تلميحات من التمريرة التي قبلها، ولكل نوع من إعادة التشغيل حدّه الخاص
4. **VDT النهائية** هي هندسة الإخراج الكاملة: كل عنصر يعرف رقم صفحته والعمود المخصّص له وموضعه ومربعه المحيط. يكون المستند «منضّدًا» بالكامل قبل أي رسم
5. يمرّ **مُخرِج** على VDT المكتملة ويرسمها بالصيغة المستهدفة: صورة نقطية على لوحة canvas، أو شجرة DOM من عناصر HTML محدّدة المواضع، أو مستند PDF بخطوط مضمّنة، أو كتاب EPUB. VDT نفسها تغذّي الأربع؛ واختيار المُخرِج قرار يخص المخرجات وحدها


## طبقة الإدخال

### نموذج المحتوى

نموذج المحتوى فلسفة بقدر ما هو بنية بيانات. أنت تصف *ماذا* تقول، لا *كيف* يُخرَج. والمحرّك يتخذ قرارات الإخراج.

<Illustration name="ContentModel" data='{"title": "نموذج المحتوى: markdown والموارد والحواشي", "desc": "يفصل مُدخل Postext بين markdown (ترتيب القراءة والبنية الدلالية) والموارد (الصور النقطية وملفات SVG والجداول) والحواشي. يحلّ المحرّك الإحالات السطرية :ref والتضمينات ::resource بالمعرّف وينتج VDT.", "caption": "يملك markdown ترتيب القراءة، وتملك الموارد البيانات المرئية.", "contentTitle": "PostextContent", "markdown": "markdown", "markdownSub": "ترتيب القراءة + :ref / ::resource بالمعرّف", "resources": "resources[]", "resourcesSub": "صور نقطية، SVG، جداول", "notes": "metadata", "notesSub": "العنوان، المؤلف، التواريخ", "resolveMarker": "تُحلّ بالمعرّف: :ref{id=…}، ::resource{id=…}", "engineLabel": "المحرّك", "vdtLabel": "VDT"}' />

```typescript
// packages/postext/src/types.ts

interface PostextContent {
  markdown: string;            // enriched markdown with :ref / ::resource markers
  metadata?: DocumentMetadata; // title, subtitle, author, publishDate, …
  resources?: Resource[];      // bitmaps, SVGs, tables, videos — referenced by id
  notes?: PostextNote[];       // not read: footnotes are written as [^id] in the markdown
}

interface Resource {
  id: string;                  // stable id, referenced by inline :refs
  typeId: string;              // ResourceType this resource belongs to ('figure', 'table', …)
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  caption?: string;            // the type prefix + number are computed, not written here
  altText?: string;
  createdAt: number;
  updatedAt: number;
  // Exactly one kind-specific payload:
  bitmap?: { fileId: string; format: string; width: number; height: number };
  svg?: { fileId: string; width?: number; height?: number };
  table?: { model: TableModel };
  video?: ResourceVideo;       // where it plays from; drawn on the page as its poster
  placement?: ResourcePlacement; // optional per-resource float override
  safeArea?: ResourceSafeArea;  // bitmap / svg: { x, y, width, height } in fractions, the part always shown
}
```

**الموارد** تحمل البيانات المرئية: التعليقات والنص البديل وحمولة خاصة بالنوع. الحمولات الثنائية (الصور النقطية وملفات SVG) تبقى *خارج النطاق* (out-of-band): لا يخزّن المورد إلا `fileId`، ويحلّه المُخرِج وقت الرسم (يحفظ Sandbox البايتات في IndexedDB). وموارد الجداول استثناء: نموذجها `TableModel` (شبكة خلايا مع امتداداتها ومحاذاتها) ينتقل داخل المورد، لأنه بيانات مهيكلة لا بايتات.
**الحواشي** تُكتب في markdown: علامة `[^id]` حيث يُحال إلى الحاشية، وتعريف `[^id]:` في فقرة مستقلة في أي موضع من الفصل. يرقّم المحرّك الحواشي بترتيب أول إحالة إليها، ويُنضّد كل حاشية في أسفل العمود الذي يحوي السطر المحيل إليها، تحت خط قصير، أو بعد آخر كتلة في الفصل مع `footnotes.placement: 'chapterEnd'` (راجع [الحواشي السفلية](/ar/docs/document-format#الحواشي-السفلية) و[الإعدادات › الحواشي السفلية](/ar/docs/configuration-notes-references#الحواشي-السفلية)). وما زال نموذج المحتوى يقبل مصفوفة `notes`، لكن لا تقرؤها أي مرحلة من خط الإخراج.

هذا الفصل خيار تصميمي مقصود، وأهميته أكبر مما يبدو. يملك markdown *ترتيب القراءة* و*البنية الدلالية*: ما يأتي أولًا، وما هو عنوان، وأين يُحال إلى حاشية سفلية وماذا تقول. وتملك مصفوفة الموارد *البيانات المرئية*: أبعاد الصور ونص التعليقات وخلايا الجداول. وبإبقائهما منفصلين، يمكن إخراج markdown نفسه بطرق مختلفة تمامًا بمجرد تغيير الإعدادات. فيمكن لتخطيط أكاديمي بعمودين ولتدوينة بعمود واحد أن يشتركا في المحتوى المصدري نفسه. ويستطيع المحرّك أن يتخذ قرارات الوضع، كتأجيل صورة إلى العمود التالي لأنها لا تتسع هنا، دون أن يمس محتواك المصدري أبدًا.

```typescript
// Example: a simple article with a referenced figure
const content: PostextContent = {
  markdown: `
# The Art of Typography

The history of typography begins with Gutenberg's
```

### استراتيجية التحليل

التحليل عمدًا أبسط خطوة في خط الإخراج. يدخل markdown ويخرج قائمة مسطّحة من كتل المحتوى المصنّفة (`ContentBlock`، في `packages/postext/src/parse/`): عنوان، أو فقرة بمقاطعها السطرية، أو عنصر قائمة، أو توجيه. وتُحفظ النتيجة لإعادة استعمالها (`parseMarkdownMemo`)، فتمريرات البناء الواحد تحلّل مرة واحدة، وكذلك أي بناء لاحق للنص نفسه. تُحلّ إحالات الموارد مقابل المصفوفة `resources[]` بالمعرّف في بداية كل تمريرة توزيع. وهناك أيضًا تخرج تعريفات الحواشي السفلية (الفقرات التي تبدأ بـ`[^id]:`) من التدفق وتُحفظ بمعرّفها للعلامات التي تحيل إليها؛ أما المصفوفة `notes[]` فلا تُقرأ.

فكّر فيها كقائمة جرد: «هناك عنوان، ثم فقرة من 200 كلمة، ثم إحالة إلى شكل، ثم فقرة أخرى». لا قياسات، ولا مواضع، ولا أي قرار إخراج. ولا توجد `VDTBlock` إلا بعد أن تقيس تمريرة التوزيع الكتلة وتعطيها موضعًا.


## شجرة المستند الافتراضية (VDT)

تخيّل أنك طلبت من منضّد محترف أن يُخرج كتابًا كاملًا، لكنه بدلًا من أن يسلّمك صفحات مطبوعة سلّمك جدولًا حسابيًا. كل صف عنصر، وكل خلية قياس دقيق: «العنوان عند (40, 30)، والفقرة الأولى تبدأ عند (40, 78) وارتفاعها 144px، والصورة أعلى العمود 2 في الصفحة 3...». ذلك الجدول هو VDT.

شجرة المستند الافتراضية هي بنية البيانات المركزية في Postext: شجرة قابلة للتعديل في مكانها تمثّل كل صفحة وعمود وكتلة وسطر، ويحمل كل منها مربعًا محيطًا دقيقًا. وما إن يُرجع `buildDocument` نتيجته حتى *تكون* VDT هي الجواب. يمكنك أن تسأل «ما الذي في الصفحة 72، العمود 2؟» دون رسم بكسل واحد.

### لماذا قابلة للتعديل

هذا هو النهج نفسه المتّبع في خطوط الرسم في محرّكات الألعاب، حيث تحدّث أنظمة متعاقبة حالةَ عالم مشتركة قابلة للتعديل في حلقة سريعة متلاحقة. وللسبب نفسه.

تملأ تمريرة التوزيع الشجرة في مكانها. تفتح صفحة، وتُلحق بها أعمدة، وتطرح ارتفاع الكتلة من `availableHeight` للعمود الذي تستقر فيه، وتغلق أعمدة الشريط حيث يقطعه إطار ممتد على عرض الصفحة. في الكتاب آلاف الكتل، والشجرة غير القابلة للتعديل (مثل DOM الافتراضي في React) كانت ستخصّص كائنًا جديدًا لكل خطوة من هذه الخطوات. لذلك فالعقد كائنات بسيطة تكتب فيها التمريرة مباشرة.

التمريرة المنتهية لا تُرقَّع. حين يحتاج `buildDocument` إلى محاولة أخرى (سقف لشريط، أو أداة موازنة)، يشغّل التمريرة من جديد انطلاقًا من المحتوى ويحصل على شجرة جديدة. وتبقى شجرة التمريرة السابقة كما كانت، فيستطيع المشغّل أن يقارن بين الاثنتين، وأن يحتفظ بالأفضل، أو أن يأخذ صفحات من كل منهما. والذاكرة المؤقتة للقياس تجعل كلفة إعادة التشغيل محتملة: الفقرة التي لم يتغير نصها ولا خطوطها ولا عرضها تُقرأ من الذاكرة المؤقتة بدل أن تُقاس من جديد.

### تعريفات الأنواع

الأشكال أدناه **مبسّطة للشرح**: التعريفات الحقيقية في `packages/postext/src/vdt.ts` تحمل حقولًا أخرى كثيرة موجّهة للرسم (سلاسل الخطوط، والألوان، ونقاط القوائم، ورسوم الرياضيات، وخانات التصميم). المهم هنا هو البنية:

```typescript
// Simplified — see packages/postext/src/vdt.ts for the full definitions

// The root of the Virtual Document Tree
interface VDTDocument {
  pages: VDTPage[];
  blocks: VDTBlock[];         // flat view of the same block objects
  config: ResolvedConfig;     // every sub-config resolved to non-optional
  baselineGrid: number;       // baseline increment in px (e.g. 24 for 16px/1.5)
  converged: boolean;         // every balancing segment ended flush or out of levers
  iterationCount: number;     // placement passes behind this layout (see The Pass Driver)
  metadata: DocumentMetadata;
}

// A physical page
interface VDTPage {
  index: number;
  width: number;
  height: number;
  columns: VDTColumn[];
  header?: VDTDesignSlot;     // running header (design slot)
  footer?: VDTDesignSlot;     // running footer / page number
  floats?: VDTBlock[];        // resource bands floated to the top/bottom of this page
  pageNumberValue: number;
  pageLabel: string;          // rendered label ('iv', '7', 'A', …)
}

// A column within a page
interface VDTColumn {
  index: number;
  bbox: BoundingBox;          // position within the page
  blocks: VDTBlock[];
  availableHeight: number;    // remaining vertical space
  baselineOffset: number;     // current baseline y-position
  band?: number;              // column band (0 unless a span block split the page)
  kind?: 'text' | 'span' | 'side'; // 'span' = full-width column holding a page-span block,
                              // 'side' = the float-only side column of a one-and-a-half layout
}

// A content block (paragraph, heading, resource, etc.)
type VDTBlockType =
  | 'paragraph' | 'heading' | 'resource' | 'blockquote'
  | 'listItem' | 'footnoteRef' | 'mathDisplay' | 'callout' | 'code';

interface VDTBlock {
  id: string;
  type: VDTBlockType;
  bbox: BoundingBox;
  lines: VDTLine[];           // for text blocks: the measured lines
  resourceBlock?: ResolvedResourceBlock; // for resource blocks
  pageIndex: number;
  columnIndex: number;
  dirty: boolean;             // not used: cleared when the block is placed, read by nothing
  snappedToGrid: boolean;     // the flow went back to the baseline grid under this block
  balancing?: VDTBalancing;   // the column-balancing levers applied to this block
}

// A measured line of text
interface VDTLine {
  text: string;
  bbox: BoundingBox;            // natural width: a justified line is painted to its block's right edge
  baseline: number;             // y-position of the text baseline
  hyphenated: boolean;          // line ends inside a word, or after a closed dash ("say—" | "that’s")
  hardHyphen?: boolean;         // …after a hyphen the text carries ("well-" | "known"): nothing added
  repeatedHyphen?: boolean;     // opens with that hyphen repeated ("vencer-" | "-se"), not in the source
  segments?: VDTLineSegment[];  // word/space/math runs for justified rendering
  isLastLine?: boolean;         // last line of its paragraph
  justifiedSpaceRatio?: number; // width every space is painted at ÷ the regular face's space
  justifiedSpaceLimitRatio?: number; // the spacing the limits bound, when the line's own spaces are not regular (lineWordSpacing reads both)
  sourceStart?: number;         // markdown source map (char offsets; a line opening with `\$` starts at the backslash)
  sourceEnd?: number;
  plainStart?: number;          // plain-text source map
  plainEnd?: number;
}

// A measured, placement-ready resource embed (bitmap / svg / table / video)
interface ResolvedResourceBlock {
  resource: Resource;
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  number: string;             // computed number, e.g. "1.7"
  captionPrefix: string;      // e.g. "Figure"
  bodyRect: BoundingBox;      // the image / table area
  bodySource?: ResourceSafeArea; // the part of the picture shown in bodyRect when cropped to its safe area
  bodyFlex?: { shrink: number; grow: number; delta: number }; // px the body can still shrink / grow, px applied
  fileId?: string;            // out-of-band binary (bitmap / svg)
  captionLines: VDTLine[];    // measured caption, prefix + number included
  table?: VDTResourceTableLayout; // cell geometry for table resources
}

// Bounding box — all values in px, relative to page origin
interface BoundingBox {
  x: number;
  y: number;
  width: number;
  height: number;
}
```

بعض هذه الحقول يستحق ملاحظة:

- **`isLastLine`** يوجّه الرسم المضبوط: تُرسم الأسطر الأخيرة غير مضبوطة حتى حين تكون الفقرة مضبوطة، إلا الأسطر الأخيرة *المكتظة* (overfull)، التي تنضغط المسافات بين كلماتها لتتسع في عرض السطر (وفق دلالات ضبط المسافات المرنة في TeX).
- **`sourceStart`/`sourceEnd` و`plainStart`/`plainEnd`** خرائط مصدر تربط كل سطر بموضعه في markdown الأصلي وفي النص الخام للكتلة، وعليها تقوم مزامنة المؤشر والتحديد في تكاملات المحررات.
- **`VDTResourceTableLayout`** (مع مدخلاته `VDTResourceTableCell`) يحمل الهندسة الكاملة لمورد جدول بعد إخراجه: حواف الأعمدة على المحور x، وحواف الصفوف على المحور y، ومستطيلات الخلايا مع أسطر محتواها المقيسة، فترسم كل المُخرِجات الجدول نفسه.
- **`dirty` و`snappedToGrid`** يُكتبان حين توضع الكتلة ولا تقرؤهما أي مرحلة ولا أي مُخرِج. يبدأ `dirty` بالقيمة `true` في الكتلة الجديدة ويُضبط على `false` حين توضع الكتلة؛ فالمحرّك لا يتتبّع التغييرات على الشجرة، بل يشغّل تمريرة التوزيع من جديد (راجع [مشغّل التمريرة](#مشغّل-التمريرة)). وتكون قيمة `snappedToGrid` هي `true` في أول جزء من كتلة نصية يعود التدفق بعده إلى الشبكة (راجع [نظام الإيقاع العمودي](#نظام-الإيقاع-العمودي)).
- **`balancing`** يبيّن أيّ أدوات موازنة الأعمدة حرّكت الكتلة أو مدّدتها؛ والكتلة التي تركتها الموازنة على حالها لا تحمله (راجع [موازنة الأعمدة](#موازنة-الأعمدة)).
- **`computePageTextExtent(page)`** دالة مساعدة عامة صغيرة تعيد الامتداد العمودي الذي يغطيه النص فعلًا في صفحة (بما في ذلك تعليقات العناصر العائمة). تستعملها طبقات التصحيح المرئية كي لا تمتد خطوط شبكة خطوط الأساس إلا على النص الحقيقي، لا على أسفل الصفحة الفارغ.


## خط الإخراج

تمريرة توزيع واحدة، تُشغَّل بقدر ما يحتاج الإخراج. هذا هو خط الإخراج كله.

تمرّ التمريرة (`placeDocumentPass`، في `packages/postext/src/pipeline/build.ts`) على المحتوى من أول كتلة إلى آخرها. وتفعل لكل كتلة كل ما يلزم لتنضيدها: تقيسها بعرض العمود الذي توشك أن تدخله، وتنظر هل تتسع، وتقسمها أو تنقلها إلى ما بعده وفق قواعد الكسر والإبقاء معًا، وتعرض خانة على العناصر العائمة التي تحيل إليها الكتلة، وتعيد التدفق إلى شبكة خطوط الأساس (راجع [نظام الإيقاع العمودي](#نظام-الإيقاع-العمودي)). وليس للعناصر العائمة ولا للأرامل ولا للشبكة تمريرة خاصة: تُحسم كلها حين تستقر كل كتلة.

بعض القرارات لا يمكن اتخاذها داخل مرور واحد، لأنها تتوقف على ما ينتهي إليه المرور: أرقام الصفحات التي يطبعها جدول المحتويات، والارتفاع الذي يقطع عنده إطار ممتد على عرض الصفحة الأعمدةَ التي فوقه، والأسطر التي ما زال يحتاج إليها عمود قصير. لهذه القرارات يعيد `buildDocument` تشغيل التمريرة مع *تلميحات* (hints) مأخوذة من نتيجة التمريرة السابقة. تتبع المراحل الخمس أدناه الكتلة خلال التمريرة؛ ويتناول [مشغّل التمريرة](#مشغّل-التمريرة) و[موازنة الأعمدة](#موازنة-الأعمدة) إعادات التشغيل.

### المرحلة 1: هيكلة المحتوى

- **المُدخل:** `PostextContent` خام
- **العمل:** تحليل markdown إلى كتل محتوى، وحلّ إحالات الموارد مقابل `resources[]` بالمعرّف، وإخراج تعريفات الحواشي السفلية (`[^id]:`) من التدفق وترقيم علاماتها بترتيب الإحالة، وترقيم العناوين، وتخطيط العناصر العائمة: أي الموارد يُعوَّم، وبعد أي كتلة (`notes[]` لا تُقرأ)
- **المُخرج:** قائمة مسطّحة من كتل المحتوى (مصنّفة وممتلئة بالمحتوى، لكن بلا صفحة ولا عمود مخصّصين) وخطة العناصر العائمة
- **تجري:** في بداية كل تمريرة توزيع. يُقرأ التحليل من نتيجته المحفوظة بعد التمريرة الأولى؛ والباقي يُحسب من جديد

### المرحلة 2: قياس النص

- **المُدخل:** كتلة محتوى فيها نص، وعرض العمود الذي توشك أن تدخله
- **العمل:** قياس أسطر الكتلة بذلك العرض عبر **وحدة القياس** المخصّصة (`packages/postext/src/measure/`)، التي تبني تقسيم الكلمات بالواصلة وضبط الأسطر والمقاطع السطرية المنسّقة وكسر الأسطر بخوارزمية Knuth-Plass فوق Pretext. والنتيجة `VDTLine[]` الخاصة بالكتلة وارتفاعها الكلي
- **تفصيل مهم:** القياس مخزّن مؤقتًا. تبني `cachedMeasureBlock` / `cachedMeasureRichBlock` (في `measure/cache.ts`) مفتاحها من النص والخطوط والعرض وكل خيار يؤثر في الإخراج، فإعادة قياس فقرة لم تتغير مجرد بحث في خريطة
- **المُخرج:** أسطر الكتلة، بأبعاد دقيقة بالبكسل
- **تجري:** حين يبلغ المرور الكتلة، لا قبل ذلك، لأن العرض يتوقف على الموضع الذي تستقر فيه الكتلة: عمود بجوار عمود جانبي، أو الأسطر المجاورة لشكل يلتف حوله النص، أو الأعمدة الفرعية لمجموعة `:::columns`. والكتلة التي تنتقل إلى عمود بعرض آخر تُقاس من جديد بذلك العرض

تنقسم الوحدة بوضوح حسب المسؤولية: `plain.ts` يقيس المقاطع البسيطة، و`rich.ts` يقيس المقاطع المختلطة من غامق ومائل ورياضيات، و`font.ts` يبني سلاسل الخطوط ويدير دورة حياة الذاكرة المؤقتة، و`canvas.ts` يغلّف الدوال الأولية لقياس عرض النص على canvas. وتفصيل واحد في دورة الحياة مهم عمليًا: يجب ألا تبقى عروض الحروف المقيسة بخط احتياطي بعد وصول الخط الحقيقي. فـ`canvas.ts` يحتفظ بعروضه لكل سلسلة خط وبجيل للقياس؛ و`evictFontFamilies` (التي تُستدعى حين يكتشف بناءٌ أن أوجه عائلة تغيّرت، ومن `watchFonts` و`prepareFonts` و`loadBundleFonts`) تطرح عروض تلك العائلات وتمسح ذاكرة Pretext المؤقتة، و`MeasurementCache` التي مُلئت في جيل أقدم تطرح كتلها المنضّدة بتلك العائلات عند أول بحث تالٍ فيها. وتفعل `clearMeasurementCache()` الشيء نفسه لكل العائلات. أما الأوجه نفسها فيحمّلها قبل الإخراج `fonts/prepare.ts` (`prepareFonts`)، ويقرأ `fonts/faces.ts` الأوجه التي استعملها مستند بعد إخراجه، من أجل تحذيرات `fontFallback`.

تسلك الفقرات الصينية واليابانية والكورية طريقًا آخر داخل الوحدة نفسها. الفقرة التي تفوق فيها حروف CJK عدد المسافات بين الكلمات تذهب إلى **مُنضِّد CJK** (`cjkCompose.ts`). يقطع النص إلى وحدات (حرف، أو مقطع من نص لاتيني، أو شرطة بعرض em مزدوج أو علامة حذف، أو صندوق ذرّي كالشارة أو علامة الحاشية)، ويقيس كل وحدة مرة واحدة، ويملأ الأسطر بطريقة أول ملاءمة (first-fit) وفق قواعد بداية السطر ونهايته في `cjkClasses.ts`: يستوعب السطر العلامةَ التي لا يجوز أن تفتتح السطر التالي بالتخلي عن الفراغ المحيط بعلامات الترقيم (`cjkPunctuation.ts`) قبل أن ينقل حرفًا إلى السطر التالي. ثم يُوزَّع السطر المضبوط بين حروفه. والمخرجات أسطر `VDTLine` عادية تحمل مقاطعها ما تحتاج إليه المُخرِجات لرسمها كما قيست بالضبط: `tracking` (بكسلات بعد كل حرف، داخلة أصلًا في عرض المقطع)، و`inkOffset` للعلامة التي تخلّت عن فراغها، و`hangs`، والمسافات بين حروف الهان والحروف اللاتينية بوصفها مقاطع `autospace`، والعلامات وقراءات الروبي (ruby) وصفوف الواريتشو (warichu) في التعليقات التوضيحية الصينية. وفي المستند الياباني يتبع المُنضِّد نفسه JLReq: تُقرأ فئات الكينسوكو في المستويات اليابانية من المحارف الواقعة على طرفَي كل وحدة لحظة الكسر، ويُضغط بياض علامات الترقيم ويُعاد بترتيب JLReq، وتُخطَّط الفوريغانا في `rubyJis.ts` (توزيع بنسبة 1:2:1، وامتداد فوق الكانا، وكلمات الجوكوغو)، وتوسّع علامات الكانبون وحدةَ المحرف الذي تحمله. والكلفة خطية في طول الفقرة: الفصل الأول من 紅樓夢 (6,949 حرفًا) يُنضَّد بقياس 1,298 حرفًا، كل حرف مميز مرة واحدة، في حين كان قياس بادئات الفقرة يتطلب 636,948. راجع [الإخراج الصيني](/ar/docs/chinese-layout).

وتحت ذلك كله، هنا تثبت Pretext جدواها. استدعاء `prepare()` هو الجزء المكلف: يحلّل النص باستعمال محرّك الخطوط في canvas ويخزّن النتيجة. أما استدعاء `layout()`؟ حساب محض، شبه مجاني. وهذا الفصل بين الاستدعاءين هو جوهر الأمر. فبعد تحضير النص، يستطيع المحرّك أن يكسره من جديد بكلفة لا تُذكر: بعرض آخر، لفقرة تكمل في عمود أضيق، أو بسطر زائد، لفقرة ترخيها موازنة الأعمدة. حضّر مرة واحدة، وأخرج بقدر ما تحتاج.

```typescript
// Simplified: how the measure module uses pretext internally
const prepared = prepare(paragraphText, '16px/1.5 Inter');
const { height } = layout(prepared, columnWidth, 24); // 24px line-height
// => "This paragraph is 168px tall at 320px column width — that's 7 lines."
```

### المرحلة 3: التوزيع على الصفحات والأعمدة

- **المُدخل:** كتلة مقيسة
- **العمل:** وضع الكتلة في العمود الحالي. إنشاء عقد `VDTPage` و`VDTColumn` كلما احتاج إليها التدفق. تتبّع `availableHeight` لكل عمود. وحين لا تتسع كتلة، قسمتها (المرحلة 5) أو الانتقال إلى العمود أو الصفحة التالية
- **الاستراتيجية:** وضع جشع بأول ملاءمة (greedy first-fit). تتبع فواصل الأعمدة والصفحات أبسط توزيع صالح
- **المُخرج:** تحصل الكتلة على `pageIndex` و`columnIndex` و`bbox`

هذه هي اللحظة التي تصير فيها VDT مستندًا حقيقيًا. قبل هذه المرحلة، الكتلة مدخل في قائمة مسطّحة، وليس لها عنوان. يخصّص التوزيع كل واحدة لصفحة وعمود، كمن يصب الماء في شبكة من الأوعية: املأ العمود 1 حتى يفيض، وانتقل إلى العمود 2، وحين تمتلئ الصفحة ابدأ صفحة جديدة.

قبل أن تستقر أي كتلة محتوى في صفحة، تحجز التمريرة مساحة للعناصر البنيوية: الترويسات والتذييلات الجارية (تُخرَج كخانات تصميم من `config.header` / `config.footer`) وأي أشرطة عائمة معلّقة للصفحة المفتوحة حديثًا. هذه الحجوزات تُنقص `availableHeight` لكل عمود، فحين تبدأ كتل المحتوى بالتدفق يعرف المحرّك بالضبط كم من المساحة متاح.

**أشرطة الأعمدة والأعمدة الممتدة.** `page.columns` مصفوفة مسطّحة بترتيب القراءة، لكن الصفحة ليست دائمًا صفًا واحدًا من الأعمدة. في تخطيط متعدد الأعمدة، الكتلة الواقعة في التدفق والممتدة على عرض الصفحة تقطع الصفحة إلى *أشرطة* (bands) متراصّة. وتُعدّ من هذا النوع أربعة أشياء: `:::callout` يحدّد نمطه أو سياجه `span: 'page'`، ومجموعة `:::columns{span="page"}` في النص الجاري، و`::resource` مضمّن في التدفق يُحلّ وضعه إلى `{ position: 'here', span: 'page' }`، وشريط مصوّر يُنضَّد على عرض الصفحة حيث كُتب (`:::strip{span=page}`). تُغلَّف الثلاثة الأخيرة قبل الوضع في إطار بلا حدود ممتد على عرض الصفحة (`pipeline/flowColumns.ts`، `pipeline/spanEmbeds.ts`)، فتنضّد آلية واحدة الأربعة كلها. عند القطع، تُغلق الأعمدة النصية للشريط الحالي عند خط القطع (يُقيَّد ارتفاعها، وتصير `availableHeight` صفرًا)، وتحصل الكتلة على عمود خاص بها بعرض كامل مع `kind: 'span'`، ويُلحق تحتها شريط جديد من الأعمدة النصية (`band + 1`، بالموضع x والعرض نفسيهما، وبالحافة السفلى نفسها للشريط الذي يحلّ محلّه). لا تُضاف الأعمدة إلا إلحاقًا، فيبقى `columnIndex` يشير إلى `page.columns[i]`، ولا تحتاج المُخرِجات إلى رسم خاص: كل عمود يُقصّ إلى مربعه المحيط (موسّعًا بـ `columnClipRect`: 2pt لحبر الحروف، يُضاف إليها ما تتدلى به عناصر تصميم العمود خارج جانبيه، كلسان العنوان أو شارة الإطار، وما يبلغه تصميم العنوان فوق أعلاه؛ أما أسفله فيبقى الحافة، وهو المستطيل نفسه في واجهتي canvas وPDF)، ويُرسم الخط الفاصل بين الأعمدة لكل شريط بين الأعمدة النصية المتجاورة، بدءًا من أسفل الشريط الذي يشغله عنوان ممتد على عرض الصفحة في رأسها (`columnRuleSegments`)، وبخط الصفحة نفسها حين يحدّده قسم منسّق (`VDTPage.columnRule`، ويُقرأ عبر `pageColumnRule`). تتجاهل موازنة الأعمدة الأعمدةَ الممتدة والأعمدةَ الجانبية والأشرطةَ ذات الارتفاع الصفري. تقطع الكتلة الممتدة مباشرةً حيث يكون الشريط مستويًا (أعلى الصفحة، أو مباشرة بعد عنوان افتتاحي، أو كتلة ممتدة أخرى، أو شريط عائم علوي)؛ أما إذا وصلت إلى شريط غير مستوٍ فتقترح بدلًا من ذلك *سقفًا للشريط* (band cap) (`packages/postext/src/pipeline/bandCaps.ts`): تُقصَّر أعمدة الشريط الذي يبدأ بكتلة محتوى معيّنة إلى `ceil(Σ used / N / grid)` سطرًا، ويعيد `buildDocument` تشغيل تمريرة التوزيع مع السقف (ويزيده سطرًا في كل مرة حين يفيض الشريط المسقوف، حتى `MAX_BAND_CAP_RETRIES` = 3 مرات، ثم يتخلى عنه، فترجع الكتلة إلى أعلى الصفحة التالية)، فيملأ النص الأعمدة المقصّرة وفق كل قواعد الوضع، وينتهي مستويًا عند القطع، وتحتفظ الأعمدة المغلقة بما يتبقى من فراغ في `availableHeight` لتستوعبه الموازنة. والآلية نفسها تسوّي الشريط *الختامي* للفصل وللمستند (`headings.balancing.trailing`): حين يُبلغ افتتاح فصل، أو `:::part`، أو إطار `placement: 'fixed'` يختم الفصل، أو نهاية المستند، وأعمدة الشريط الحالي غير مستوية، يُقترح سقف من نوع `kind: 'trailing'` مفتاحه كتلة الحدّ؛ ولأن مفتاح السقف هو الكتلة التي تفتتح شريطه (وهذه الكتلة تتحرك كلما استوعبت صفحة سابقة أسطر موازنة إضافية)، تُحلّ السقوف الختامية *بعد* استقرار موازنة الأعمدة، مع تجميد تلميحات الموازنة، ثم تتيح جولة تحسين قصيرة لأدوات الموازنة (levers) أن تملأ ما تركه القطع ناقصًا. أما الإطارات ذات `placement: 'fixed'` فتغادر التدفق: يُثبَّت الإطار إلى منطقة محتوى الصفحة / مربع القص (trim box) / مربع النزف (bleed box)، وتتخلى الأعمدة النصية التي يغطيها عن تلك المنطقة (تُقطع من الأسفل أو الأعلى كشريط عائم، وتنتقل إلى الصفحة التالية عند التعارض)، ويذهب الإطار مع أبنائه إلى `page.floats`.

**الصفحات العمودية.** مع `layout.writingMode: 'vertical-rl'` تُخرج التمريرة صفحة أفقية مُدارة ربع دورة باتجاه عقارب الساعة. في مثل هذه الصفحة تكون منطقة المحتوى والأعمدة والكتل والأسطر والعناصر العائمة ومناطق الحواشي في **إحداثيات التدفق** (flow coordinates)، ويحمل `VDTPage.flow` الدوران الذي ينقلها إلى الورقة: نقطة التدفق (x, y) تقع عند (عرض الصفحة − y, x). ولا شيء في المراحل اللاحقة يحتاج إلى معرفة ذلك: الكسر والعناصر العائمة وقواعد الإبقاء معًا والموازنة تعمل في إطار التدفق كما في أي صفحة، وعمود التدفق صفٌّ (tier) على الورقة، ويطبّق كل مُخرِج الدوران حين يرسم (`flowToPage` و`pageToFlow` يحوّلان النقاط في الاتجاهين). وتبقى الترويسات وأرقام الصفحات وعلامات القص والخلفية في إحداثيات الورقة. تُخرَج الأشكال والجداول كتلًا قائمة تُدار عائدةً داخل الإطار، والحروف التي تقف قائمة تُدار عائدةً واحدًا واحدًا وقت الرسم.

### المرحلة 4: وضع الموارد

- **المُدخل:** خطة العناصر العائمة من المرحلة 1، والصفحات كما وُضعت حتى الآن
- **العمل:** تعويم كل مورد مُحال إليه إلى أول خانة حرّة بعد أول إحالة إليه: أسفل العمود المُحيل، أو أعلى / أسفل العمود الفارغ التالي، أو شريط في الصفحة التالية (`packages/postext/src/pipeline/floatPlacement.ts` يخطّط العناصر العائمة، و`pipeline/floatSlots.ts` يعدّد الخانات ويقيسها؛ وتحجز تمريرة التوزيع الأشرطة في أثناء مرورها)
- **تجري:** فور استقرار الكتلة التي تحمل أول إحالة، داخل المرور نفسه؛ والنص الذي يوضع بعد ذلك يتدفق حول الشريط

في `ResourcePlacement` حقول أخرى غير هذين: `rotate` و`width` و`align` و`columns` و`captionSide` و`shrink` و`minScale` و`captionMeasure` و`wrap` و`wrapGap` و`citingPage`. يشرح [الإعدادات › أنواع الموارد](/ar/docs/configuration-resources#أنواع-الموارد) و[صيغة المستند › الموضع](/ar/docs/document-format#الموضع) عمل كل واحد منها.

- **الوضع المؤجَّل:** العنصر العائم الذي لا يتسع في أي خانة من الصفحة الحالية ينتظر الصفحة التالية التي يفتحها التدفق، وعند حدّ فصل يُفرَّغ على صفحات تُفتح قبل الحدّ. تحتفظ الصورة بحجمها ما لم يسمح `placement.shrink` (أو `layout.floatShrink` للمستند كله) بتصغيرها إلى الحيّز المتاح في خانة. والجدول الأطول من أن تتسع له صفحة جديدة يُقطع بين الصفوف ويتابَع في الصفحات التالية مع تكرار صفوف رأسه (`tableStyle.overflow: 'split'`، القيمة الافتراضية)
- **المُخرج:** موارد موضوعة في أشرطة الصفحة (`page.floats`)، مع إنقاص ارتفاعات الأعمدة المتأثرة كي يتدفق النص حول الأشرطة

في وضع الموارد يصير الأمر أدق، لأن العناصر العائمة لا تشغل المساحة فحسب، بل تعيد تشكيل المساحة حولها. حين تستقر الكتلة التي تحمل الإحالة، تُعرض على العنصر العائم المعلّق الخاناتُ الحرّة في الصفحة الحالية بعدها: أسفل ذلك العمود، ثم أعلى العمود الفارغ التالي وأسفله (وللعنصر العائم الممتد على الصفحة: أسفل الصفحة، حين يبقى في كل عمود متسع)؛ وما لا يتسع في أي مكان ينتظر الصفحة التالية، حيث تحجز العناصر العائمة المعلّقة أشرطتها قبل أن يتدفق أي نص. تنكمش الأعمدة لتتسع بين الأشرطة، ويتدفق النص عبر الأعمدة المضيّقة دون انقطاع، ويرى القارئ الشكل قرب النقطة التي ذُكر فيها (لا عندها تمامًا). هذه ممارسة معتادة في التنضيد المهني، والكتب تفعلها باستمرار.

**قواعد الوضع.** إلى جانب توزيع الوضع، تتبع العناصر العائمة قيودًا تحريرية صارمة:

- **قاعدة ما بعد الإحالة.** يستقر العنصر العائم في أول خانة حرّة *بعد* أول إحالة إليه في النص، ولا يسبقها أبدًا. يصادف القارئ الإحالة أولًا، ثم يرى المورد. وإن لم يتسع العنصر العائم، يتأجل إلى الأمام إلى خانة أو صفحة لاحقة، لا إلى الخلف أبدًا.
- **ترتيب الإحالات داخل السلسلة.** تُعرض كل خانة على العناصر العائمة المعلّقة بترتيب أول إحالة، والعنصر الذي لا يتسع في أي مكان يؤخّر ما خلفه في سلسلة ترقيمه: الجدول 3 لا يستقر أبدًا بعد الجدول 4، والشكل 12 لا يسبق الشكل 11 أبدًا. ولا تؤخّر السلاسل بعضها بعضًا: الجدول المنتظر يسمح بمرور شكل لاحق. وحتى لا يضطر جدول طويل إلى انتظار صفحة جديدة، فإن الجدول الذي يُعرض عليه رأس عمود فارغ يُقطع على مقاس ذلك العمود ويُكمَل في الخانة التالية (العمود المجاور، أو أشرطة الصفحة التالية)، مع تكرار صفوف ترويسته.
- **حاجز الفصل.** لا تفلت العناصر العائمة من فصلها أبدًا. عند افتتاح فصل (مستوى عنوان مع `breakBefore` أو `span: 'page'`)، و`:::part`، ونمط إطار مع `floatBarrier: true`، ونهاية المستند، يوضع كل عنصر عائم معلّق أولًا (في الخانات الحرّة للصفحة، ثم على صفحات تُفتح قبل الحدّ، تضع كل منها قسرًا عنصرًا عائمًا واحدًا على الأقل) قبل فاصل الصفحة الخاص بالحدّ. وقبل فتح مثل هذه الصفحة، تُعرض على أي شكل أو جدول لا يزال معلّقًا الخاناتُ الحرّة في الصفحة الحالية مرة أخرى أيًّا كانت قيمة `position` فيه: العنصر العائم المخصّص لرأس الصفحة والمُحال إليه في الصفحة الختامية للفصل يأخذ أسفل تلك الصفحة، تحت الأعمدة الموزونة، بدلًا من صفحة خاصة به (وتحتفظ الإطارات العائمة بوضعها). ويرسل `:::pagebreak` العناصر العائمة المعلّقة إلى الصفحة التي تليه، بعد أي حشو لضبط زوجية الصفحة.
- **الحد الأدنى لمساحة النص.** في الصفحة المفتوحة حديثًا لا يُحجز شريط إلا إذا بقي متسع لـ 3 أسطر متن على الأقل في الأعمدة المتأثرة، مع استثناء واحد: يجوز وضع عنصر عائم مفرط الحجم قسرًا في شريط لا يزال كله نصًا، كي لا يعطّل شكل مهيمن الطابور إلى الأبد. وأما الخانة في الصفحة الحالية فيجب أن تتسع في الارتفاع المتبقي للعمود؛ ولا تنطبق قاعدة الأسطر الثلاثة هناك إلا بجوار شريط عائم آخر.
- **مسافة للتنفس.** تفصل فجوةٌ بارتفاع سطر متن واحد الشريطَ عن النص المجاور له.
- **المحاذاة مع شبكة خطوط الأساس.** تُقرَّب الأشرطة العلوية *صعودًا* إلى مضاعف لشبكة خطوط الأساس (فتكبر الفجوة تحت العنصر العائم)، فيقع كل سطر مُزاح على الشبكة. وتُثبَّت العناصر العائمة السفلية بحيث يقع آخر خط أساس في التعليق على الشبكة: يشترك التعليق في خط أساسه مع آخر سطر نصي في الأعمدة المجاورة، وتنتهي الصفحات عند الارتفاع نفسه عبر الأعمدة والصفحات المتقابلة.

**الترقيم حسب النوع عند أول إحالة.** لا تُرقَّم الموارد في markdown. يخصّص `pipeline/resourceNumbering.ts` لكل مورد رقمه عند أول إحالة إليه بترتيب القراءة، مستعملًا `ResourceType` الخاص بالمورد: يجمع `numberingTemplate` بين عدّاد النوع `{n}` وعدّادات العناوين `{h1}`..`{h6}` السارية عند الإحالة (مثلًا `'{h1}.{n}'` ← «1.7»)، ويتحكم `resetOn` في موعد إعادة العدّاد إلى البداية (`'never'` أو عند أي مستوى عنوان)، ويختار `counterFormat` الأرقام العشرية أو الرومانية أو الأبجدية. ويأتي النوعان المدمجان *الشكل* و*الجدول* من `defaultResourceTypes(locale)`، مترجمَين إلى لغة المستند. ولأن الترقيم يتبع ترتيب أول إحالة، فإن إدراج شكل جديد في وسط المستند يعيد ترقيم كل ما بعده تلقائيًا، دون أي تعديل في المصدر.

### المرحلة 5: الكسر وقواعد الإبقاء معًا

هذه المرحلة هي ما يميّز محرّك الإخراج من أداة تفرغ النص على الصفحة. تفرض قواعد الجودة التحريرية التي طبّقها المنضّدون المحترفون يدويًا منذ قرون، والتي يتجاهلها رسم النص الساذج تمامًا.

تتقاسم العملَ ثلاث آليات، تعمل كل منها حيث توجد المعلومة التي تحتاج إليها: **جزاء الكلمة المعزولة** داخل كاسر الأسطر، و**قسمة تُقيَّم بالدرجات** حيث تبلغ الفقرة نهاية العمود، و**قواعد الإبقاء معًا البنيوية** بين الكتل.

#### الأرامل والأسطر اليتيمة والكلمات المعزولة

**الأرامل والأسطر اليتيمة** أوضح علامات التنضيد غير المحترف:

- **الأرملة** (widow) سطر واحد من فقرة تُرك وحده أسفل عمود. تكمل الفقرة في العمود التالي، لكن ذلك السطر الوحيد يبدو عالقًا (كأن العمود انتهى قبل أوانه).
- **السطر اليتيم** (orphan) سطر واحد من فقرة عالق أعلى عمود. معظم الفقرة في العمود السابق، لكن سطرًا واحدًا انسكب إلى ما بعده (فيبدو منفصلًا عن سياقه).
- **الكلمة المعزولة** (runt) فقرة سطرها الأخير كلمة قصيرة واحدة (أو اثنتان)، أقصر بصريًا من أن يبدو سطرًا نصيًا حقيقيًا. أقل خطورة بنيويًا من الأرملة، لكنها مزعجة بالقدر نفسه للقارئ المتأني.

**تُحسم الكلمات المعزولة في كاسر الأسطر.** الكلمة المعزولة شأن الفقرة وحدها: سطرها الأخير بالقِصر نفسه أينما استقرت الفقرة. ولذلك فهي القاعدة الوحيدة من الثلاث التي يراها كاسر الأسطر Knuth-Plass. حين تُنهي مجموعةُ كسور الفقرةَ بسطر محتواه أضيق من `runtMinCharacters × normalSpaceWidth` (القيمة الافتراضية لـ `runtMinCharacters` هي 20: محتوى بعرض عشرين مسافة بين الكلمات، أي نحو 8 إلى 12 حرفًا)، يضيف الكاسر `runtPenalty` (الافتراضي 1000) إلى رداءة ذلك السطر داخل صيغة نقاط الجزاء المربّعة، فتتنافس على المقياس نفسه الذي تتنافس عليه رداءة السطر (التي تتشبع عند 10000) بدلًا من أن تتضاءل أمامها. يجتمع هذا الجزاء مع نقاط الجزاء المعتادة (الرداءة، وكلفة تقسيم الكلمات، وعدم تطابق فئة الملاءمة) في تحسين شامل واحد، ويجد الكاسر في أغلب الأحوال مجموعة كسور بلا كلمة معزولة. وحيث لا يجدها، يُنضّد `bodyText.tightenRunts` الفقرة بسطر أقل حين تستطيع المسافات بين كلماتها، مع قليل من التتبّع السالب، أن تستوعب الفرق. تسلّم وحدة القياس الجزاء إلى الكاسر (`measure/plain.ts`، `measure/rich.ts`) ويطبّقه `knuthPlass/breakpoints.ts`.

**تُحسم الأرامل والأسطر اليتيمة عند نهاية العمود.** يكسر كاسر الأسطر الفقرة لعرض معيّن. لا يعرف أين ستقع الفقرة في الصفحة، فلا يستطيع أن يعرف أي أسطرها سيختم عمودًا. أما تمريرة التوزيع فتعرف. حين لا تتسع أسطر الفقرة كلها في ما بقي من العمود، يجرّب `chooseParagraphSplit` (في `pipeline/orphanWidow.ts`) كل قسمة `k` للأسطر المكسورة سلفًا، من 0 إلى عدد الأسطر التي تتسع: يبقى `k` من الأسطر ويفتتح الباقي العمود التالي. وتُحسب لكل مرشّح درجة:

- `slackWeight · slack²` للأسطر التي يتركها فارغة أسفل العمود، و`slack` هو عدد الأسطر التي تتسع ناقصًا `k` (القيمة الافتراضية لـ `slackWeight` هي 10)؛
- مضافًا إليها `widowPenalty` (الافتراضي 1000) حين يترك أقل من `widowMinLines` سطرًا أسفل العمود؛
- ومضافًا إليها `orphanPenalty` (الافتراضي 1000) حين ينقل أقل من `orphanMinLines` سطرًا إلى أعلى العمود التالي.

تفوز القسمة ذات أدنى درجة، و`k = 0` تنقل الفقرة كاملة. القواعد ليّنة، والأرقام تبيّن مقدار لينها: جزاء قدره 1000 يساوي كلفة الفراغ لعشرة أسطر فارغة (10 · 10² = 1000)، فمع القيم الافتراضية تفوز القسمة التي تحترم القاعدتين كلما تركت أقل من عشرة أسطر فارغة في العمود. وبعد هذا الحد قد تكون الأرملة أو السطر اليتيم الخيار الأرخص. تختار القسمة من بين الأسطر التي صنعها كاسر الأسطر سلفًا؛ ولا تكسر الفقرة من جديد. وتمرّ عناصر القوائم بالقسمة نفسها عبر `avoidOrphansInLists` و`avoidWidowsInLists`، وتأخذ جزاء الكلمة المعزولة عبر `avoidRuntsInLists` (كلها `true` افتراضيًا).

كل هذا قابل للضبط في `BodyTextConfig`؛ راجع [الإعدادات › الأسطر اليتيمة والأرامل والكلمات المعزولة وقواعد الإبقاء معًا](/ar/docs/configuration-text#الأسطر-اليتيمة-والأرامل-والكلمات-المعزولة-وقواعد-الإبقاء-معًا). وضبط أي `*Penalty` على `0` يعطّل تلك القاعدة فعليًا.

#### قواعد الإبقاء معًا البنيوية

بعض التجميعات أكبر من فقرة واحدة: تمتد على كتل متجاورة ولا يمكن معالجتها بكسر الأسطر وحده. تفرض تمريرة التوزيع هذه القواعد حين تستقر كل كتلة، فتنقل مجموعات كاملة إلى الأمام حين كانت ستنقسم عبر فاصل عمود أو صفحة:

- **العنوان مع فقرته الأولى.** يجب ألا يظهر العنوان أبدًا أسفل عمود إذا كانت الفقرة التي يقدّمها ستبدأ في العمود التالي. يفرض ذلك `headings.keepWithNext` (الافتراضي `true`): إذا لم يتسع المكان للعنوان *مع* الحد الأدنى لأسطر الأرملة في المتن (`bodyText.widowMinLines`، الافتراضي `2`) من الكتلة التالية (أو سطر واحد فقط حين يكون `avoidWidows` معطّلًا)، يُدفع العنوان إلى الأمام ليرافق نصه.
- **العناوين المتتالية.** حين تظهر عدة عناوين متتابعة (مثلًا h2 يليه h3 تليه فقرة)، يجب أن تبقى المجموعة كلها معًا. ولا يجوز أن يُترك أي من العناوين عالقًا أسفل عمود دون المحتوى الذي يقدّمه.
- **القوائم التي تقدّمها نقطتان رأسيتان.** حين تنتهي فقرة بنقطتين رأسيتين تقدّمان قائمة مباشرة، يجب أن يبقى السطر الحامل للنقطتين مع بداية القائمة. يفرض ذلك `bodyText.keepColonWithList` (الافتراضي `true`): إذا كان وضع الفقرة لن يترك متسعًا لبدء أول عنصر في القائمة (كاملًا حين تُبقيه قواعد الأسطر اليتيمة والأرامل للقوائم كاملًا؛ وسطرًا واحدًا مع `bodyText.colonListRoom: 'line'`، كما كان حتى postext 1.4)، ينتقل السطر الأخير الحامل للنقطتين (أو الفقرة كلها، إن كانت سطرًا واحدًا) إلى الأمام مع القائمة. وكلما اضطرت هذه القاعدة إلى دفع الفقرة كلها وسبقتها مباشرة في العمود سلسلة من العناوين، تُسحب تلك العناوين إلى الأمام أيضًا كي لا يُنتهك `keepWithNext` بصمت؛ والاستثناء الوحيد حين لا يحتوي العمود إلا العنوان (أو العناوين) الذي دفعه نقل سابق إلى الأمام، وعندها يُبقي المحرّك الفقرة مع العنوان ويقبل الفصل الأخف بين النقطتين والقائمة تجنبًا للدوران بلا نهاية.
- **الشكل مع تعليقه.** الشكل وتعليقه وحدة لا تنفصل، ويتحركان معًا دائمًا.

حين يُكتشف انتهاك لقاعدة إبقاء معًا، يدفع المحرّك المجموعة كلها إلى العمود أو الصفحة التالية. فينتهي العمود الذي غادرته قصيرًا، بمقدار الأسطر التي كانت المجموعة ستشغلها. وملؤه مهمة [موازنة الأعمدة](#موازنة-الأعمدة).

هذه التصحيحات غير مرئية حين تُتقن (لا ينبغي أن يلاحظها القارئ أبدًا). لكن *غيابها* واضح فورًا لكل من يقرأ بانتباه: ذلك السطر الوحيد المحرج أعلى عمود، وتلك الفجوات غير المتساوية حيث كفّ المحرّك عن محاولة جعل النص يتسع. لدى الناشرين المحترفين أدلة أسلوب كاملة لمنع هذه المشكلات بالذات. وPostext يؤتمتها.

تجري الجولات من 3 إلى 8 واحدة بعد أخرى داخل بناء واحد (`buildDocumentBalanced`). أما الجولتان 1 و2 فخارجه: جولة المحتويات أو جولة أرقام الحواشي بناء كامل، له جولاته الخاصة من 3 إلى 8. لا حدّ للبناء في مجموعه، بل هذه الحدود وحدها.

**كل إعادة تشغيل توزيع كامل.** التلميح لا يرقّع شجرة التمريرة السابقة. تضع التمريرة المستند من جديد والتلميح سارٍ، فالعنوان الذي فوقه سطران إضافيان، أو الشريط المقطوع أعلى بستة أسطر، يمرّ بقواعد الكسر والإبقاء معًا نفسها التي يمرّ بها كل شيء آخر. ثم يفحص المشغّل النتيجة: سقف الشريط الذي لم يستقر إطاره عند القطع يُزاد أو يُتخلى عنه، وتمريرة الموازنة التي لم تحسّن مقطعًا تُهمل لذلك المقطع. وما يعيده المشغّل مؤلَّف من صفحات وضعتها تمريرة: تمريرة واحدة بكاملها، أو، بعد موازنة الأعمدة، صفحات كل مقطع من أفضل تمريرة حظي بها ذلك المقطع.

**ما يبلغ عنه المستند.** يعدّ `doc.iterationCount` تمريرات التوزيع التي يقوم عليها الإخراج الذي يعيده المشغّل: الأولى وتمريرات جولات سقوف الأشرطة والموازنة والأشرطة الختامية. ولا تدخل فيه تمريرات التعليقات الجانبية وصفحة الإحالة، ولا عمليات البناء السابقة في جولة محتويات أو جولة أرقام حواشٍ؛ ويُستدعى `BuildDocumentOptions.onPass` لكل تمريرة، مع زمنها الفعلي. أما `doc.converged` فيخص موازنة الأعمدة وحدها. قيمته `true` حين ينتهي كل مقطع بلا سطر فارغ في أعمدته القابلة للموازنة أو بلا أداة باقية يقترحها، و`false` حين يتوقف مقطع عند تمريرة لم تحسّنه، أو تنفد محاولاته، وفيه فجوة ما زالت مفتوحة. ومع تعطيل الموازنة قيمته `true`. والمستند الذي فيه `converged: false` مستند كامل: يحمل أفضل إخراج وجده المشغّل، وأحد أعمدته ينتهي قصيرًا.

### موازنة الأعمدة

- **تجري:** في الجولتين 6 و8 من المشغّل (مفعّلة افتراضيًا؛ ويعطّلها `headings.balancing.enabled: false`، وهي معطّلة افتراضيًا في النص العمودي وفي شبكة المحارف، انظر [الإعدادات › موازنة الأعمدة](/ar/docs/configuration-text#موازنة-الأعمدة))
- **المُدخل:** أفضل إخراج حتى الآن وأسطر الشبكة الفارغة أسفل كل عمود قابل للموازنة (`collectColumnGaps`، في `pipeline/columnBalancing.ts`)
- **العمل:** اقتراح أدوات (levers) تملأ كل عمود قصير في مكانه، وتشغيل تمريرة التوزيع بها، والاحتفاظ بالنتيجة لمقطع حين تنخفض درجة فجواته
- **المُخرج:** أعمدة تنتهي عند آخر سطر في شبكة الصفحة، مع تسجيل كل أداة على الكتلة التي طُبّقت عليها (`VDTBlock.balancing`)

تلاحظ الأعمدة غير الموزونة فورًا. وقواعد الكسر تتركها على الدوام: عنوان انتقل ليبقى مع نصه، وفقرة انتقلت كاملة تجنبًا لأرملة، وشكل لم يتسع. العمود الذي يتوقف قبل العمود المجاور بسطرين يبدو غير مكتمل، كأن الإخراج توقف في منتصف الطريق.

لا تغيّر أي كتلة عمودها لإصلاح ذلك. ففاصل العمود مرتبط بالعنصر الذي لم يتسع: الكتلة التي تفتتح العمود التالي كانت أطول من المتسع الذي بقي، وهي ما زالت أطول من متسع أصغر. لذلك يُملأ العمود القصير من داخله، بمقدار فجوته على الأكثر، ولا يعبر شيء إلى العمود التالي. التعديل موضعي، وهو ما يفعله المنضّد بيده: يضيف سطرًا من المسافة حيث تقبله العين. يكون العمود قابلًا للموازنة حين يتدفق المحتوى بعده إلى عمود لاحق في الصفحة نفسها، أو، للعمود الأخير في الصفحة، حين يستمر تدفق الصفحة إلى التالية. ويجوز أن تنتهي الصفحة الأخيرة من الفصل قصيرة؛ فشريطها الختامي يقطعه سقف ختامي قطعًا مستويًا (راجع [المرحلة 3](#المرحلة-3-التوزيع-على-الصفحات-والأعمدة)).

لكل فجوة تُقترح الأدوات بترتيب الأولوية التحريرية، وهو الترتيب نفسه الذي تسردها به [الإعدادات › موازنة الأعمدة](/ar/docs/configuration-text#موازنة-الأعمدة):

1. **إطار يختم العمود** يأخذ المتسع الذي تحت قاعدته مسافةً فوقه، فتقع قاعدته على آخر سطر في شبكة الصفحة، بمحاذاة آخر سطر في العمود المجاور. ويُسجَّل باسم `trailingCallout`.
2. **الصور ذات المنطقة الآمنة** (`Resource.safeArea`)، المضمّنة في العمود أو العائمة في رأسه أو أسفله وفوقه وحده، تطول بأسطر كاملة من الشبكة، مقصوصة داخل منطقتها الآمنة. والصورة الأطول لا تترك فجوة في الصفحة، ولذلك تعمل هذه الأداة قبل إضافة أي مسافة. وتُسجَّل باسم `flexFigure`.
3. **العناوين** تأخذ أسطرًا كاملة من الشبكة فوقها، سطرًا واحدًا في كل دور، والعنوان الأهم (صاحب أصغر رقم مستوى) أولًا، فينال الحصة الكبرى. والعنوان الواقع في أعلى العمود تمامًا لا يأخذ شيئًا، فتظل الأعمدة تبدأ عند أعلى الصفحة. ولا يأخذ العنوان بهذه الطريقة إلا أسطره الأولى قبل تجربة الأدوات التالية، ثم يأخذ المزيد، حتى حدّه الأقصى، حين لا يبقى لديها ما تعطيه. وتُسجَّل باسم `heading`.
4. **نهايات القوائم** تأخذ سطرًا من الشبكة حيث تنتهي قائمة. وتُسجَّل باسم `listEnd`.
5. **تحت المعادلات والإطارات والأشكال** يُضاف سطر من الشبكة: تحت معادلة مستقلة أو إطار يُستأنف النص بعده (`afterDisplay`)، وبين شكل أو جدول يتصدّر العمود والنص الذي تحته (`afterFloat`).
6. **الفقرات المرخاة** آخر الأدوات. تُكسر فقرات العمود، الأطول أولًا، كلٌّ منها بسطر زائد (`\looseness=+1` في TeX، عبر الخيار `looseness` في كاسر Knuth-Plass)، ولا يُقبل التنضيد الأطول إلا ما دام كل سطر ضمن `bodyText.maxWordSpacing`. وحين لا يكفي تباعد الكلمات وحده لكسب السطر، يجوز للفقرة أن تأخذ أيضًا أصغر تتبّع موجب يحقق ذلك، دون تجاوز حدّ أقصى. وتُسجَّل باسم `looseParagraph`.

الحدود القصوى وخيارات التفعيل والاستثناءات (شبكة المحارف، والصفحات الختامية، وعنصر عائم فوق عدة أعمدة) كلها مفاتيح في `headings.balancing`. تسردها صفحة الإعدادات وتُحدَّث معها؛ وهذه الصفحة لا تكررها.

يُختبر الاقتراح بتوزيع المستند به. التمريرة التي تطبّق الأدوات توزيع كامل، وبين حين وآخر تنقل أداةٌ محتوى عبر فاصل عمود مع ذلك: فقرة مقسومة لم يعد رأسها يتسع، أو عنصر عائم فقد خانته. فتتدفق الصفحات بعد تلك النقطة على نحو مختلف وتنفتح فجوات في مواضع أخرى. يرى المشغّل ذلك في الدرجة، فيهمل التمريرة لذلك المقطع، ويضع في القائمة السوداء الأدوات المطبّقة حديثًا في أول عمود تغيّر، فيُبقي الاقتراح التالي على الأدوات التي نجحت ويستبعد الأداة التي امتد أثرها إلى ما بعد عمودها.

**تتقارب الموازنة لكل مقطع على حدة.** الصفحات الواقعة بين الفواصل الصريحة (افتتاح فصل، أو `:::pagebreak`) تُخرَج مستقلة بعضها عن بعض: لا شيء يتدفق عبر مثل هذا الفاصل، فلا يمكن لأداة موازنة داخل مجموعة من الصفحات أن تحرك سطرًا من مجموعة أخرى. ولذلك تحكم حلقة موازنة الأعمدة على كل *مقطع* (segment) من هذا النوع بمفرده. ودرجة فجواته هي عدد أسطر الشبكة الفارغة أسفل أعمدته القابلة للموازنة. لا تزال التمريرة الواحدة تضع المستند كله، لكن كل مقطع يحتفظ بنصيبه من أدوات الموازنة أو يرفضه وفق درجة الفجوات الخاصة به، ويضع سلاسل التتابع (cascades) الخاصة به في القائمة السوداء، ويبلغ حالة الثبات وحده، وينفق ميزانيته الخاصة من المحاولات؛ والمقطع الذي تراجعت نتيجته بعد إعادة المحاولة يستعيد صفحاته من أفضل تمريرة حظي بها بينما تمضي المقاطع الأخرى. وهكذا يتوازن كتاب من ثلاثين فصلًا تمامًا كما تتوازن فصوله واحدًا واحدًا (صفحات الفصل في ملف PDF للكتاب كله مطابقة لملف PDF لذلك الفصل وحده)، بدلًا من أن تكلّف سلسلة تتابع واحدة في أي مكان كل صفحات الكتاب تمريرة إضافية.

الحدود صمام أمان. بعض الأعمدة لا يمكن إغلاقها: العمود الذي لا يحمل إلا فقرات قصيرة لا أداة له، والعمود الذي تدفع كلُّ أداة من أدواته كتلةً عبر فاصل العمود ليس فيه أداة يمكن الاحتفاظ بها. يحتفظ المحرّك بأفضل إخراج وجده ويترك ذلك العمود قصيرًا. ولأن الأدوات مسجّلة على الكتل، تستطيع بروفة أو اختبار أن يسرد الأعمدة التي لم يغلقها شيء (راجع [الإعدادات › أيّ أداة عملت](/ar/docs/configuration-text#أيّ-أداة-عملت)).


## نظام الإيقاع العمودي

ارفع كتابًا حسن التنضيد إلى الضوء. ستجد أسطر الصفحة اليسرى متحاذية مع أسطر الصفحة اليمنى. خط أساس السطر 5 في العمود 1 يقع في الموضع العمودي نفسه تمامًا الذي يقع فيه خط أساس السطر 5 في العمود 2. هذا هو الإيقاع العمودي، وهو من أول ما تفحصه العين المدرّبة عند تقييم جودة التنضيد. وهو أيضًا من أبرز ما يميّز Postext.

حين لا يحتوي العمودان إلا نص متن بالحجم نفسه، تكون المحاذاة بديهية: كل سطر بالارتفاع نفسه، فتتطابق خطوط الأساس طبيعيًا. يظهر التحدي حين يحتوي أحد العمودين عنوانًا بحجم خط أكبر، أو صورة بارتفاع اعتباطي بالبكسل، أو مسافة إضافية حول اقتباس كتلي. هذه العناصر «تكسر» الشبكة: يُزاح المحتوى تحتها بمقدار ليس مضاعفًا لخطوة خط الأساس، فتخرج خطوط الأساس في ذلك العمود فجأة عن التزامن مع العمود المجاور. ويضيع الانسجام البصري.

والهدف استعادته: يجب أن تتحاذى خطوط أساس نص المتن في الأعمدة المتجاورة أفقيًا، حتى حين تظهر العناوين أو الصور أو غيرها من العناصر ذات الارتفاع غير القياسي في عمود دون الآخر.

### شبكة خطوط الأساس

كل شيء يرتكز على رقم واحد. يعرّف المستند قيمة `baselineGrid` مشتقة من ارتفاع سطر نص المتن: فنص متن بحجم `16px` و`line-height` قدره `1.5` ينتج شبكة خطوط أساس قدرها `24px`. وينبغي أن يقع كل خط أساس لنص المتن على مضاعف لهذه القيمة. هذا هو العقد.

### العناصر الكاسرة للشبكة

بعض العناصر تكسر الشبكة حتمًا لأن ارتفاعها ليس مضاعفًا لـ `baselineGrid`:

- **العناوين** (حجم خط أكبر، وارتفاع سطر مختلف)
- **الصور** (ارتفاع اعتباطي بالبكسل)
- **الجداول** (ارتفاع متغيّر)
- **الاقتباسات الكتلية** (قد تستعمل حجم خط أو حشوة مختلفين)
- **مناطق الحواشي السفلية** (الحواشي أسفل العمود وخطها الفاصل: تنتهي منطقة نص العمود فوقها)

تُحفظ الشبكة عند الوضع، كتلةً كتلة. ولا تمرّ تمريرة لاحقة على الأعمدة بحثًا عن انحراف. ارتفاع سطر المتن خط واحد من الشبكة، فسلسلة أسطر المتن التي تبدأ على الشبكة تبقى عليها. وحين تضع تمريرة التوزيع كتلة يمكن أن تخرج عن الشبكة، تقرّب الارتفاع المستعمل في العمود صعودًا إلى خط الشبكة التالي قبل أن تبدأ الكتلة التالية. والكتل التي تُقرَّب بهذه الطريقة هي:

- آخر عنوان في سلسلة عناوين (تتوالى العناوين المتتالية بلا تقريب، والأخير يعيد محاذاة النص الذي بعدها)؛
- آخر عنصر في قائمة، أيًّا كانت المسافة بين العناصر؛
- المعادلة المستقلة؛
- الإطار، وكتلة الشيفرة، والشكل أو الجدول المضمّن في التدفق؛
- آخر فقرة في حاوية `:::paragraphs` وقصيدة `:::verse`، ولهما تباعد أسطر خاص بهما.

تُحسب المسافة تحت الكتلة (`marginBottom`) قبل التقريب، فالهامش حدّ أدنى والشبكة تقرر الباقي. في الشكل، يحمل العمود 1 عنوانًا ارتفاعه 36px على شبكة 24px، بلا هامش تحته. تقع قاعدته بعد خط من خطوط الشبكة بـ 12px، فيضيف التقريب 12px، ويبدأ سطر المتن التالي على الشبكة، بمحاذاة السطر المجاور له في العمود 2. ومع `marginBottom` قدره 16px كانت القاعدة ستقع عند 52px، وكان التقريب سيرفعها إلى 72px.

تحافظ أشرطة العناصر العائمة على الشبكة بطريقتها، الموصوفة في [المرحلة 4](#المرحلة-4-وضع-الموارد): يُقرَّب الشريط العلوي صعودًا إلى أسطر كاملة من الشبكة، ويُثبَّت العنصر العائم السفلي بحيث يقع آخر خط أساس في تعليقه على الشبكة. وموازنة الأعمدة تضيف مسافتها بأسطر كاملة من الشبكة، فتحافظ على الشبكة هي أيضًا.

لا شيء يقارن عمودًا بآخر. يبدأ كل عمود على الشبكة ويعود إليها كل تقريب، فتلتقي أسطر الأعمدة المتجاورة، وأسطر الصفحات المتقابلة، بلا تمريرة ثانية.

**إلغاء التقريب.** `snapToGrid: false` يُبقي المسافة تحت الكتلة كما هي. يمكن ضبطه في `headings` (لكل المستويات، أو لمستوى واحد، أو لنمط عنوان واحد)، وفي نمط فقرة، وفي نمط إطار، وفي `codeStyle`. وقد يقع النص الذي بعد مثل هذه الكتلة خارج الشبكة حتى أول كتلة تالية تُقرَّب. أما النص داخل الإطار فيتبع تباعد الأسطر الخاص بالإطار ولا شبكة له.


## واجهة المُخرِجات

هناك مصدر واحد فقط للحقيقة في قياس النص، هو وحدة القياس المبنية على مقاييس خطوط Canvas في Pretext، وكل مُخرِج (backend) يرسم من شجرة VDT المكتملة نفسها التي أنتجتها.

هذا اختيار مقصود، وله سبب حاسم: **يجب أن تطابق طريقة قياس النص طريقة رسمه تمامًا.** تخيّل أن القياس يستخدم مقاييس خطوط Canvas، بينما يستخدم أحد المُخرِجات مكتبة PDF بجداول تقنين أزواج (kerning) مختلفة قليلًا. عندها لن يطابق الإخراج الناتج النهائي. فالأسطر التي قاسها المحرّك على أنها تتسع في 320px قد تفيض أو تقصر عند رسمها. وكل بكسل من الانحراف كذبة. وحين يُقاس النص مرة واحدة ثم يُرسم في كل مكان من الهندسة الناتجة، لا يمكن للمُخرِجات أن تختلف: فمواضع فواصل الأسطر وارتفاعات الأعمدة ومواضع الموارد تُثبَّت في VDT قبل أن يعمل أي مُخرِج.

لهذا السبب لا يعيد مُخرِج PDF، مثلًا، قياس النص: بل يستهلك VDT مكتملة ويحوّل إحداثياتها بالبكسل إلى نقاط PDF. مقاييس Canvas هي مصدر الحقيقة، وPDF مجرد وسيلة نقل. ومن يستخدم `renderToPdf` (من الحزمة `postext-pdf`) يمرّر شجرة VDT نفسها التي كان سيمرّرها إلى `renderToCanvas` أو `renderToHtml`، والمخرجات الثلاثة مضمون تطابقها.

### واجهة البرمجة المتاحة (API)

المُخرِجات دوال بسيطة تعمل على `VDTDocument`، وليست تسلسلًا هرميًا من الأصناف. لا توجد واجهة `PostextBackend`، بل نقاط دخول الرسم لكل مخرج والدوال المساعدة التي يحتاجها:

```typescript
// Canvas (from 'postext')
renderToCanvas(doc, options?): HTMLCanvasElement[];     // one canvas per page
renderPage(page, doc, options?): HTMLCanvasElement;     // a single page
renderPageToCanvas(page, doc, canvas, options?): void;  // draw into an existing canvas

// Canvas resource-image registry — decoded images keyed by Resource fileId
registerResourceImage(fileId, image, options?): void;   // options: { vector?, singleInk? }
unregisterResourceImage(fileId): void;
clearResourceImages(): void;

// HTML (from 'postext')
renderToHtml(doc, options?): string;
renderToHtmlIndexed(doc, options?): HtmlRenderIndex;    // per-page / per-block breakdown

// PDF (from 'postext-pdf')
renderToPdf(doc, options): Promise<Uint8Array>;

// EPUB (from 'postext-epub'), a book's chapters in order
renderToEpub(docs, options): Promise<Uint8Array>;
```

ولأن البيانات الثنائية للموارد تُحفظ خارج الشجرة، يحلّ كل مُخرِج معرّفات `fileId` بطريقته. يحتفظ مُخرِج Canvas بسجلّ لكائنات `CanvasImageSource` المفكوكة: يسجّل التطبيق المضيف كل صورة نقطية أو SVG مرة واحدة باستدعاء `registerResourceImage(fileId, image)`، ويبحث عنها المُخرِج وقت الرسم. أما مُخرِج HTML فيتلقى في خياراته دالة الحلّ `resourceImageUrl(fileId)`، ويُصدر وسوم `<img>` تشير إلى أي عناوين URL يعيدها المضيف (عناوين كائنات، أو data URI، أو مسارات CDN). ويتلقى مُخرِج PDF مزوّدًا `resourceBytes` ويضمّن البايتات الفعلية؛ ويتلقى كاتب EPUB مزوّدًا مماثلًا ويخزّن كل صورة مرة واحدة ملفًّا من ملفات الكتاب. ويُرسم مورد الفيديو غلافَه، وهو صورة نقطية كغيرها؛ ويتلقى مُخرِج HTML أيضًا دالة الحلّ `resourceVideoUrl(fileId)` لملفات الفيديو التي يشغّلها، ويخزّن كاتب EPUB هذه الملفات تحت `media/`. ويرسم مُخرِج PDF علامة التشغيل ورمز QR مسارات متجهية فوق الغلاف، وإذا كان `video.linkPoster` مفعّلًا وضع فوقه تعليق رابط URI يفتح `video.link`؛ وفي ملف PDF الموسوم ينضمّ الرابط إلى عنصر `Figure` الخاص بالغلاف، ويبدأ نصّه البديل باسم النوع (*فيديو: …*). ولا تحتاج موارد الجداول إلى شيء من هذا، فنموذجها مضمّن، وكل مُخرِج يرسم الخلايا من هندسة الجدول في VDT.

وتستحق `renderToHtmlIndexed` ملاحظة: فإلى جانب سلسلة HTML الكاملة، تعيد تفصيلًا لكل صفحة ولكل كتلة (`HtmlRenderIndex`) كي يقارن المستدعون بالرسم السابق ولا يرقّعوا إلا الأشجار الفرعية في DOM التي تغيّر HTML الخاص بها فعلًا، وهذا هو مسار المعاينة الحيّة في Sandbox.

تستهلك المُخرِجات الأربعة المتاحة `VDTDocument` نفسها. والفصل بين `postext` (التي تصدّر مُخرِجَي Canvas وHTML) و`postext-pdf` (التي تصدّر مُخرِج PDF) سببه الاعتماديات وحدها: فمسار PDF يجلب `pdf-lib` و`@pdf-lib/fontkit`، ومعظم عمليات التكامل على الويب لا تحتاج إليهما. ثبّت `postext-pdf` فقط حين تريد فعلًا إصدار بايتات PDF. و`postext-epub` حزمة مستقلة للسبب نفسه، ولا تُحتاج إلا للكتب الإلكترونية. وسطر الأوامر ليس مُخرِجًا خامسًا: `postext-cli` يشغّل هذه الكاتبات نفسها حيث لا متصفح.

**أين يعمل الإخراج:** يقيس المحرّك النص على Canvas، فيعمل حيثما أُعطي واحدًا. في المتصفح يمكن تشغيل خط المعالجة (pipeline) إما على الخيط الرئيسي (`buildDocument`) أو داخل Web Worker مخصّص (`createLayoutWorker` من `postext/worker`)، ومسار العامل هو طريقة التكامل الموصى بها للتطبيقات التي تقودها واجهة المستخدم، لأنه يُبعد القياس وتمريرات التوزيع عن الخيط الرئيسي، ويدعم الإلغاء بقاعدة «الأحدث يفوز» (last-wins) عبر `AbortSignal`، ويملك ذاكرته المؤقتة الخاصة للقياس وذاكرة مؤقتة لصور المعادلات النقطية، فتبقى عمليات إعادة البناء المتتالية رخيصة. انظر [الإعدادات › تشغيل الإخراج في Web Worker](/ar/docs/configuration-programmatic-usage#تشغيل-الإخراج-في-web-worker) لنمط التكامل الكامل. وخارج المتصفح يشغّل [سطر الأوامر](/ar/docs/command-line) خط المعالجة نفسه، ويقوم فيه Skia مقام Canvas المتصفح، فيتوزّع الكتاب على الصفحات نفسها في الطرفية أو في برنامج نصي أو على خادم بناء.


## استراتيجية الأداء

الفرق بين أداة بطيئة وأخرى تبدو سحرية يقارب 10 أضعاف. فإخراج يستغرق 500ms يعني أن المستخدم يرى تقطّعًا ظاهرًا في كل مرة يغيّر فيها كلمة. أما إخراج يستغرق 50ms فيبدو فوريًا، كأن المستند كان هناك دائمًا. ولا يمكن ترقيع هذا الفارق لاحقًا، بل يجب تصميمه منذ اليوم الأول.

انظر إلى ما يواجهه المحرّك: آلاف الكتل النصية عبر مئات الصفحات، تُخرَج من جديد عند كل تعديل، وعدة مرات حين يحتاج الإخراج إلى جولاته. وتواجه محرّكات الألعاب فئة المشكلات نفسها: معالجة آلاف الكائنات (الهندسة والفيزياء والإضاءة والذكاء الاصطناعي) 60 مرة في الثانية، وتحلّها بألا تكرر عملًا أنجزته. ويطبّق Postext ذلك على أكثر ما يكلّفه، وهو قياس النص.

### المبادئ

1. **الحساب في الذاكرة.** تتسع شجرة VDT كاملة في الذاكرة. لا قراءات من DOM أثناء الإخراج. ولا يُلمس DOM
   إلا في النهاية تمامًا، أثناء الرسم.

2. **تمريرات كاملة على قياسات محفوظة.** إعادة تشغيل تمريرة التوزيع لا تبحث عمّا تغيّر:
   تضع المستند من جديد من أول كتلة. وكلفة ذلك محتملة لأن القياس، وهو الجزء المكلف،
   محفوظ في الذاكرة المؤقتة لكل فقرة (المبدأ 5). والتمريرة التي لا تغيّر شيئًا في نص الفقرة
   أو خطوطها أو عرضها تقرأ أسطرها من الذاكرة المؤقتة.

3. **جولات محدودة.** لكل نوع من إعادة التشغيل حدّ ثابت (راجع
   [مشغّل التمريرة](#مشغّل-التمريرة))، ولموازنة الأعمدة حدّ لكل مستند فضلًا عن حدّ
   لكل مقطع، فلا يستطيع كتاب كثير الفصول أن ينفق تمريرات بلا نهاية. ويمكن قياس كلفة البناء
   تمريرةً تمريرة: يبلغ `BuildDocumentOptions.onPass` عن كل تمريرة وزمنها الفعلي.


4. **سرعة Pretext.** قياس النص بسرعة تفوق DOM بـ300 إلى 600 ضعف يعني أن المحرّك يستطيع
   إعادة قياس النص على سبيل التجربة (بتجربة عروض أعمدة مختلفة، ومواضع تقسيم الكلمات بالواصلة، وتعديلات
   التتبّع) دون أن يحجب الخيط الرئيسي.

5. **ذاكرة مؤقتة متعددة الطبقات للقياس.** تحتفظ وحدة القياس (`packages/postext/src/measure/`) بذاكرة
   مؤقتة صريحة للقياس مفتاحها النص والخطوط والعرض وكل خيار يؤثر في الإخراج،
   فوق ذاكرة `prepare()` المؤقتة الخاصة بـPretext وذاكرة مؤقتة خام لعرض النص. وإعادة قياس
   فقرة لم تتغير تكلّف بحثًا واحدًا في جدول. وحين تتغيّر أوجه عائلة، يطرح المحرّك عروض تلك العائلة
   وذاكرة Pretext المؤقتة، وتطرح ذاكرة القياس المؤقتة الكتل المنضّدة بها عند أول بحث تالٍ فيها
   (فهي تحمل الجيل الذي مُلئت فيه)، فتصحّ عروض الحروف بعد اكتمال تحميل الخطوط دون أي استدعاء
   من المضيف؛ وتطرح `clearMeasurementCache()` كل العائلات.

6. **تقسيم الأسطر في المسار الساخن.** أُعيدت كتابة معالجة العُقد النشطة في Knuth-Plass طلبًا للسرعة:
   تُضغط مجموعة العُقد النشطة في مكانها كلما تقاعدت عُقد، وتُزال المرشّحات المكرّرة
   لكل زوج (سطر، فئة ملاءمة) فلا تبقى إلا العقدة ذات أدنى نقاط جزاء لكل مفتاح. والنتائج
   الخوارزمية متطابقة: مجموعات الفواصل نفسها، لكنها تُحسب أسرع.

7. **البناء خارج الخيط الرئيسي.** تشغّل نقطة الدخول `postext/worker` خط المعالجة كاملًا
   داخل Web Worker مخصّص. يرسل الخيط الرئيسي `{ content, config }`
   و`AbortSignal`؛ فيسجّل العامل الخطوط (المنقولة بصيغة `ArrayBuffer`)، ويشغّل
   تمريرات التوزيع، ثم يعيد `VDTDocument` المكتملة. وأي استدعاء أحدث لـ`build()`
   يلغي الاستدعاء السابق تعاونيًا: إذ يشغّل العامل `buildDocumentAsync`، التي تفحص خطّاف إلغاء لكل كتلة
   وبين التمريرات وترمي `BuildCancelledError`، فلا ينتظر مستخدم يكتب في محرّر
   إخراجًا تجاوزه الزمن. ويحتفظ العامل أيضًا بذاكرة مؤقتة دائمة خاصة به
   للقياس، وبذاكرة مؤقتة لصور المعادلات النقطية مفتاحها المحتوى، كي تبقى كائنات `MathRender`
   المنسوخة بالاستنساخ البنيوي (structured clone) عبر عمليات إعادة البناء دون إعادة تحويلها إلى صور نقطية.

8. **VDT مزدوجة الوصول.** تتيح الشجرة (`pages > columns > blocks`) وصولًا هرميًا للعمل
   الذي يجري صفحة بصفحة أو عمودًا بعمود (تقيس موازنة الأعمدة الفجوة أسفل
   كل عمود). وتتيح مصفوفة مسطّحة موازية `blocks[]` وصولًا مباشرًا إلى كل كتلة
   أينما كانت (تقرأ منها جولة أرقام الحواشي العلامة التي طبعتها كل حاشية). وكلا العرضين
   يشير إلى كائنات الكتل نفسها (لا تكرار، بل طريقتان لاجتياز
   البيانات نفسها).

### الإخراج من جديد

لا توجد نقطة دخول تزايدية: لا استدعاء يأخذ VDT مكتملة ويحدّثها. حين يتغير المحتوى أو الإعدادات (ضغطة مفتاح، أو مقاس صفحة آخر)، يستدعي المضيف `buildDocument` من جديد ويحصل على مستند جديد.

ما ينتقل من بناء إلى الذي يليه هو القياس. أنشئ `MeasurementCache` مرة واحدة باستدعاء `createMeasurementCache()` ومرّرها معاملًا ثالثًا في كل استدعاء لـ`buildDocument`. الفقرة التي لم يتغير نصها ولا خطوطها ولا عرضها ولا خيارات كسرها تُقرأ منها، فالمحرّر الذي يُخرج المستند عند كل ضغطة مفتاح لا يقيس إلا الفقرة التي يُكتب فيها. وتغيير مقاس الصفحة أو عدد الأعمدة يغيّر العروض، فتُقاس تلك الفقرات من جديد؛ وتظل نتائج `prepare()` في Pretext صالحة، لأنها تعتمد على الخط والنص لا على العرض، فلا يجري إلا حساب `layout()` الرخيص. ونتيجة التحليل محفوظة أيضًا.

وللمحرّر الحيّ، يفعل `createLayoutWorker` (من `postext/worker`) هذا كله خارج الخيط الرئيسي: يملك العامل ذاكرة مؤقتة للقياس تعيش ما عاش، وأي استدعاء أحدث لـ`build()` يلغي الاستدعاء الجاري. انظر [الإعدادات › ذاكرة القياس المؤقتة](/ar/docs/configuration-programmatic-usage#ذاكرة-القياس-المؤقتة) و[تشغيل الإخراج في Web Worker](/ar/docs/configuration-programmatic-usage#تشغيل-الإخراج-في-web-worker).

### قياسات الأداء

يوجد قياسا أداء في `packages/postext/src/__bench__/`. يتخطاهما `pnpm test`؛ ويشغّلهما `pnpm bench` عند تشغيله في `packages/postext`. يُخرج `chapter.bench.test.ts` فصلًا بحجم فصل من كتاب مدرسي (أربعون قسمًا من عناوين وفقرات وقوائم) خمس مرات بذاكرة قياس مؤقتة فارغة (تشغيل بارد) وخمس مرات بذاكرة ممتلئة (تشغيل دافئ)، ويبلغ عن الوسيطين وعن عدد التمريرات. ويُخرج `cjkChapter.bench.test.ts` الفصل الأول من 红楼梦 ويعدّ المحارف المرسلة إلى `measureText`، ليُلزم مُنضِّد CJK بكلفة خطية في طول الفقرة.

```typescript
// From packages/postext/src/__bench__/chapter.bench.test.ts
const cold: number[] = [];
for (let i = 0; i < ROUNDS; i++) cold.push(time(() => buildDocument({ markdown }, config, createMeasurementCache())));

const warmCache = createMeasurementCache();
buildDocument({ markdown }, config, warmCache);
const warm: number[] = [];
for (let i = 0; i < ROUNDS; i++) warm.push(time(() => buildDocument({ markdown }, config, warmCache)));

const passes: BuildPassInfo[] = [];
const doc = buildDocument({ markdown }, config, createMeasurementCache(), { onPass: (p) => passes.push(p) });
// [bench] chapter: … pages, … passes (… ms), iterationCount=…; cold median … ms, warm median … ms (5 rounds)
```

تحفّظ من باب الأمانة: لا يوجد canvas في Node، فيستعيض القياسان عن قياس النص ببديل وهمي (stub)، وأزمنتهما المطلقة ليست أزمنة المتصفح. أما نسبة التشغيل البارد إلى الدافئ وعدد التمريرات فهما كما في المتصفح، وأي تراجع في أحدهما يظهر هنا قبل أن يظهر في Sandbox. قياس الفصل يبلغ عن أرقام ولا يُفشل البناء؛ والقياس الصيني يتحقق من أن المحارف المقيسة تبقى دون ثلاثة أضعاف طول أطول فقرة. ولا يجري أي منهما في CI: تُكتشف حالات التراجع بمقارنة الأرقام بين التشغيلات حين يتغير مسار ساخن (كما جرى عند إعادة كتابة معالجة العُقد النشطة في Knuth-Plass). الأداء ميزة لا أمنية، لكن ضمانه اليوم هو القياس والمراجعة، لا خط معالجة يفشل.

## خارج النطاق

كل حدّ من هذه الحدود اختيار مقصود: فالمحرّك معقّد بما يكفي وحده،
وتحمّل مسؤوليات مكانها في موضع آخر هو أسرع طريق إلى عدم إنجازه أبدًا.

- **التحرير المرئي المباشر (WYSIWYG).** Postext محرّك إخراج، لا محرّر. محتوى يدخل، وهندسة تخرج. وبناء سطح تحرير تفاعلي (إدارة المؤشر، والتحديد، والتراجع والإعادة، ومعالجة الإدخال) مشكلة منفصلة تمامًا. يمكن أن يكون Postext مُخرِج الرسم لمحرّر، لكنه لا يوفّر بنفسه إمكانات التحرير.
- **غلاف لـ column-count في CSS.** يحلّ Postext محلّ تخطيط الأعمدة المتعددة في CSS، ولا يغلّفه. فهو يحسب هندسة دقيقة التموضع من الصفر، لأن خوارزمية تخطيط الأعمدة في المتصفح تفتقر إلى التحكم في مواضع الموارد، ومنع الأسطر الأرامل واليتيمة، والقواعد الطباعية العابرة للأعمدة. وهذه هي الغاية كلها.
- **إدارة نقاط التوقف المتجاوبة (breakpoints).** يحسب Postext الإخراج عند مقاس صفحة معيّن. والمستهلك هو من يقرر متى يعيد الإخراج (عند تغيير حجم نافذة العرض، أو عند تغيّر الاتجاه). لا يدير Postext نقاط التوقف ولا استعلامات الوسائط ولا قرارات التصميم المتجاوب. فهذه مهمتك أنت.
- **التحرير التعاوني في الزمن الحقيقي.** Postext عملية حساب إخراج عديمة الحالة (محتوى يدخل، وهندسة تخرج)، لا نظام مستندات تعاوني فيه حلّ للتعارضات أو تحويلات تشغيلية (operational transforms) أو إدراك لتعدد المستخدمين.
- **ملفات الخطوط.** تحمّل حزمة `postext` الخطوط لكنها لا تتضمّنها. تحمّل `prepareFonts` قبل البناء الأول كل وجه تطلبه الإعدادات ونصها، والوجه الذي لم تستطع مجموعة الخطوط تقديمه يظهر بين تحذيرات المستند بوصفه `fontFallback`. أما الملفات فيقدّمها التطبيق المضيف: قاعدة `@font-face` في الصفحة، أو دالة `resolve` تقول أين يوجد كل وجه. انظر [الإعدادات › تحميل الخطوط قبل الإخراج](/ar/docs/configuration-programmatic-usage#تحميل-الخطوط-قبل-الإخراج).

### أين تقع أنواع VDT

تقع أنواع VDT (`VDTDocument`، `VDTPage`، `VDTColumn`، `VDTBlock`، `VDTLine`، `VDTLineSegment`، `ResolvedResourceBlock`، `VDTResourceTableLayout`، `BoundingBox`، وأخواتها) في `packages/postext/src/vdt.ts`، إلى جانب دوال المصنع المساعدة (`createVDTDocument`، `createVDTPage`، `createVDTBlock`، …) و`computePageTextExtent`. لا توجد وحدة منفصلة لواجهة المُخرِجات، فنقاط دخول الرسم الموصوفة في [واجهة المُخرِجات](#واجهة-المُخرِجات) تُصدَّر مباشرة من `postext` (Canvas، HTML) ومن `postext-pdf` (PDF) ومن `postext-epub` (EPUB).
