# Postext架构

如果你用过React，就已经懂得这里的核心技巧。React先在内存里构建虚拟DOM，做差异比较，然后才去改动浏览器里真实的DOM。Postext做的是同一件事，只不过它构建的不是UI组件，而是一棵由**页面、栏、文本块和边界框**组成的树。一份多页、多栏文档的全部几何信息，在渲染出第一个像素之前就已算好。每个段落、标题、图片、脚注和引文框都放在精确的坐标上，并且遵守延续了几百年、CSS根本无法表达的排版规则。

这一切得益于[`@chenglou/pretext`](https://github.com/chenglou/pretext)。它是一个不依赖DOM的文本测量库，比浏览器的布局重排快300–600倍。项目背后的故事（十年间的屡次失败、卡住所有尝试的那个瓶颈，以及最终消除它的那个库）见[简介](/zh/docs/introduction)。

## 核心思路

设想一份74页的双栏文档，比如一份公司年报，或者一本插图密集的教材。你把它交给Postext，引擎就在内存里构建出完整的版面：每一页、每一栏、每个段落的确切位置和像素尺寸。想知道第72页第2栏里有什么？答案已经在那里，不需要渲染。引擎已经决定好每个段落在哪里断行、每张图片放在哪里、怎样避免段末孤行和段首孤行，以及相邻各栏的基线如何对齐。

下面说说这一点为什么如此重要。

排版规则彼此牵连，而且牵连得让人头疼。第5页有一个段末孤行，也就是被孤零零留在栏底的最后一行，你把它拉回前一栏，问题解决了。可这一改动让第5页那一栏变短，内容随之后移，第6页就可能冒出一个段首孤行：段落的第一行被单独推到新的一栏，和段落其余部分分离。仅仅为了*发现*自己制造了新问题，你就需要整份文档的版面都可供检查。而要*修正*它又不在别处引出新问题，你就得能够调整、重新测量、重新检查整份文档。

这就是“先全部算好，再渲染”的理念。它不是性能技巧。专业排字工几百年来一直遵循几十条相互关联的排版规则，要运用这些规则，这是唯一的途径。

**内容在引擎中经历的过程如下：**

1. **解析器**读取你的增强Markdown，把它变成一个由带类型的内容块组成的扁平列表：只有内容和结构，还没有位置
2. **放置遍**把这个列表遍历一次，构建出VDT。它按每个块即将进入的那一栏的宽度，通过Pretext测量这个块，把文本、浮动体和框放入页面和栏，并在行进中执行分页规则和保持同页规则
3. **驱动器**（`buildDocument`）在某个决定要依据整个版面的结果时重新运行这一遍：印出页码的目录，必须让上方各栏在切割处齐平的通栏框，提前结束的一栏。每次重新运行都从前一遍取得提示，每一类重新运行各有自己的上限
4. **最终的VDT**就是完整的版面几何：每个元素都知道自己的页码、所在栏、位置和边界框。在任何渲染发生之前，文档就已完全“排好”
5. **后端**遍历完成的VDT，把它渲染成目标格式：栅格化的canvas位图、由定位HTML元素组成的DOM树、嵌入字体的PDF文档，或EPUB。同一份VDT供四者使用，选哪个后端纯粹是输出方面的决定


## 输入层

### 内容模型

内容模型既是一种数据结构，也是一种理念。你描述要说*什么*，而不是*如何*排版。版面上的决定由引擎来做。

<Illustration name="ContentModel" data='{"title": "内容模型：markdown、资源、注释", "desc": "Postext的输入把markdown（阅读顺序和语义结构）与资源（位图、SVG、表格）和注释分开。引擎按ID解析行内的:ref引用和::resource嵌入，并生成VDT。", "caption": "Markdown决定阅读顺序，资源提供视觉数据。", "contentTitle": "PostextContent", "markdown": "markdown", "markdownSub": "阅读顺序 + 按id的:ref / ::resource", "resources": "resources[]", "resourcesSub": "位图、SVG、表格", "notes": "metadata", "notesSub": "标题、作者、日期", "resolveMarker": "按id解析：:ref{id=…}、::resource{id=…}", "engineLabel": "引擎", "vdtLabel": "VDT"}' />

```typescript
// packages/postext/src/types.ts

interface PostextContent {
  markdown: string;            // 带:ref / ::resource标记的增强markdown
  metadata?: DocumentMetadata; // 标题、副标题、作者、发布日期……
  resources?: Resource[];      // 位图、SVG、表格、视频，按id引用
  notes?: PostextNote[];       // 不读取：脚注在markdown中写成[^id]
}

interface Resource {
  id: string;                  // 稳定的id，供行内:ref引用
  typeId: string;              // 该资源所属的ResourceType（'figure'、'table'……）
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  caption?: string;            // 类型前缀和编号由计算得出，不写在这里
  altText?: string;
  createdAt: number;
  updatedAt: number;
  // 恰好一种与kind对应的数据：
  bitmap?: { fileId: string; format: string; width: number; height: number };
  svg?: { fileId: string; width?: number; height?: number };
  table?: { model: TableModel };
  video?: ResourceVideo;       // 从哪里播放；页面上画的是它的封面
  placement?: ResourcePlacement; // 可选：单个资源覆盖浮动设置
  safeArea?: ResourceSafeArea;  // 位图 / svg：{ x, y, width, height }，以比例表示，始终显示的部分
}
```

**资源**承载视觉数据：题注、替代文本，以及与其类型对应的数据。二进制数据（位图、SVG）存放在*带外*：资源只保存一个`fileId`，渲染器在绘制时再去解析它（沙盒把这些字节保存在IndexedDB里）。表格资源是例外：它的`TableModel`（一个带合并和对齐信息的单元格网格）随资源一起内联传递，因为它是结构化数据，而不是字节。
**注释**写在markdown里：引用脚注的地方写`[^id]`标记，定义`[^id]:`自成一段，可以放在本章的任何位置。引擎按首次引用的顺序给脚注编号，把每条脚注排在引用它的那一行所在栏的底部，上方有一条短线；设置`footnotes.placement: 'chapterEnd'`时，则排在该章最后一个块之后（见[脚注](/zh/docs/document-format#脚注)和[配置 → 脚注](/zh/docs/configuration-notes-references#脚注)）。内容模型仍然接受`notes`数组，但流水线的任何阶段都不读取它。

这种分离是一个有明确取向的设计选择，其意义比看上去要大。markdown掌管*阅读顺序*和*语义结构*：什么在前，什么是标题，脚注在哪里被引用、写了什么。资源数组掌管*视觉数据*：图片尺寸、题注文字、表格单元格。两者分开后，同一份markdown只需改变配置，就能排成完全不同的样子。双栏的学术版式和单栏的博客文章可以共用同一份源内容。引擎也可以做出安放上的决定，比如因为这一栏放不下而把图片推迟到下一栏，却完全不必改动你的源内容。

```typescript
// 示例：一篇引用了一幅图的简单文章
const content: PostextContent = {
  markdown: `
# The Art of Typography

The history of typography begins with Gutenberg's
movable type, shown in :ref{id="printing-press"}.
His invention transformed the production of books.

The technique spread rapidly across Europe, reaching
Italy by 1465 and France by 1470.
  `,
  resources: [
    {
      id: 'printing-press',
      typeId: 'figure',
      kind: 'bitmap',
      caption: 'A reconstruction of the original press.',
      altText: "Reconstruction of Gutenberg's printing press",
      createdAt: 1765379100000,
      updatedAt: 1765379100000,
      bitmap: { fileId: 'press-photo', format: 'jpeg', width: 600, height: 400 },
    },
  ],
};
```

资源通过id与正文关联，**只要引用它，就能把它纳入文档**。行内的`:ref{id="printing-press"}`同时做两件事：它在正文中渲染出资源经计算得到的编号（“Fig. 1”）；并且在阅读顺序中的第一次引用处，把资源*浮动*到页面上，在该引用附近页面的顶部或底部预留一个区带，和印刷排字工的做法完全一样。你不需要再安放一次这幅图。少数资源必须位于文本流中的某个确切位置，这时可以把`::resource{id="…"}`单独写成一行，作为可选的块级嵌入：只有当资源解析后的`placement.position`为`'here'`（即不参与浮动）时，它才在原处渲染；对于浮动的资源，它只被当作又一次引用。作者从不需要考虑安放问题，由引擎来考虑。

### 解析策略

解析有意设计成流水线中最简单的一步。Markdown输入后，输出一个由带类型的内容块组成的扁平列表（`ContentBlock`，位于`packages/postext/src/parse/`）：标题、带行内片段的段落、列表项、指令。解析结果有记忆化（`parseMarkdownMemo`），所以同一次构建的各遍只解析一次，之后对同一文本的构建也是如此。资源引用在每个放置遍开始时按ID在`resources[]`数组中解析。脚注定义（以`[^id]:`开头的段落）也在这时离开文本流，按id保存，留给引用它们的标记；`notes[]`数组不读取。

可以把它看成一份清单：“先是一个标题，然后是一个200词的段落，然后是一处图的引用，然后又是一个段落。”没有测量，没有定位，也完全没有版面上的决定。只有在放置遍测量了一个块并给了它位置之后，`VDTBlock`才存在。


## 虚拟文档树（VDT）

设想你请一位专业排字工排一整本书，他交给你的不是印好的页面，而是一张电子表格。每一行是一个元素，每个单元格是一个精确的测量值：“标题位于(40, 30)，第一段从(40, 78)开始，高144px，图片放在第3页第2栏的顶部……”这张电子表格就是VDT。

虚拟文档树是Postext的核心数据结构：一棵可原地修改的树，表示每个页面、栏、块和行，每个节点都带有精确的边界框。`buildDocument`返回之后，VDT*就是*答案。你可以查询“第72页第2栏里有什么？”，而不必渲染一个像素。

### 为什么是可变的

游戏引擎的渲染流水线也采用同样的做法：共享的可变世界状态在一个紧凑的循环里被各个系统依次更新。原因也相同。

放置遍原地填充这棵树。它打开一个页面，向页面追加栏，从块落入的那一栏的`availableHeight`中减去块的高度，并在通栏框切割栏带的地方封闭该栏带的各栏。一本书有几千个块，而不可变的树（比如React的虚拟DOM）会为其中每一步分配一个新对象。所以节点是普通对象，这一遍直接写入它们。

已经完成的一遍不会被修补。`buildDocument`需要再试一次时（一个栏带上限，一个齐底手段），它从内容出发重新运行这一遍，得到一棵新树。前一遍的树保持原样，驱动器因此可以比较两者，留下较好的那一棵，或者从两棵树中各取若干页。测量缓存让重新运行的开销可以承受：文本、字体和宽度都没有变化的段落从缓存中读出，不再重新测量。

### 类型定义

下面的结构是**为便于说明而简化的**：`packages/postext/src/vdt.ts`中的实际定义还有许多面向渲染的字段（字体字符串、颜色、列表符号、公式渲染结果、设计槽位）。这里重要的是结构本身：

```typescript
// 已简化，完整定义见packages/postext/src/vdt.ts

// 虚拟文档树的根
interface VDTDocument {
  pages: VDTPage[];
  blocks: VDTBlock[];         // 同一批块对象的扁平视图
  config: ResolvedConfig;     // 每个子配置都已解析为非可选值
  baselineGrid: number;       // 基线增量，单位px（例如16px/1.5对应24）
  converged: boolean;         // 每个齐底分段都已齐平结束，或已无手段可用
  iterationCount: number;     // 这份版面背后的放置遍数（见“放置遍的驱动器”）
  metadata: DocumentMetadata;
}

// 一个物理页面
interface VDTPage {
  index: number;
  width: number;
  height: number;
  columns: VDTColumn[];
  header?: VDTDesignSlot;     // 页眉（设计槽位）
  footer?: VDTDesignSlot;     // 页脚 / 页码
  floats?: VDTBlock[];        // 浮动到本页顶部/底部的资源区带
  pageNumberValue: number;
  pageLabel: string;          // 渲染出的标签（'iv'、'7'、'A'……）
}

// 页面中的一栏
interface VDTColumn {
  index: number;
  bbox: BoundingBox;          // 在页面中的位置
  blocks: VDTBlock[];
  availableHeight: number;    // 剩余的竖直空间
  baselineOffset: number;     // 当前基线的y位置
  band?: number;              // 栏所在区带（除非有通栏块把页面分割开，否则为0）
  kind?: 'text' | 'span' | 'side'; // 'span' = 容纳通栏块的全宽栏，
                              // 'side' = 一栏半版式中只放浮动体的侧栏
}

// 一个内容块（段落、标题、资源等）
type VDTBlockType =
  | 'paragraph' | 'heading' | 'resource' | 'blockquote'
  | 'listItem' | 'footnoteRef' | 'mathDisplay' | 'callout' | 'code';

interface VDTBlock {
  id: string;
  type: VDTBlockType;
  bbox: BoundingBox;
  lines: VDTLine[];           // 用于文本块：经过测量的行
  resourceBlock?: ResolvedResourceBlock; // 用于资源块
  pageIndex: number;
  columnIndex: number;
  dirty: boolean;             // 未使用：块放置时清除，没有任何地方读取
  snappedToGrid: boolean;     // 文本流在这个块之下回到了基线网格
  balancing?: VDTBalancing;   // 作用于这个块的各栏齐底手段
}

// 一行经过测量的文本
interface VDTLine {
  text: string;
  bbox: BoundingBox;            // 自然宽度：两端对齐的行会一直画到所在块的右边缘
  baseline: number;             // 文本基线的y位置
  hyphenated: boolean;          // 行在词中结束，或在不带空格的破折号之后结束（"say—" | "that’s"）
  hardHyphen?: boolean;         // ……在文本自带的连字符之后结束（"well-" | "known"）：不添加任何字符
  repeatedHyphen?: boolean;     // 以重复的那个连字符开头（"vencer-" | "-se"），源文本中没有它
  segments?: VDTLineSegment[];  // 供两端对齐渲染使用的词/空格/公式片段
  isLastLine?: boolean;         // 所在段落的最后一行
  justifiedSpaceRatio?: number; // 每个空格绘制的宽度 ÷ 正体的空格宽度
  justifiedSpaceLimitRatio?: number; // 上下限所约束的间距，行内空格不全是正体时才有（lineWordSpacing两个都读）
  sourceStart?: number;         // 到markdown源文件的映射（字符偏移；以`\$`开头的行从反斜杠算起）
  sourceEnd?: number;
  plainStart?: number;          // 到纯文本的映射
  plainEnd?: number;
}

// 经过测量、可以安放的资源嵌入（位图 / svg / 表格 / 视频）
interface ResolvedResourceBlock {
  resource: Resource;
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  number: string;             // 计算出的编号，例如"1.7"
  captionPrefix: string;      // 例如"Figure"
  bodyRect: BoundingBox;      // 图片 / 表格区域
  bodySource?: ResourceSafeArea; // 按安全区裁切时，图片在bodyRect中显示的部分
  bodyFlex?: { shrink: number; grow: number; delta: number }; // 主体还能缩短 / 增高的px，已改变的px
  fileId?: string;            // 带外的二进制数据（位图 / svg）
  captionLines: VDTLine[];    // 经过测量的题注，含前缀和编号
  table?: VDTResourceTableLayout; // 表格资源的单元格几何信息
}

// 边界框：所有值的单位为px，相对于页面原点
interface BoundingBox {
  x: number;
  y: number;
  width: number;
  height: number;
}
```

其中几个字段值得说明：

- <strong>`isLastLine`</strong>控制两端对齐的渲染：即使段落两端对齐，最后一行也按齐左渲染。*过满*的最后一行除外，它的词间距会压缩以适应行长（TeX的粘连设置语义）。
- <strong>`sourceStart`/`sourceEnd`和`plainStart`/`plainEnd`</strong>是源映射，把每一行分别映射回原始markdown和块的纯文本，编辑器集成靠它们实现光标和选区的同步。
- **`VDTResourceTableLayout`**（及其`VDTResourceTableCell`条目）承载表格资源排好后的全部几何信息：各列的x边界、各行的y边界，以及每个单元格的矩形和其中经过测量的内容行，这样每个后端画出的表格都相同。
- <strong>`dirty`和`snappedToGrid`</strong>在块被放置时写入，没有任何阶段和后端读取它们。新建的块上`dirty`初始为`true`，块放置时设为`false`；引擎不在树上跟踪变化，而是重新运行放置遍（见[放置遍的驱动器](#放置遍的驱动器)）。如果文本流在某个文本块之后回到网格，该块的第一部分上`snappedToGrid`为`true`（见[垂直韵律系统](#垂直韵律系统)）。
- <strong>`balancing`</strong>说明是哪些各栏齐底手段移动或拉伸了这个块；齐底没有处理的块不带这个字段（见[各栏齐底](#各栏齐底)）。
- <strong>`computePageTextExtent(page)`</strong>是一个小的公共辅助函数，返回页面上文本实际覆盖的竖直范围（包括浮动体的题注）。调试叠加层用它让基线网格线只覆盖真正有文本的部分，而不延伸到空白的页面底部。


## 排版流水线

一个放置遍，版面需要几次就运行几次。这就是排版流水线的全部。

这一遍（`placeDocumentPass`，位于`packages/postext/src/pipeline/build.ts`）从第一个块到最后一个块遍历内容。对每个块，它做完排定这个块所需的一切：按块即将进入的那一栏的宽度测量它，看它是否放得下，按分页规则和保持同页规则拆分它或把它后移，给它引用的浮动体提供位置，再让文本流回到基线网格上（见[垂直韵律系统](#垂直韵律系统)）。浮动体、孤行和网格都没有各自单独的一遍：它们在每个块落定时就已解决。

有些决定无法在一次遍历之内做出，因为它们取决于遍历最终的结果：目录印出的页码，通栏框切割上方各栏的高度，一个短栏还缺的行数。对于这些决定，`buildDocument`带着从前一遍结果中取得的*提示*重新运行这一遍。下面的五个阶段跟随一个块走完这一遍；[放置遍的驱动器](#放置遍的驱动器)和[各栏齐底](#各栏齐底)讲述重新运行。

### 第1阶段：内容结构化

- **输入**：原始的`PostextContent`
- **处理**：把Markdown解析成内容块，按ID在`resources[]`中解析资源引用，把脚注定义（`[^id]:`）移出文本流并按引用顺序给标记编号，给标题编号，并规划浮动体：哪些资源浮动，排在哪个块之后（不读取`notes[]`）
- **输出**：内容块的扁平列表（已确定类型并填入内容，但尚未分配页和栏）和浮动体规划
- **运行时机**：每个放置遍开始时。第一遍之后，解析结果从记忆化缓存中读出；其余部分重新计算

### 第2阶段：文本测量

- **输入**：一个含文本的内容块，以及它即将进入的那一栏的宽度
- **处理**：通过专门的**测量模块**（`packages/postext/src/measure/`）按这个宽度测量块的各行。该模块在Pretext之上叠加了断词、两端对齐、富文本行内片段和Knuth-Plass断行。结果是块的`VDTLine[]`和总高度
- **关键细节**：测量结果有缓存。`cachedMeasureBlock` / `cachedMeasureRichBlock`（位于`measure/cache.ts`）以文本、字体、宽度和所有影响版面的选项为键，重新测量一个未改动的段落只是一次映射查找
- **输出**：块的各行，带有精确的像素尺寸
- **运行时机**：在遍历到达这个块时，而不是提前进行，因为宽度取决于块落在哪里：侧栏旁边的栏，绕排图旁边的那些行，`:::columns`组的子栏。块转到另一种宽度的栏时，按那个宽度重新测量

该模块按职责清晰拆分：`plain.ts`测量纯文本片段，`rich.ts`测量粗体、斜体、数学公式混排的片段，`font.ts`构造字体字符串并管理缓存的生命周期，`canvas.ts`封装底层的Canvas文本宽度原语。有一个生命周期细节在实践中很重要：按后备字体测得的字形宽度，不能在真实字体到达之后继续留用。`canvas.ts`按字体字符串保存宽度，并记录一个测量代次；`evictFontFamilies`（构建发现某个字体族的字体有变化时调用，`watchFonts`、`prepareFonts`和`loadBundleFonts`也会调用）丢弃这些字体族的宽度并清空Pretext的缓存，在较早代次下填充的`MeasurementCache`则在下一次查找时丢弃用这些字体族排出的块。`clearMeasurementCache()`对所有字体族做同样的事。字体本身由`fonts/prepare.ts`（`prepareFonts`）在排版前加载，`fonts/faces.ts`读出已排好的文档用到了哪些字体，用于`fontFallback`警告。

中文、日文和韩文段落在同一模块中走另一条路径。CJK字符数多于词间空格数的段落交给**CJK排版器**（`cjkCompose.ts`）处理。它把文本切分成单元（一个字符、一串拉丁文、一个两字宽的破折号或省略号、行内标签或注释标记这样不可分割的盒子），每个单元只测量一次，然后按`cjkClasses.ts`的避头尾规则以首次适配的方式填充各行：遇到不能出现在下一行行首的标点时，本行先通过标点挤压（`cjkPunctuation.ts`）让出标点的空白把它容纳进来，然后才考虑把一个字符移到下一行。两端对齐的行再把余量分配到字符之间。输出是普通的`VDTLine`，其片段携带渲染器按测量结果精确绘制所需的一切：`tracking`（每个字符后的像素数，已计入片段宽度）、让出空白的标点的`inkOffset`、`hangs`、作为`autospace`片段的汉字与拉丁文之间的间距，以及中文注释的着重号、注音和割注行。在日文文档中，同一个排版器遵循JLReq：断行时从每个单元两端的字符读出日文级别的禁则类别，标点空白按JLReq的顺序挤压和让出，振假名由`rubyJis.ts`排布（1:2:1间距、伸到假名上、熟语），汉文训读记号则加宽其所属字符的单元。开销与段落长度成线性关系：排《紅樓夢》第1回（6,949个字符）时测量了1,298个字符，每个不同的字符只测一次；而如果测量段落的各个前缀，则需要测量636,948个字符。详见[中文排版](/zh/docs/chinese-layout)。

在底层，这正是Pretext发挥作用的地方。`prepare()`调用开销大：它用Canvas字体引擎分析文本并缓存结果。而`layout()`调用只是纯算术，几乎没有开销。这种拆分是关键所在。文本一旦准备好，引擎再次给它断行的开销就可以忽略不计：换一个宽度，用于在更窄的栏中接续的段落；或者多排一行，用于被各栏齐底放松的段落。准备一次，需要排多少次就排多少次。

```typescript
// 简化示例：测量模块在内部如何使用pretext
const prepared = prepare(paragraphText, '16px/1.5 Inter');
const { height } = layout(prepared, columnWidth, 24); // 行距24px
// => “在320px栏宽下，这个段落高168px，即7行。”
```

### 第3阶段：页面与栏的放置

- **输入**：一个已测量的块
- **处理**：把块排入当前栏。随文本流的需要创建`VDTPage`和`VDTColumn`节点。记录每栏的`availableHeight`。某个块放不下时，拆分它（第5阶段），或者转到下一栏或下一页
- **策略**：贪心的首次适配放置。分栏和分页采用最简单的有效分配
- **输出**：这个块分配了`pageIndex`、`columnIndex`和`bbox`

到这一步，VDT才成为一份真正的文档。在这个阶段之前，块只是扁平列表中的一项，没有位置。放置把每个块分配到某一页的某一栏，就像往一排格子容器里倒水：先注满第1栏，溢出后流入第2栏，一页满了就开新页。

在往页面上放入任何内容块之前，这一遍先为结构性元素预留空间：书眉和页脚（按`config.header` / `config.footer`作为设计槽排出），以及已经等待放到新开页面上的浮动带。这些预留会减少每栏的`availableHeight`，因此内容块开始排入时，引擎已经确切知道还有多少空间。

**栏带与通栏栏。**`page.columns`是一个按阅读顺序排列的扁平数组，但一页并不总是只有一排栏。在多栏版面中，通栏的行内块会把页面切成上下堆叠的*栏带*。有四种东西算作这样的块：样式或围栏设置了`span: 'page'`的`:::callout`，正文中的`:::columns{span="page"}`组，放置规则解析为`{ position: 'here', span: 'page' }`的行内`::resource`，以及在书写处横跨页面排出的漫画条（`:::strip{span=page}`）。后三种在放置之前先被包进一个无边框的通栏框（`pipeline/flowColumns.ts`、`pipeline/spanEmbeds.ts`），所以四种都由同一个机制排出。在切割处，当前栏带的文本栏在切割线处封闭（高度被截断，`availableHeight`为零），该块获得自己的一个全宽栏，`kind: 'span'`，并在它下方追加一个新的文本栏带（`band + 1`，x和宽度相同，底边与被替代的栏带相同）。栏只会被追加，因此`columnIndex`始终对应`page.columns[i]`，渲染器也无需特殊绘制：每栏按自己的bbox裁剪（由`columnClipRect`放宽：字形墨迹留2pt，再加上该栏的设计覆盖层（如标题标签或标注框徽标）超出其两侧的距离，以及标题设计超出其顶部的距离；底边仍是栏的边缘；Canvas和PDF后端使用同一个矩形）。栏间分隔线按栏带在相邻文本栏之间绘制，从页首通栏标题所占栏带的下方开始（`columnRuleSegments`）；带样式的章节设置了分隔线时，使用该页自己的分隔线（`VDTPage.columnRule`，通过`pageColumnRule`读取）。各栏齐底会忽略通栏栏、侧栏和高度为零的栏带。通栏块在栏带齐平的位置（页首、紧接章首标题之后、另一个通栏块之后或顶部浮动带之后）直接切割；如果到达时栏带各栏不齐，它就提出一个*栏带上限*（`packages/postext/src/pipeline/bandCaps.ts`）：以某个内容块开头的栏带，其各栏被缩短到`ceil(Σ used / N / grid)`行。`buildDocument`带着这个上限重新运行放置遍（受限栏带溢出时每次增加一行，最多`MAX_BAND_CAP_RETRIES` = 3次，之后放弃这个上限，该块于是退回到下一页的顶部），于是文本在遵守所有放置规则的前提下填满缩短后的各栏，在切割处齐平结束，封闭的栏把剩余的空白保留为`availableHeight`，交给各栏齐底去吸收。同一机制也用于让章节末尾和文档末尾的*收尾*栏带齐平（`headings.balancing.trailing`）：遇到章首页、`:::part`、结束一章的`placement: 'fixed'`标注框或文档末尾时，如果当前栏带各栏不齐，就提出一个`kind: 'trailing'`上限，以该边界块为键。由于上限以开启其栏带的块为键，而只要前面某页吸收了额外的齐底行，这个块就会移动，因此收尾上限要在各栏齐底稳定*之后*、在冻结齐底提示的情况下求解，然后再进行一轮简短的润色，让各种调节手段补足切割留下的空缺。`placement: 'fixed'`的标注框脱离文本流：框锚定在页面内容区、成品框或出血框上，它覆盖的文本栏让出该区域（像浮动带一样从底部或顶部切掉，冲突时移到下一页），框体及其子元素进入`page.floats`。

**竖排页面**。设置`layout.writingMode: 'vertical-rl'`时，这一遍排出的是一个顺时针旋转了90度的横排页面。在这样的页面上，内容区、栏、块、行、浮动体和脚注区都使用**流坐标**，`VDTPage.flow`携带把它们变换到纸面上的旋转：流坐标中的点(x, y)落在(页宽 − y, x)。下游无需知道这一点：断行、浮动体、保持同页规则和各栏齐底都在流坐标系中照常工作，流中的一栏就是纸面上的一层，各后端在绘制时应用旋转（`flowToPage`和`pageToFlow`在两个方向上映射点）。书眉、页码、裁切标记和背景保持纸面坐标。图和表作为直立的块排版，在框内转回原方向；需要直立的字符在绘制时逐个转回。

### 第4阶段：资源放置

- **输入**：第1阶段的浮动体规划，以及到目前为止已放置的各页
- **处理**：把每个被引用的资源浮动到其首次引用之后的第一个空闲位置：引用所在栏的底部、下一个空栏的顶部或底部，或下一页的某个浮动带（`packages/postext/src/pipeline/floatPlacement.ts`规划浮动体，`pipeline/floatSlots.ts`枚举并测量各位置；放置遍在遍历过程中预留浮动带）
- **运行时机**：包含首次引用的块一落定就运行，在同一次遍历之内；此后放置的文本绕开浮动带排布
- **放置规则解析**：对每个资源，引擎依次解析`resource.placement` → 该类型的`resourceType.defaultPlacement` → 内置默认值`{ position: 'auto', span: 'column' }`

除了这两个字段，`ResourcePlacement`还有`rotate`、`width`、`align`、`columns`、`captionSide`、`shrink`、`minScale`、`captionMeasure`、`wrap`、`wrapGap`和`citingPage`。各字段的作用见[配置 → 资源类型](/zh/docs/configuration-resources#资源类型)和[文档格式 › 位置](/zh/docs/document-format#位置)。

- **延后放置**：在当前页找不到任何合适位置的浮动体会等到文本流打开的下一页。在章节边界处，它会被排到边界之前新开的页面上。图片保持原尺寸，除非`placement.shrink`（或作用于整个文档的`layout.floatShrink`）允许把它缩小到某个位置实有的空间。新页面也放不下的表格按行切开，在后续页面上接续，并重复表头行（`tableStyle.overflow: 'split'`，默认值）
- **输出**：资源定位在页面浮动带中（`page.floats`），受影响的栏高度相应减少，使文本绕开浮动带排布

资源放置是有意思的地方，因为浮动体不只是占据空间，还会重塑周围的空间。包含引用的块落定后，等待中的浮动体会依次尝试当前页该块之后的空闲位置：先是该栏底部，再是下一个空栏的顶部和底部（通栏浮动体则是页底，前提是每栏都还有空间）；哪里都放不下的，就等到下一页，在那里等待中的浮动体先占据各自的浮动带，然后才排入文本。各栏缩短以容纳在浮动带之间，文本不间断地流过变窄的栏，读者在提到图的位置附近（但不一定恰好在那里）看到它。这是专业排版的标准做法，图书中随处可见。

**放置规则**。除了放置分派之外，浮动体还遵循严格的编辑约束：

- **引用在先规则**。浮动体落在正文中首次引用它之后的第一个空闲位置，绝不会在引用之前。读者先读到引用，再看到资源。浮动体放不下时，向后延到更晚的位置或页面，绝不往前挪。
- **同一序列内保持引用顺序**。等待中的浮动体按首次引用的顺序依次尝试每个位置；某个浮动体哪里都放不下时，同一编号序列中排在它后面的浮动体也要等待：表3绝不会排在表4之后，图12绝不会排在图11之前。不同序列之间互不阻挡，一个等待中的表不会挡住后面的图。为了让长表不必等到新开一页，一个被分配到空栏顶部的长表会在该栏处截断，在下一个位置（旁边的栏或下一页的浮动带）接续，并重复表头行。
- **章节屏障**。浮动体绝不会越出自己所在的章。在章首页（设置了`breakBefore`或`span: 'page'`的标题级别）、`:::part`、带`floatBarrier: true`的标注框样式以及文档末尾，所有等待中的浮动体都会先被放下：先放在本页的空闲位置，再放到边界之前新开的页面上（每页至少强制放置一个浮动体），然后才执行边界本身的分页。在打开这样的页面之前，仍在等待的图或表会再尝试一次当前页的空闲位置，不论其`position`如何：在一章最后一页被引用的页首浮动体会占据该页底部、位于已齐底的各栏下方，而不是单独占一页（浮动的标注框保持自己的放置方式）。`:::pagebreak`会把等待中的浮动体送到它之后的那一页，排在为奇偶页补齐而插入的页面之后。
- **最少文本空间**。在新开的页面上，只有受影响的栏中仍能容纳至少3行正文时，才会预留浮动带。有一个例外：超大的浮动体可以被强制放进一个仍然全是文本的浮动带，以免一个占主导地位的图永远卡住队列。当前页上的位置必须能放进该栏的剩余高度；3行规则在那里只适用于紧邻另一个浮动带的情况。
- **留白**。浮动带与旁边的文本之间隔开一个正文行高。
- **基线网格对齐**。顶部浮动带*向上*取整到基线网格的整数倍（增大浮动体下方的间隙），使每一行被推开的文本仍然落在网格上。底部浮动体的锚定方式是让题注的最后一条基线落在网格上：题注与相邻各栏最后一行文本共用基线，各栏和对页的页面在同一高度结束。

<strong>按类型、按首次引用编号。</strong>资源*不*在Markdown中编号。`pipeline/resourceNumbering.ts`按阅读顺序，在每个资源首次被引用时为它分配编号，依据是资源的`ResourceType`：`numberingTemplate`把按类型计数的`{n}`与引用处生效的标题计数器`{h1}`..`{h6}`组合起来（例如`'{h1}.{n}'` → “1.7”），`resetOn`控制计数器何时重置（`'never'`或任意标题级别），`counterFormat`选择十进制、罗马数字或字母编号。内置的*图*和*表*类型来自`defaultResourceTypes(locale)`，按文档语言本地化。由于编号遵循首次引用的顺序，在文档中间插入一张新图时，其后的所有编号会自动更新，无需修改源文件。

### 第5阶段：分页与保持同页规则

排版引擎与只会堆砌文字的工具，区别就在这个阶段。它执行专业排版师几百年来手工遵循的编辑质量规则，而简单的文本渲染对这些规则完全不管。

这项工作由三种机制分担，各自在所需信息存在的地方起作用：断行器内部的**孤字惩罚值**，段落遇到栏末时的**计分拆分**，以及块之间的**结构性保持同页规则**。

#### 段首孤行、段末孤行和孤字

**段末孤行和段首孤行**是业余排版最明显的标志：

- **段首孤行**（widow）是段落在栏底单独留下的一行。段落在下一栏继续，但这孤零零的一行
  看起来被搁浅了（好像这一栏提前结束了）。
- **段末孤行**（orphan）是段落搁浅在栏顶的单独一行。段落的主体在上一栏，只有一行溢了过来
  （看起来与上下文脱节）。
- **孤字**是指段落最后一行只有一两个短词，从视觉上看太短，不像一行正常的文字。它在结构上不如段首孤行严重，但对细心的读者同样刺眼。

**孤字在断行器中解决**。孤字只与段落本身有关：无论段落落在哪里，它的最后一行都一样短。所以三条规则中只有这一条是Knuth-Plass断行器看得到的。如果一组断点会让段落的最后一行内容宽度小于`runtMinCharacters × normalSpaceWidth`（`runtMinCharacters`默认20：二十个词间空格宽的内容，大约8到12个字母），断行器就在平方缺陷值公式中把`runtPenalty`（默认1000）加到这一行的劣度上。这样它与行劣度（在10000处饱和）在同一尺度上竞争，而不会被后者淹没。这个惩罚值与通常的缺陷值（劣度、断词代价、适配等级不匹配）一起参与同一个全局优化，断行器几乎总能找到一组没有孤字的断点。找不到时，只要词间空格加上少量负字距能吸收这一差额，`bodyText.tightenRunts`就把段落少排一行。测量模块把惩罚值交给断行器（`measure/plain.ts`、`measure/rich.ts`），由`knuthPlass/breakpoints.ts`应用。

**段首孤行和段末孤行在栏末解决**。断行器按某个宽度给段落断行。它不知道段落会落在页面的什么位置，所以无从知道哪一行会结束一栏。放置遍知道。段落的各行无法全部放进这一栏剩下的空间时，`chooseParagraphSplit`（位于`pipeline/orphanWidow.ts`）对已经断好的各行尝试每一种拆分`k`，从0到放得下的行数：`k`行留下，其余的行开启下一栏。每个候选拆分这样计分：

- `slackWeight · slack²`，对应它在栏底留空的行，其中`slack`是放得下的行数减去`k`（`slackWeight`默认10）；
- 在栏底留下的行少于`widowMinLines`时，加上`widowPenalty`（默认1000）；
- 带到下一栏顶部的行少于`orphanMinLines`时，加上`orphanPenalty`（默认1000）。

得分最低的拆分胜出，`k = 0`表示整段后移。这些规则是软约束，软到什么程度可以从数字看出：1000的惩罚值相当于十个空行的余量代价（10 · 10² = 1000），所以在默认值下，只要栏内留空的行少于十行，同时满足两条规则的拆分就会胜出。超过这个限度，段首孤行或段末孤行就可能是代价更低的选择。拆分只在断行器已经断好的行中选择，不重新给段落断行。列表项通过`avoidOrphansInLists`和`avoidWidowsInLists`走同样的拆分，并通过`avoidRuntsInLists`接受孤字惩罚值（默认都为`true`）。

所有这些都可以在`BodyTextConfig`中调整，参见[配置 → 段首孤行、段末孤行、孤字与保持同页规则](/zh/docs/configuration-text#段首孤行段末孤行孤字与不拆分规则)。把任何`*Penalty`设为`0`，实际上就关闭了对应的规则。

#### 结构性保持同页规则

有些组合比单个段落更大：它们跨越相邻的块，仅靠断行无法处理。放置遍在每个块落定时执行这些规则，当这些组合会被分栏或分页拆开时，把整组向后移：

- **标题与其第一段**。如果标题所引出的段落会从下一栏开始，标题就绝不能出现在栏底。由`headings.keepWithNext`（默认`true`）执行：如果放不下标题*加上*下一个块的正文段首孤行最小行数（`bodyText.widowMinLines`，默认`2`；`avoidWidows`关闭时只算一行），标题就被推到后面，与其正文一起移动。
- **连续的标题**。多个标题相继出现时（例如h2之后是h3，再之后是段落），整组必须保持在一起。任何一个标题都不能被留在栏底而脱离它所引出的内容。
- **以冒号引出的列表**。段落以直接引出列表的冒号结尾时，带冒号的那一行必须与列表的开头保持在一起。由`bodyText.keepColonWithList`（默认`true`）执行：如果放下这个段落后没有空间让第一个列表项开始（当列表的段首孤行和段末孤行规则使它不可拆分时，需要容纳整个列表项；设置`bodyText.colonListRoom: 'line'`时只需一行，与postext 1.4及以前的行为相同），带冒号的最后一行（如果段落只有一行，则是整个段落）就与列表一起后移。每当这条规则需要推动整个段落，而该栏中紧挨在它前面有一串标题时，这些标题也会被一起拉走，以免悄悄违反`keepWithNext`；唯一的例外是，该栏中只有先前一次移动已经带到后面的标题，此时引擎让段落与标题待在一起，接受冒号与列表分离这一较轻的问题，以避免循环。
- **图与其题注**。图和题注是不可分割的整体，总是一起移动。

检测到违反保持同页规则时，引擎把整组推到下一栏或下一页。它离开的那一栏于是提前结束，短了这一组本该占用的行数。把它填满是[各栏齐底](#各栏齐底)的工作。

这些修正做得好时是看不见的，读者不应察觉到它们。但只要细心阅读，一旦*缺少*这些修正就会立刻发现：栏顶那一行别扭的孤行，引擎放弃让文本排得下时留下的那些不均匀的空隙。专业出版社有整本的体例手册专门防止这些问题。Postext把它们自动化了。

第3至8轮在一次构建之内依次运行（`buildDocumentBalanced`）。第1、2轮在它之外：一轮目录或一轮注释编号是一次完整的构建，带有它自己的第3至8轮。整个构建没有总的上限，只有上述这些。

**每次重新运行都是一次完整的放置**。提示不会去修补前一遍的树。这一遍在提示生效的情况下把文档重新放置一次，所以，上方多了两行的标题，或者在高出六行处切割的栏带，都和其他内容一样经过同样的分页规则和保持同页规则。随后驱动器检查结果：框没有落在切割处的栏带上限会被加大或放弃，没有改善某个分段的齐底遍对该分段作废。驱动器返回的版面由某一遍放置出的页面组成：要么是某一遍的全部页面，要么在各栏齐底之后，每个分段的页面取自该分段最好的那一遍。

**文档报告什么**。`doc.iterationCount`统计返回的版面背后的放置遍数：第一遍，加上栏带上限、各栏齐底和收尾栏带各轮的那些遍。侧栏题注和引用页的各遍不计入，目录轮或注释编号轮中较早的构建也不计入；`BuildDocumentOptions.onPass`在每一遍都会被调用，并带有该遍的实际耗时。`doc.converged`只与各栏齐底有关。每个分段结束时，可齐底的栏中没有空行，或者已经没有手段可以提议，它就为`true`；有分段停在没有改善它的一遍上，或者用完了尝试次数，而空隙仍然存在，它就为`false`。齐底关闭时它为`true`。`converged: false`的文档是完整的：它保存着驱动器找到的最好版面，只是其中某一栏提前结束。

### 各栏齐底

- **运行时机**：作为驱动器的第6轮和第8轮（默认开启；`headings.balancing.enabled: false`可将其关闭，在竖排和字符网格上默认关闭，见[配置 → 各栏齐底](/zh/docs/configuration-text#各栏齐底)）
- **输入**：目前为止最好的版面，以及每个可齐底的栏底部的空网格行（`collectColumnGaps`，位于`pipeline/columnBalancing.ts`）
- **处理**：提议在原处填满每个短栏的手段，带着它们运行放置遍，分段的空隙分数下降时为该分段保留结果
- **输出**：结束于页面最后一个网格行的各栏，每个手段都记录在它所作用的块上（`VDTBlock.balancing`）

各栏不齐是一眼就能看出来的。分页规则随时都在留下短栏：为了与正文待在一起而后移的标题，为了避免段首孤行而整段后移的段落，一幅放不下的图。比旁边一栏早两行结束的栏看上去像没做完，仿佛排版进行到一半就放弃了。

修正它时没有任何块换栏。分栏的位置与那个放不下的元素绑定在一起：开启下一栏的块对当时剩下的空间来说太高，对更小的空间来说仍然太高。所以短栏可以从内部填满，填充量最多等于它的空隙，没有任何内容越入下一栏。这种调整是局部的，排字工手工做的也正是这件事：在眼睛能接受的地方加一行空。如果内容流过某一栏进入了同页后面的栏，这一栏就是可齐底的；对一页的最后一栏来说，条件是该页的文本流继续到下一页。一章的最后一页可以提前结束；它的收尾栏带改由收尾上限切齐（见[第3阶段](#第3阶段页面与栏的放置)）。

对每个空隙，手段按编辑上的优先顺序提议，与[配置 → 各栏齐底](/zh/docs/configuration-text#各栏齐底)列出的顺序相同：

1. **收尾的框**：结束一栏的框把其底部下方的空余当作它上方的空白，使它的下边缘落在页面最后一个网格行上，与相邻栏的最后一行平齐。记录为`trailingCallout`。
2. **有安全区的图片**：设了安全区（`Resource.safeArea`）的图片，如果以行内方式排在这一栏里，或者作为只占这一栏的浮动体排在栏顶或栏底，就按整数个网格行增高，在安全区以内裁切。图片变高不会在页面上留下空洞，所以这一手段在增加任何空白之前执行。记录为`flexFigure`。
3. **标题**：在标题上方增加整数个网格行，各标题轮流每次加一行，最重要的标题（级别数最小的）排在最前，因此分得最多。位于栏顶的标题从不加空，因此各栏始终从页面顶部开始。一个标题这样只先加最初几行，然后轮到后面的手段；只有它们再也补不了时，标题才继续加行，直到它的上限。记录为`heading`。
4. **列表结尾**：在列表结束处增加一个网格行。记录为`listEnd`。
5. **公式、框和图的下方**：在它们下方增加一个网格行：独立公式或标注框之下、文字接续之处（`afterDisplay`），以及栏首的图或表与其下文字之间（`afterFloat`）。
6. **放松段落**：最后手段。栏内的段落从最长的开始，各自重新断行、多排一行（即TeX的`\looseness=+1`，通过Knuth-Plass断行器的`looseness`选项），只有每一行都保持在`bodyText.maxWordSpacing`以内时，放松后的方案才会被采用。单靠词间距无法多出这一行时，段落还可以采用恰好能多出这一行的最小正字距，字距有上限。记录为`looseParagraph`。

各项上限、开关和例外情况（字符网格、收尾各页、跨多栏的浮动体）都是`headings.balancing`的键。配置页列出了它们，并随它们保持更新；本页不再重复。

提议要靠放置来检验。应用这些手段的那一遍是一次完整的放置，偶尔某个手段终究还是让内容越过了分栏处：头部再也放不下的拆分段落，失去了位置的浮动体。那一点之后的页面排法变了，别处就出现空隙。驱动器从分数上看出这一点，对该分段作废这一遍，并把第一个发生变化的栏中新应用的手段列入黑名单，于是下一次提议保留有效的手段，去掉引起连锁反应的那一个。

**各栏齐底按分段收敛**。显式断点（章首页、`:::pagebreak`）之间的页面彼此独立排版：没有内容会跨越这样的断点流动，因此一段页面中的齐底手段不可能移动另一段中的任何一行。所以各栏齐底循环对每个这样的*分段*单独评判。分段的空隙分数是其可齐底的栏底部空网格行的数目。每一遍仍然放置整份文档，但每个分段按自己的空隙分数决定保留或拒绝自己那部分手段，把自己的连锁反应列入黑名单，自己判断进入平台期，并消耗自己的尝试预算；某个分段重试后变差时，会从它自己最好的那一遍取回页面，其他分段则继续前进。这样，一本三十章的书排出来的结果与逐章单独排版完全相同（全书PDF与同一章的单章PDF完全一致），而不会因为任何地方的一次连锁反应就让全书每一页多跑一遍。

这些上限是安全阀。有些栏无法填满：只有短段落的栏没有可用的手段；每个手段都会把某个块推过分栏处的栏，也没有一个手段留得住。引擎保留它找到的最好版面，让那一栏短着。由于手段记录在块上，校样或测试可以列出没有任何手段能补齐的栏（见[配置 → 哪个手段起了作用](/zh/docs/configuration-text#哪个手段起了作用)）。


## 垂直韵律系统

把一本排得好的书对着光举起来。左页的行与右页的行对齐。第1栏第5行的基线与第2栏第5行的基线处在完全相同的垂直位置。这就是垂直韵律，也是训练有素的眼睛评判排版质量时最先检查的事项之一。它也是Postext的关键特色之一。

当两栏都只有同一字号的正文时，对齐轻而易举：每行高度相同，基线自然对齐。难题出现在某一栏包含更大字号的标题、任意像素高度的图像，或块引用周围的额外间距时。这些元素“破坏”了网格：它们下方的内容偏移了一个不是基线增量整数倍的距离，这一栏的基线突然就与相邻栏错开了。视觉上的和谐消失了。

目标是把它找回来：即使标题、图像或其他非标准高度的元素只出现在一栏中，相邻栏的正文基线也必须水平对齐。

### 基线网格

一切都以一个数值为基准。文档定义一个`baselineGrid`值，由正文的行距推导而来：例如，正文字号为`16px`、`line-height`为`1.5`时，基线网格为`24px`。每条正文基线都应落在这个值的整数倍上。这就是约定。

### 破坏网格的元素

有些元素的高度不是`baselineGrid`的整数倍，因而不可避免地会破坏网格：

- **标题**（字号更大，行距不同）
- **图像**（任意像素高度）
- **表格**（高度可变）
- **块引用**（可能使用不同的字号或内边距）
- **脚注区**（栏底的脚注及其分隔线：该栏的文本区在它们上方结束）

### 文本流如何回到网格

<Illustration name="VerticalRhythm" data='{"title": "垂直韵律对齐", "desc": "第1栏有一个标题，使基线网格偏移了12像素。放置这个标题时，引擎把该栏已用的高度向上取整到下一条网格线，这在标题下方增加了12像素，让下一行正文重新落在网格上。第2栏始终保持对齐。", "caption": "破坏网格的元素下方的空白在放置该元素时向上取整到网格，使各栏基线保持同步。", "column1": "第1栏", "column2": "第2栏", "bodyLine": "正文行", "bodyBaseline": "正文行（基线：24px）", "heading": "标题（高36px）", "adjustment": "+12px间距调整", "backOnGrid": "正文（回到网格上）", "aligned": "已对齐", "legendTitle": "放置时对齐网格", "legendSteps": ["1. 排入块：先是它的各行，再是它下方的间距（marginBottom）", "2. 把该栏已用的高度向上取整到下一条网格线", "3. 下一个块从那里开始，所以下方的间距是最小值", "4. snapToGrid: false保留精确的间距，直到下一个对齐网格的块"]}' />

网格是在放置时逐块保持的。之后没有哪一遍会遍历各栏去找偏移。正文行的高度是一个网格行，所以从网格上开始的一串正文会一直留在网格上。放置遍排入一个可能离开网格的块之后，会在下一个块开始之前，把该栏已用的高度向上取整到下一条网格线。以这种方式对齐网格的块有：

- 一串标题中的最后一个（连续的标题一个接一个，中间不对齐，由最后一个让其后的文本重新对齐）；
- 列表的最后一项，不论各项之间的间距如何；
- 独立公式；
- 标注框、代码清单，以及以行内方式嵌入的图或表；
- `:::paragraphs`容器的最后一段，以及`:::verse`诗歌，两者用的都是自己的行距。

块下方的间距（`marginBottom`）在取整之前计入，所以这个边距是最小值，其余由网格决定。图中，第1栏在24px的网格上有一个高36px的标题，下方没有边距。它的底边越过网格线12px，对齐时补上12px，下一行正文就从网格上开始，与第2栏中旁边的那一行平齐。如果`marginBottom`为16px，底边会在52px处，对齐时会把它向上取整到72px。

浮动带以自己的方式保持网格，见[第4阶段](#第4阶段资源放置)：顶部浮动带向上取整到整数个网格行，底部浮动体的锚定方式是让题注的最后一条基线落在网格上。各栏齐底按整数个网格行加空，所以也保持网格。

没有任何东西拿一栏去和另一栏比较。每一栏都从网格上开始，每次对齐都回到网格上，所以相邻各栏以及左右对页的行不需要第二遍就能对上。

**不参与对齐**。`snapToGrid: false`改为保留块下方的精确间距。它可以设在`headings`上（针对所有级别、某一级别或某个标题样式），也可以设在段落样式、标注框样式和`codeStyle`上。这样的块之后的文本可能不在网格上，直到下一个对齐网格的块为止。标注框内的文本遵循框自己的行距，没有网格。


## 后端接口

文本测量只有一个事实来源：基于Pretext Canvas字体度量的测量模块。每个后端都从它生成的同一个完成的VDT进行渲染。

这是一个有意的选择，原因很关键：**测量文本的方式必须与渲染文本的方式完全一致**。设想测量使用Canvas字体度量，而某个渲染后端使用的PDF库字距调整表略有不同，那么版面就会与输出对不上。引擎测得能放进320px的行，渲染时可能溢出或留空。每一像素的偏差都是一个谎言。只测量一次，所有输出都按由此得到的几何数据渲染，各后端就不可能出现分歧：断行、栏高和资源位置在任何后端运行之前就已固定在VDT中。

例如，PDF后端正是因此不重新测量文本：它接收完成的VDT，把其中的像素坐标换算成PDF点。Canvas度量是事实来源，PDF只是传输载体。使用`renderToPdf`（来自`postext-pdf`包）时，传入的VDT与交给`renderToCanvas`或`renderToHtml`的完全相同，三种输出保证一致。

### API接口

后端是作用于`VDTDocument`的普通函数，而不是类层次结构。没有`PostextBackend`接口，只有每种输出的渲染入口及其所需的辅助函数：

```typescript
// Canvas（来自'postext'）
renderToCanvas(doc, options?): HTMLCanvasElement[];     // 每页一个canvas
renderPage(page, doc, options?): HTMLCanvasElement;     // 单页
renderPageToCanvas(page, doc, canvas, options?): void;  // 绘制到已有的canvas中

// Canvas资源图像注册表：以Resource的fileId为键的已解码图像
registerResourceImage(fileId, image, options?): void;   // options: { vector?, singleInk? }
unregisterResourceImage(fileId): void;
clearResourceImages(): void;

// HTML（来自'postext'）
renderToHtml(doc, options?): string;
renderToHtmlIndexed(doc, options?): HtmlRenderIndex;    // 按页、按块的分解结果

// PDF（来自'postext-pdf'）
renderToPdf(doc, options): Promise<Uint8Array>;

// EPUB（来自'postext-epub'），按顺序传入一本书的各章
renderToEpub(docs, options): Promise<Uint8Array>;
```

由于资源的二进制数据在带外传递，每个后端以自己的方式解析`fileId`。Canvas后端维护一个已解码`CanvasImageSource`的注册表：宿主应用用`registerResourceImage(fileId, image)`把每个位图或SVG注册一次，渲染器在绘制时查找。HTML后端在选项中接收一个`resourceImageUrl(fileId)`解析函数，生成指向宿主返回的URL（object URL、data URI、CDN路径）的`<img>`标签。PDF后端接收一个`resourceBytes`提供函数，嵌入实际的字节；EPUB写入器也接收这样一个函数，每张图片只作为书中的一个文件存一次。视频资源绘制为它的封面，和其他位图一样；HTML后端还接收一个`resourceVideoUrl(fileId)`解析函数，用于它要播放的视频文件，EPUB写入器则把这些文件存放在`media/`下。PDF后端把播放标记和二维码以矢量路径画在封面上；`video.linkPoster`开启时，还在封面上方加一个打开`video.link`的URI链接注释。在带标签的PDF中，这个链接归入封面的`Figure`，其替代文字以类型名称开头（*视频：…*）。表格资源不需要这些：它们的模型是内联的，每个后端都按VDT中的表格几何数据绘制单元格。

`renderToHtmlIndexed`值得单独说明：除了完整的HTML字符串，它还返回按页、按块的分解结果（`HtmlRenderIndex`），调用方可以与上一次渲染做差异比较，只修补HTML确实发生变化的DOM子树。沙盒的实时预览走的就是这条路径。

四个已发布的后端都接收同一个`VDTDocument`。`postext`（导出Canvas和HTML后端）与`postext-pdf`（导出PDF后端）的拆分纯粹是出于依赖考虑：PDF路径会引入`pdf-lib`和`@pdf-lib/fontkit`，而大多数Web集成并不需要它们。只有在确实要输出PDF字节时才安装`postext-pdf`。`postext-epub`出于同样的原因单独成包，只在制作电子书时需要。命令行不是第五个后端：`postext-cli`在没有浏览器的地方运行同样这些写入器。

## 性能策略

迟钝的工具和神奇的工具之间大约差10倍。500ms的排版意味着用户每改动一个词都会看到明显的卡顿。50ms的排版则感觉是即时的，仿佛文档一直就在那里。这个差距没法事后补上，必须从第一天起就设计进去。

想想引擎要面对的是什么：几百页中的几千个文本块，每次编辑都要重新排一遍，版面需要各轮处理时还要排上好几遍。游戏引擎面对的是同一类问题：每秒60次处理几千个对象（几何、物理、光照、AI）。它们的解决办法是不重复已经做过的工作。Postext把这个办法用在自己开销最大的地方，也就是文本测量上。

### 原则

1. **内存中计算**。整个VDT都能放进内存。排版期间不读取DOM。DOM
   只在最后渲染时才会被触及。

2. **在缓存的测量结果上跑完整的一遍**。重新运行放置遍时不去找哪里变了：它从第一个块开始把文档重新放置一遍。这之所以负担得起，是因为开销大的测量部分按段落缓存（原则5）。如果某一遍没有改变一个段落的文本、字体或宽度，它就从缓存中读出该段落的各行。

3. **有界的轮**。每一类重新运行都有固定的上限（见[放置遍的驱动器](#放置遍的驱动器)），各栏齐底除了每个分段的上限之外还有每份文档的上限，所以章数很多的书不会无止境地消耗放置遍。一次构建的开销可以逐遍测量：`BuildDocumentOptions.onPass`报告每一遍及其实际耗时。

4. **Pretext的速度**。文本测量速度是DOM的300至600倍，因此引擎可以
   投机性地重新测量文本（尝试不同的栏宽、断词点、字距调整），
   而不会阻塞主线程。

5. **分层的测量缓存**。测量模块（`packages/postext/src/measure/`）在Pretext自己的
   `prepare()`缓存和底层文本宽度缓存之上，维护一个显式的测量缓存，以文本、字体、宽度
   和所有影响版面的选项为键。重新测量一个未改动的段落只需一次映射查找。
   某个字体族的字体变化时，引擎丢弃该字体族的宽度和Pretext的缓存，测量缓存则在下一次查找时丢弃用该字体族排出的块（它记着自己是在哪个代次下填充的），因此字体加载完成后字形宽度是正确的，宿主不必调用任何函数；`clearMeasurementCache()`丢弃所有字体族。

6. **热路径上的断行**。Knuth-Plass的活动节点处理为速度而重写：
   节点退出时就地压缩活动集合，候选节点按（行，适配等级）去重，
   每个键只保留缺陷值最低的节点。算法结果完全相同：
   断点组合不变，只是计算得更快。

7. **在主线程之外构建。**`postext/worker`入口在专用的Web Worker中
   运行整个流水线。主线程发送`{ content, config }`和一个
   `AbortSignal`；工作线程注册字体（以`ArrayBuffer`转移），运行
   放置遍，再发回完成的`VDTDocument`。新的`build()`调用会以协作方式
   取消上一次调用：工作线程运行`buildDocumentAsync`，它在每个块处和各遍之间查询取消钩子，
   并抛出`BuildCancelledError`，因此在编辑器中打字的用户
   从不需要等待一个已被取代的排版。工作线程还维护自己的持久
   测量缓存和一个以内容为键的数学公式光栅缓存，使经过结构化克隆的
   `MathRender`对象在多次重新构建之间保留下来，无需重新光栅化。

8. **双重访问的VDT**。树结构（`pages > columns > blocks`）为按页或按栏进行的工作提供层级访问（各栏齐底测量每一栏底部的空隙）。一个并行的扁平`blocks[]`数组可以直接访问每一个块，不论它位于何处（注释编号轮从中读出每条注释印出的标记）。两种视图引用相同的块对象（没有重复，只是遍历同一份数据的两种方式）。

### 重新排版

没有增量式的入口：没有哪个调用接收一个完成的VDT并更新它。内容或配置发生变化时（一次按键，换一种页面尺寸），宿主再次调用`buildDocument`，得到一份新文档。

从一次构建延续到下一次构建的是测量结果。用`createMeasurementCache()`创建一次`MeasurementCache`，把它作为第三个参数传给每一次`buildDocument`调用。文本、字体、宽度和断行选项都没有变化的段落从缓存中读出，所以每次按键都重新排版的编辑器只需测量正在输入的那个段落。页面尺寸或栏数的变化会改变宽度，这些段落就要重新测量；Pretext的`prepare()`结果仍然有效，因为它们取决于字体和文本，与宽度无关，所以只需运行低开销的`layout()`算术。解析结果也有记忆化。

对于实时编辑器，`createLayoutWorker`（来自`postext/worker`）在主线程之外完成这一切：工作线程拥有一个与它同寿命的测量缓存，新的`build()`会取消正在进行的那一次。见[配置 → 测量缓存](/zh/docs/configuration-programmatic-usage#测量缓存)和[在Web Worker中运行排版](/zh/docs/configuration-programmatic-usage#在web-worker中运行排版)。

### 基准测试

`packages/postext/src/__bench__/`中有两个基准测试。`pnpm test`跳过它们；在`packages/postext`中运行`pnpm bench`才会执行。`chapter.bench.test.ts`把一个教材篇幅的章（四十节，含标题、段落和列表）对着空的测量缓存排五次，再对着热缓存排五次，报告两个中位数和放置遍数。`cjkChapter.bench.test.ts`排《红楼梦》第1回，并统计送入`measureText`的字符数，以确保CJK排版器的开销与段落长度成线性关系。

```typescript
// 摘自packages/postext/src/__bench__/chapter.bench.test.ts
const cold: number[] = [];
for (let i = 0; i < ROUNDS; i++) cold.push(time(() => buildDocument({ markdown }, config, createMeasurementCache())));

const warmCache = createMeasurementCache();
buildDocument({ markdown }, config, warmCache);
const warm: number[] = [];
for (let i = 0; i < ROUNDS; i++) warm.push(time(() => buildDocument({ markdown }, config, warmCache)));

const passes: BuildPassInfo[] = [];
const doc = buildDocument({ markdown }, config, createMeasurementCache(), { onPass: (p) => passes.push(p) });
// [bench] chapter: … pages, … passes (… ms), iterationCount=…; cold median … ms, warm median … ms (5 rounds)
```

需要如实说明一点：Node中没有Canvas，所以两个基准测试都用桩代替文本测量，它们的绝对时间不是浏览器中的时间。冷缓存与热缓存的比值以及放置遍数则与浏览器中一致，其中任何一项退化，都会先在这里显现，然后才在沙盒中显现。章的基准测试只报告数字，不会让构建失败；中文的那个则断言测量的字符数低于最长段落长度的三倍。两者都不在CI中运行：性能退化是在热路径改动时通过对比多次运行的数字发现的（Knuth-Plass活动节点重写时就是这样做的）。性能是一项功能，而不是一种期望；不过目前的保障手段是测量和审查，而不是一条会失败的流水线。

## 不做的事

下面每一条限制都是有意的取舍。引擎本身已经足够复杂，再去承担本该由别处负责的工作，最容易让它永远做不完。

- **所见即所得编辑**。Postext是排版引擎，不是编辑器：输入内容，输出几何信息。构建交互式编辑界面（光标管理、选区、撤销/重做、输入处理）是另一个完全不同的问题。Postext可以作为编辑器的渲染后端，但它本身不提供编辑功能。
- **CSS column-count的封装**。Postext取代CSS多栏布局，而不是在它外面包一层。它从零开始计算精确定位的几何信息，因为浏览器的分栏算法无法控制资源的摆放、段首孤行和段末孤行的避免，以及跨栏的排版规则。而这些恰恰是Postext存在的意义。
- **响应式断点管理**。Postext按给定的页面尺寸计算版面。何时重新排版（视口尺寸变化、屏幕方向变化时）由调用方决定。Postext不管理断点、媒体查询，也不替你做响应式设计的决定。那是你的工作。
- **实时协同编辑**。Postext是无状态的排版计算（输入内容，输出几何信息），不是带冲突解决、操作变换或多用户感知的协同文档系统。
- **字体文件**。`postext`包负责加载字体，但不自带字体。`prepareFonts`在第一次构建之前加载配置及其文本要求的所有字体，字体集无法提供的字体会作为`fontFallback`列在文档的警告中。文件本身由宿主提供：页面上的一条`@font-face`规则，或者一个说明每个字体在哪里的`resolve`函数。见[配置 → 排版前加载字体](/zh/docs/configuration-programmatic-usage#排版前加载字体)。

### VDT类型在哪里

VDT类型（`VDTDocument`、`VDTPage`、`VDTColumn`、`VDTBlock`、`VDTLine`、`VDTLineSegment`、`ResolvedResourceBlock`、`VDTResourceTableLayout`、`BoundingBox`等）位于`packages/postext/src/vdt.ts`，与工厂辅助函数（`createVDTDocument`、`createVDTPage`、`createVDTBlock`……）和`computePageTextExtent`放在一起。没有单独的后端接口模块：[后端接口](#后端接口)一节所述的渲染入口直接从`postext`（Canvas、HTML）、`postext-pdf`（PDF）和`postext-epub`（EPUB）导出。
