# Arquitectura de Postext

Si has treballat amb React, ja coneixes el truc fonamental. React construeix un DOM virtual a la memòria, el compara amb l'anterior i només llavors toca el DOM real del navegador. Postext fa exactament el mateix, però en lloc de components d'interfície construeix un arbre de **pàgines, columnes, blocs de text i caixes delimitadores**. Tota la geometria d'un document de moltes pàgines i moltes columnes, calculada abans de renderitzar un sol píxel. Cada paràgraf, encapçalament, imatge, nota a peu de pàgina i cita destacada col·locats en coordenades exactes, respectant regles tipogràfiques centenàries que CSS senzillament no pot expressar.

Tot això és possible gràcies a [`@chenglou/pretext`](https://github.com/chenglou/pretext), una biblioteca de mesura de text sense DOM entre 300 i 600 vegades més ràpida que el reflow del navegador. Si vols conèixer la història que hi ha darrere del projecte (una dècada d'intents fallits, el coll d'ampolla que els frenava tots i la biblioteca que finalment el va eliminar), consulta la [Introducció](/ca/docs/introduction).

## La idea central

Pensa en un document de 74 pàgines a dues columnes. Un informe anual, potser, o un llibre de text densament il·lustrat. L'entregues a Postext i el motor construeix tota la composició a la memòria: cada pàgina, cada columna, la posició exacta i les dimensions en píxels de cada paràgraf. Vols saber què hi ha a la pàgina 72, columna 2? La resposta ja hi és. Sense renderitzar res. El motor ja ha decidit on partir cada paràgraf, on col·locar cada imatge, com evitar vídues i òrfenes, i com alinear les línies de base entre columnes adjacents.

I aquí ve l'important.

Les regles tipogràfiques són profundament i desesperadament interdependents. Corregeixes una vídua a la pàgina 5 — aquella línia solitària encallada al final d'una columna — fent-la tornar a la columna anterior. Perfecte. Però aquest canvi escurça la columna de la pàgina 5, cosa que desplaça contingut cap endavant, cosa que podria crear una òrfena a la pàgina 6. Una primera línia empesa a una columna nova, desconnectada del seu paràgraf. Per arribar a *detectar* que has creat un problema nou, necessites la composició completa del document disponible per inspeccionar-la. I per *corregir-lo* sense crear-ne un altre en un altre lloc, necessites poder ajustar, tornar a mesurar i tornar a verificar-ho tot.

Aquesta és la filosofia de "calcular-ho tot primer, renderitzar després". No és un truc de rendiment. És l'única manera d'aplicar les desenes de regles tipogràfiques interconnectades que els tipògrafs professionals fan servir des de fa segles.

**Aquest és el recorregut del teu contingut a través del motor:**

1. El **parser** llegeix el markdown enriquit i el converteix en una llista plana de blocs de contingut tipats: contingut i estructura, encara sense posicions
2. Una **passada de col·locació** recorre aquesta llista una vegada i construeix el VDT. Mesura cada bloc a través de Pretext a l'amplada de la columna on està a punt d'entrar, col·loca text, flotants i caixes en pàgines i columnes, i aplica les regles de tall i de cohesió sobre la marxa
3. El **controlador** (`buildDocument`) torna a executar la passada quan una decisió necessita el resultat d'una composició sencera: una taula de continguts que imprimeix números de pàgina, una caixa a amplada de pàgina que ha de tallar a nivell les columnes que té a sobre, una columna que ha acabat curta. Cada repetició rep indicacions de la passada anterior, i cada mena de repetició té el seu propi límit
4. El **VDT final** és la geometria completa de la composició: cada element coneix el seu número de pàgina, la columna assignada, la posició i la caixa delimitadora. El document està completament "compost" abans que es produeixi cap renderitzat
5. Un **backend** recorre el VDT acabat i el renderitza al format de destinació: un bitmap rasteritzat sobre canvas, un arbre DOM d'elements HTML posicionats, un document PDF amb fonts incrustades o un EPUB. El mateix VDT alimenta tots quatre; triar backend és purament una decisió de sortida


## Capa d'entrada

### Model de contingut

El model de contingut és tant una filosofia com una estructura de dades. Tu descrius *què* dir, no *com* compondre-ho. Les decisions de composició les pren el motor.

<Illustration name="ContentModel" data='{"title": "Model de contingut: markdown, recursos, notes", "desc": "L’entrada a Postext separa el markdown (ordre de lectura i estructura semàntica) dels recursos (bitmaps, SVG, taules) i les notes. El motor resol les referències en línia :ref i els incrustats ::resource per ID i produeix el VDT.", "caption": "El markdown aporta l’ordre de lectura; els recursos aporten les dades visuals.", "contentTitle": "PostextContent", "markdown": "markdown", "markdownSub": "ordre de lectura + :ref / ::resource per id", "resources": "resources[]", "resourcesSub": "bitmaps, SVG, taules", "notes": "metadata", "notesSub": "títol, autoria, dates", "resolveMarker": "resolt per id: :ref{id=…}, ::resource{id=…}", "engineLabel": "motor", "vdtLabel": "VDT"}' />

```typescript
// packages/postext/src/types.ts

interface PostextContent {
  markdown: string;            // markdown enriquit amb marcadors :ref / ::resource
  metadata?: DocumentMetadata; // títol, subtítol, autoria, data de publicació, …
  resources?: Resource[];      // bitmaps, SVG, taules, vídeos — referenciats per id
  notes?: PostextNote[];       // no es llegeix: les notes a peu de pàgina s'escriuen com a [^id] al markdown
}

interface Resource {
  id: string;                  // id estable, referenciat pels :ref en línia
  typeId: string;              // ResourceType al qual pertany ('figure', 'table', …)
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  caption?: string;            // el prefix del tipus + el número es calculen, no s'escriuen aquí
  altText?: string;
  createdAt: number;
  updatedAt: number;
  // Exactament un payload específic del kind:
  bitmap?: { fileId: string; format: string; width: number; height: number };
  svg?: { fileId: string; width?: number; height?: number };
  table?: { model: TableModel };
  video?: ResourceVideo;       // d'on es reprodueix; a la pàgina se'n dibuixa el pòster
  placement?: ResourcePlacement; // substitució opcional del flotament per recurs
  safeArea?: ResourceSafeArea;  // bitmap / svg: { x, y, width, height } en fraccions, la part que sempre es veu
}
```

Els **recursos** porten les dades visuals: peus, text alternatiu i un payload específic del seu `kind`. Els payloads binaris (bitmaps, SVG) viuen *fora de banda* — el recurs només desa un `fileId`, i el renderitzador el resol en el moment de dibuixar (el sandbox desa els bytes a IndexedDB). Les taules són l'excepció: el seu `TableModel` (una quadrícula de cel·les amb fusions i alineació) viatja en línia, perquè són dades estructurades, no bytes.
Les **notes** s'escriuen al markdown: una crida `[^id]` on se cita la nota i una definició `[^id]:`, un paràgraf propi en qualsevol lloc del capítol. El motor les numera en l'ordre en què se citen per primera vegada i compon cadascuna al peu de la columna que conté la línia que la cita, sota un filet curt, o després del darrer bloc del capítol amb `footnotes.placement: 'chapterEnd'` (vegeu [Notes a peu de pàgina](/ca/docs/document-format#notes-a-peu-de-pàgina) i [Configuració → Notes a peu de pàgina](/ca/docs/configuration-notes-references#notes-a-peu-de-pàgina)). El model de contingut continua acceptant un array `notes`, però cap etapa del pipeline no el llegeix.

Aquesta separació és una decisió de disseny deliberada, i té més importància del que sembla. El markdown és l'amo de l'*ordre de lectura* i de l'*estructura semàntica* — què va primer, què és un encapçalament, on se cita una nota a peu de pàgina i què diu. L'array de recursos és l'amo de les *dades visuals* — dimensions d'imatge, text dels peus de foto, cel·les de taula. Mantenint-los separats, el mateix markdown es pot compondre de maneres completament diferents només canviant la configuració. Una maquetació acadèmica a dues columnes i un article de blog a una sola columna poden compartir el mateix contingut font. I el motor pot prendre decisions de col·locació — com ara ajornar una imatge a la columna següent perquè aquí no hi cap — sense tocar mai el teu contingut original.

```typescript
// Exemple: un article senzill amb una figura referenciada
const content: PostextContent = {
  markdown: `
# L'art de la tipografia

La història de la tipografia comença amb els tipus
mòbils de Gutenberg, mostrats a :ref{id="imprenta"}.
La seva invenció va transformar la producció de llibres.

La tècnica es va estendre ràpidament per Europa, i va arribar
a Itàlia el 1465 i a França el 1470.
  `,
  resources: [
    {
      id: 'imprenta',
      typeId: 'figure',
      kind: 'bitmap',
      caption: 'Una reconstrucció de la impremta original.',
      altText: 'Reconstrucció de la impremta de Gutenberg',
      createdAt: 1765379100000,
      updatedAt: 1765379100000,
      bitmap: { fileId: 'foto-imprenta', format: 'jpeg', width: 600, height: 400 },
    },
  ],
};
```

Els recursos es connecten a la prosa per id, i **n'hi ha prou de referenciar-ne un per incorporar-lo**. El `:ref{id="imprenta"}` en línia fa dues feines alhora: renderitza el número calculat del recurs al text corrent ("Fig. 1") i — a la primera referència en ordre de lectura — fa *flotar* el recurs cap a la pàgina, reservant una banda a la part superior o inferior a prop d'aquesta referència, exactament com ho faria un tipògraf d'impremta. La figura no es col·loca mai una segona vegada. Per al recurs ocasional que ha de quedar en un punt exacte del flux, `::resource{id="…"}` en una línia pròpia és un incrustat de bloc opcional: només es renderitza en línia quan el `placement.position` resolt del recurs és `'here'` (cosa que l'exclou del flotament); per a un recurs flotat es tracta simplement com una referència més. L'autor no ha de pensar mai en la col·locació. D'això se n'encarrega el motor.

### Estratègia d'anàlisi

L'anàlisi és deliberadament el pas més simple de tot el pipeline. El markdown entra i en surt una llista plana de blocs de contingut tipats (`ContentBlock`, a `packages/postext/src/parse/`): un encapçalament, un paràgraf amb els seus trams en línia, un ítem de llista, una directiva. El resultat es memoritza (`parseMarkdownMemo`), de manera que les passades d'un mateix build analitzen el text una sola vegada, i un build posterior del mateix text tampoc no el torna a analitzar. Les referències a recursos es resolen contra l'array `resources[]` per ID a l'inici de cada passada de col·locació. Les definicions de notes a peu de pàgina (paràgrafs que comencen per `[^id]:`) també surten del flux en aquest punt i es desen per id per a les crides que les citen; l'array `notes[]` no es llegeix.

Pensa-hi com en un manifest: "hi ha un encapçalament, després un paràgraf de 200 paraules, després una referència a una figura, després un altre paràgraf." Sense mesures. Sense posicionament. Sense cap decisió de composició. Un `VDTBlock` només existeix quan la passada de col·locació ha mesurat un bloc i li ha donat un lloc.


## Arbre Virtual del Document (VDT)

Suposa que demanes a un tipògraf professional que compongui un llibre sencer, però en lloc d'entregar-te pàgines impreses, t'entrega un full de càlcul. Cada fila és un element. Cada cel·la és una mesura precisa: "l'encapçalament és a (40, 30), el primer paràgraf comença a (40, 78) i fa 144px d'alçada, la imatge va a la part superior de la columna 2 a la pàgina 3..." Aquest full de càlcul és el VDT.

L'Arbre Virtual del Document és l'estructura de dades central de Postext — un arbre mutable, modificat in situ, que representa cada pàgina, columna, bloc i línia, cadascun amb una caixa delimitadora precisa. Un cop `buildDocument` retorna, el VDT *és* la resposta. Pots consultar "què hi ha a la pàgina 72, columna 2?" sense renderitzar un sol píxel.

### Per què mutable

És el mateix enfocament que fan servir els pipelines de renderitzat dels motors de jocs, on sistemes successius actualitzen un estat mutable compartit del món en un bucle tancat. I per la mateixa raó.

Una passada de col·locació omple l'arbre in situ. Obre una pàgina, hi afegeix columnes, resta l'alçada d'un bloc de l'`availableHeight` de la columna on cau, i tanca les columnes d'una banda allà on la talla una caixa a amplada de pàgina. Un llibre té milers de blocs, i un arbre immutable (com el DOM virtual de React) assignaria un objecte nou per a cadascun d'aquests passos. Per això els nodes són objectes plans i la passada hi escriu.

Una passada acabada no s'apedaça. Quan `buildDocument` necessita un altre intent (un topall de banda, una palanca d'equilibrat), torna a executar la passada a partir del contingut i obté un arbre nou. L'arbre de la passada anterior queda com estava, de manera que el controlador pot comparar-los, quedar-se el millor o prendre unes pàgines de cadascun. La memòria cau de mesura fa assumible la repetició: un paràgraf el text, les fonts i l'amplada del qual no han canviat es llegeix de la memòria cau en lloc de tornar-se a mesurar.

### Definicions de tipus

Les formes de sota estan **simplificades per a l'exposició** — les definicions reals a `packages/postext/src/vdt.ts` porten molts més camps orientats al renderitzat (cadenes de font, colors, vinyetes de llista, renders matemàtics, slots de disseny). El que importa aquí és l'estructura:

```typescript
// Simplificat — vegeu packages/postext/src/vdt.ts per a les definicions completes

// L'arrel de l'Arbre Virtual del Document
interface VDTDocument {
  pages: VDTPage[];
  blocks: VDTBlock[];         // vista plana dels mateixos objectes bloc
  config: ResolvedConfig;     // cada subconfiguració resolta a no opcional
  baselineGrid: number;       // increment de línia de base en px (p. ex. 24 per a 16px/1.5)
  converged: boolean;         // cada segment d'equilibrat ha acabat a ras o sense palanques
  iterationCount: number;     // passades de col·locació darrere d'aquesta composició (vegeu El controlador de la passada)
  metadata: DocumentMetadata;
}

// Una pàgina física
interface VDTPage {
  index: number;
  width: number;
  height: number;
  columns: VDTColumn[];
  header?: VDTDesignSlot;     // capçalera (slot de disseny)
  footer?: VDTDesignSlot;     // peu / número de pàgina
  floats?: VDTBlock[];        // bandes de recursos flotats a dalt/a baix d'aquesta pàgina
  pageNumberValue: number;
  pageLabel: string;          // etiqueta renderitzada ('iv', '7', 'A', …)
}

// Una columna dins d'una pàgina
interface VDTColumn {
  index: number;
  bbox: BoundingBox;          // posició dins de la pàgina
  blocks: VDTBlock[];
  availableHeight: number;    // espai vertical restant
  baselineOffset: number;     // posició y actual de la línia de base
  band?: number;              // banda de columnes (0 tret que un bloc a amplada de pàgina parteixi la pàgina)
  kind?: 'text' | 'span' | 'side'; // 'span' = columna a tota l'amplada amb un bloc a amplada de pàgina,
                              // 'side' = la columna lateral, només per a flotants, d'una disposició de columna i mitja
}

// Un bloc de contingut (paràgraf, encapçalament, recurs, etc.)
type VDTBlockType =
  | 'paragraph' | 'heading' | 'resource' | 'blockquote'
  | 'listItem' | 'footnoteRef' | 'mathDisplay' | 'callout' | 'code';

interface VDTBlock {
  id: string;
  type: VDTBlockType;
  bbox: BoundingBox;
  lines: VDTLine[];           // per a blocs de text: les línies mesurades
  resourceBlock?: ResolvedResourceBlock; // per a blocs de recurs
  pageIndex: number;
  columnIndex: number;
  dirty: boolean;             // no es fa servir: es neteja en col·locar el bloc i no el llegeix res
  snappedToGrid: boolean;     // el flux ha tornat a la retícula de base sota aquest bloc
  balancing?: VDTBalancing;   // les palanques d'equilibrat de columnes aplicades a aquest bloc
}

// Una línia de text mesurada
interface VDTLine {
  text: string;
  bbox: BoundingBox;            // amplada natural: una línia justificada es pinta fins a la vora dreta del seu bloc
  baseline: number;             // posició y de la línia de base del text
  hyphenated: boolean;          // la línia acaba dins d'una paraula, o després d'un guió llarg sense espais («I.—» | «Que»)
  hardHyphen?: boolean;         // …després d'un guionet del mateix text («físico-» | «química»): no s'hi afegeix res
  repeatedHyphen?: boolean;     // comença amb aquest guionet repetit («léxico-» | «-semántico»), que no és a la font
  segments?: VDTLineSegment[];  // trams paraula/espai/matemàtica per justificar
  isLastLine?: boolean;         // última línia del seu paràgraf
  justifiedSpaceRatio?: number; // amplada a què es pinta cada espai ÷ espai de la rodona
  justifiedSpaceLimitRatio?: number; // l'espaiat que fiten els límits, quan els espais de la línia no són de rodona (lineWordSpacing llegeix tots dos)
  sourceStart?: number;         // mapa al markdown original (offsets de caràcter; una línia que comença per `\$` comença a la barra)
  sourceEnd?: number;
  plainStart?: number;          // mapa al text pla del bloc
  plainEnd?: number;
}

// Un incrustat de recurs mesurat i a punt per col·locar (bitmap / svg / taula / vídeo)
interface ResolvedResourceBlock {
  resource: Resource;
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  number: string;             // número calculat, p. ex. "1.7"
  captionPrefix: string;      // p. ex. "Figura"
  bodyRect: BoundingBox;      // l'àrea de la imatge / taula
  bodySource?: ResourceSafeArea; // la part de la imatge que es veu a bodyRect quan es retalla a la zona segura
  bodyFlex?: { shrink: number; grow: number; delta: number }; // px que el cos encara pot encongir / créixer, px aplicats
  fileId?: string;            // binari fora de banda (bitmap / svg)
  captionLines: VDTLine[];    // peu mesurat, amb prefix + número inclosos
  table?: VDTResourceTableLayout; // geometria de cel·les per a recursos taula
}

// Caixa delimitadora — tots els valors en px, relatius a l'origen de la pàgina
interface BoundingBox {
  x: number;
  y: number;
  width: number;
  height: number;
}
```

Alguns d'aquests camps mereixen una nota:

- **`isLastLine`** governa el renderitzat justificat: les línies finals es renderitzen en bandera fins i tot quan el paràgraf està justificat — excepte les línies finals *desbordades*, els espais entre paraules de les quals es comprimeixen per cabre a la mesura (semàntica d'ajust de glue de TeX).
- **`sourceStart`/`sourceEnd` i `plainStart`/`plainEnd`** són mapes des de cada línia cap al markdown original i cap al text pla del bloc — alimenten la sincronització de cursor i selecció en integracions d'editor.
- **`VDTResourceTableLayout`** (amb les seves entrades `VDTResourceTableCell`) porta la geometria completa d'una taula composta: les vores x de les columnes, les vores y de les files i els rectangles per cel·la amb les seves línies de contingut mesurades, de manera que tots els backends dibuixen la mateixa taula.
- **`dirty` i `snappedToGrid`** s'escriuen quan es col·loca un bloc i no els llegeix cap etapa ni cap backend. `dirty` comença a `true` en un bloc nou i passa a `false` quan el bloc es col·loca; el motor no fa cap seguiment de canvis sobre l'arbre, torna a executar la passada de col·locació (vegeu [El controlador de la passada](#el-controlador-de-la-passada)). `snappedToGrid` val `true` a la primera part d'un bloc de text després del qual el flux torna a la retícula (vegeu [Sistema de ritme vertical](#sistema-de-ritme-vertical)).
- **`balancing`** diu quines palanques d'equilibrat de columnes han mogut o estirat el bloc; un bloc que l'equilibrat ha deixat com estava no en porta (vegeu [Equilibrat de columnes](#equilibrat-de-columnes)).
- **`computePageTextExtent(page)`** és un petit helper públic que retorna l'extensió vertical realment coberta per text en una pàgina (incloent-hi els peus dels flotants). Les superposicions de depuració el fan servir perquè les línies de la retícula de base abastin només text real, no el final buit de la pàgina.


## Pipeline de composició

Una sola passada de col·locació, executada tantes vegades com la composició necessiti. Aquest és tot el pipeline de composició.

La passada (`placeDocumentPass`, a `packages/postext/src/pipeline/build.ts`) recorre el contingut del primer bloc a l'últim. Per a cada bloc fa tot el que cal per compondre'l: el mesura a l'amplada de la columna on està a punt d'entrar, mira si hi cap, el parteix o el fa avançar segons les regles de tall i de cohesió, ofereix un forat als flotants que cita, i torna el flux a la retícula de línies de base (vegeu [Sistema de ritme vertical](#sistema-de-ritme-vertical)). Els flotants, les vídues i la retícula no tenen cap passada pròpia: es resolen a mesura que cada bloc aterra.

Algunes decisions no es poden prendre dins d'un sol recorregut, perquè depenen d'on acaba el recorregut: els números de pàgina que imprimeix una taula de continguts, l'alçada a què una caixa a amplada de pàgina talla les columnes que té a sobre, les línies que encara falten a una columna curta. Per a aquestes, `buildDocument` torna a executar la passada amb *indicacions* tretes del resultat de la passada anterior. Les cinc etapes de sota segueixen un bloc al llarg de la passada; [El controlador de la passada](#el-controlador-de-la-passada) i [Equilibrat de columnes](#equilibrat-de-columnes) expliquen les repeticions.

### Etapa 1: Estructuració del contingut

- **Entrada:** `PostextContent` sense processar
- **Acció:** Analitzar el markdown en blocs de contingut, resoldre les referències a recursos contra `resources[]` per ID, treure del flux les definicions de notes a peu de pàgina (`[^id]:`) i numerar-ne les crides per ordre de citació, numerar els encapçalaments i planificar els flotants: quins recursos floten, i després de quin bloc (`notes[]` no es llegeix)
- **Sortida:** Una llista plana de blocs de contingut (tipats i amb contingut, però sense assignació de pàgina ni de columna) i el pla de flotants
- **S'executa:** a l'inici de cada passada de col·locació. L'anàlisi memoritzada es reutilitza després de la primera passada; la resta es torna a calcular

### Etapa 2: Mesura de text

- **Entrada:** Un bloc de contingut amb text, i l'amplada de la columna on està a punt d'entrar
- **Acció:** Mesurar les línies del bloc a aquesta amplada a través del **mòdul de mesura** dedicat (`packages/postext/src/measure/`), que afegeix partició de mots, justificació, trams enriquits en línia i partició de línies Knuth-Plass per sobre de Pretext. El resultat són les `VDTLine[]` del bloc i la seva alçada total
- **Detall clau:** La mesura es desa a la memòria cau. `cachedMeasureBlock` / `cachedMeasureRichBlock` (a `measure/cache.ts`) fan servir com a clau el text, les fonts, l'amplada i cada opció que afecta la composició, de manera que tornar a mesurar un paràgraf sense canvis és una consulta a un mapa
- **Sortida:** Les línies del bloc, amb dimensions precises en píxels
- **S'executa:** quan el recorregut arriba al bloc, no abans, perquè l'amplada depèn d'on cau el bloc: una columna al costat d'una columna lateral, les línies al costat d'una figura que el text envolta, les subcolumnes d'un grup `:::columns`. Un bloc que passa a una columna d'una altra amplada es torna a mesurar a aquesta amplada

El mòdul es reparteix netament per responsabilitat: `plain.ts` mesura trams plans, `rich.ts` mesura trams mixtos de negreta/cursiva/matemàtiques, `font.ts` construeix les cadenes de font i governa el cicle de vida de les memòries cau, i `canvas.ts` embolcalla les primitives crues d'amplada de text del canvas. Un detall del cicle de vida importa a la pràctica: les amplades de glif mesurades amb una font de reserva no han de sobreviure a l'arribada de la font real. `canvas.ts` desa les seves amplades per cadena de font juntament amb una generació de mesura; `evictFontFamilies` (que criden un build que descobreix que han canviat les cares d'una família, `watchFonts`, `prepareFonts` i `loadBundleFonts`) descarta les amplades d'aquelles famílies i buida la memòria cau de Pretext, i una `MeasurementCache` omplerta en una generació anterior descarta els seus blocs d'aquelles famílies a la consulta següent. `clearMeasurementCache()` fa el mateix amb totes les famílies. Les cares mateixes es carreguen abans de compondre a `fonts/prepare.ts` (`prepareFonts`), i `fonts/faces.ts` recupera les cares que ha fet servir un document compost, per als avisos `fontFallback`.

Els paràgrafs en xinès, japonès i coreà segueixen un altre camí dins del mateix mòdul. Un paràgraf amb més caràcters CJK que espais entre paraules passa al **compositor CJK** (`cjkCompose.ts`). Divideix el text en unitats (un caràcter, un tram de text llatí, un guió llarg o uns punts suspensius de dos quadratins, una caixa indivisible com una etiqueta o una crida de nota), mesura cada unitat una sola vegada i omple les línies per ordre, amb les regles de principi i final de línia de `cjkClasses.ts`: una línia admet un signe que no pot obrir la següent cedint blanc de la puntuació (`cjkPunctuation.ts`) abans de baixar un caràcter. Després, una línia justificada s'eixampla entre els seus caràcters. El resultat són `VDTLine` normals amb segments que porten el que els renderitzadors necessiten per pintar-los tal com es van mesurar: `tracking` (píxels després de cada caràcter, ja inclosos en l'amplada del segment), `inkOffset` per a un signe que ha cedit blanc, `hangs`, els espais entre xinès i llatí com a segments `autospace`, i les marques, les lectures ruby i les files warichu de les anotacions xineses. En un document japonès el mateix compositor segueix JLReq: les classes de kinsoku dels nivells japonesos es llegeixen, en el moment del tall, dels caràcters dels extrems de cada unitat, els blancs de la puntuació es comprimeixen i es retornen en l'ordre de JLReq, `rubyJis.ts` disposa els furigana (espaiat 1:2:1, desbordament sobre kana, paraules jukugo) i les marques de kanbun eixamplen la unitat del seu caràcter. El cost és lineal en la longitud del paràgraf: el capítol 1 de 紅樓夢 (6949 caràcters) es compon mesurant 1298 caràcters, una vegada cada caràcter diferent, mentre que mesurar prefixos del paràgraf en costava 636 948. Vegeu [Composició xinesa](/ca/docs/chinese-layout).

Per sota, aquí és on Pretext demostra el seu valor. La crida a `prepare()` és la part costosa — analitza el text fent servir el motor de fonts del canvas i desa el resultat a la memòria cau. I la crida a `layout()`? Aritmètica pura, pràcticament gratuïta. Aquesta divisió ho canvia tot. Un cop el text està preparat, el motor el pot tornar a partir en línies amb un cost insignificant: a una altra amplada, per a un paràgraf que continua en una columna més estreta, o amb una línia més, per a un paràgraf que l'equilibrat de columnes fa córrer. Preparar una vegada, compondre tantes vegades com calgui.

```typescript
// Simplificat: com fa servir pretext el mòdul de mesura internament
const prepared = prepare(paragraphText, '16px/1.5 Inter');
const { height } = layout(prepared, columnWidth, 24); // line-height de 24px
// => "Aquest paràgraf fa 168px d'alçada a 320px d'amplada de columna — són 7 línies."
```

### Etapa 3: Col·locació en pàgines i columnes

- **Entrada:** Un bloc mesurat
- **Acció:** Compondre el bloc a la columna actual. Crear nodes `VDTPage` i `VDTColumn` a mesura que el flux els necessita. Registrar `availableHeight` per columna. Quan un bloc no hi cap, partir-lo (Etapa 5) o avançar a la columna o la pàgina següent
- **Estratègia:** Col·locació greedy de primer ajust. Els salts de columna i de pàgina segueixen l'assignació vàlida més simple
- **Sortida:** El bloc té `pageIndex`, `columnIndex` i `bbox` assignats

Aquest és el moment en què el VDT es converteix en un document de debò. Abans d'aquesta etapa un bloc és una entrada d'una llista plana, sense adreça. La col·locació assigna cadascun a una pàgina i una columna, com qui aboca aigua en una quadrícula de recipients: omplir la columna 1 fins que vessi, passar a la columna 2 i, quan la pàgina és plena, començar-ne una de nova.

Abans que aterri cap bloc de contingut en una pàgina, la passada reserva espai per als elements estructurals — capçaleres i peus de pàgina (compostos com a slots de disseny a partir de `config.header` / `config.footer`) i les bandes de flotants ja pendents per a la pàgina acabada d'obrir. Aquestes reserves redueixen l'`availableHeight` de cada columna, de manera que quan els blocs de contingut comencen a fluir el motor ja sap exactament quant d'espai hi ha disponible.

**Bandes de columnes i columnes a amplada de pàgina.** `page.columns` és un array pla en ordre de lectura, però una pàgina no sempre és una única fila de columnes. En una disposició multicolumna, un bloc en línia a amplada de pàgina talla la pàgina en *bandes* apilades. Quatre coses compten com a tal: un `:::callout` l'estil o la tanca del qual fixa `span: 'page'`, un grup `:::columns{span="page"}` dins del text corrent, un `::resource` en línia la col·locació del qual es resol a `{ position: 'here', span: 'page' }`, i una tira de còmic composta a amplada de pàgina allà on s'escriu (`:::strip{span=page}`). Els tres últims s'emboliquen en una caixa a amplada de pàgina sense marc abans de la col·locació (`pipeline/flowColumns.ts`, `pipeline/spanEmbeds.ts`), de manera que un sol mecanisme els compon tots quatre. Al tall, les columnes de text de la banda actual es tanquen a la línia de tall (se'n retalla l'alçada i `availableHeight` queda a zero), el bloc rep la seva pròpia columna a tota l'amplada amb `kind: 'span'`, i a sota s'afegeix una banda nova de columnes de text (`band + 1`, amb la mateixa x i amplada i el mateix fons que la banda que substitueix). Les columnes només s'afegeixen al final, de manera que `columnIndex` continua apuntant a `page.columns[i]`, i els renderitzadors no necessiten cap traçat especial: cada columna retalla al seu propi bbox (eixamplat per `columnClipRect`: 2pt per a la tinta dels glifs més el que sobresurtin pels costats de la columna els seus dissenys superposats, com la pestanya d'un títol o el distintiu d'un requadre, i el que pugi per damunt de la seva part alta el disseny d'un encapçalament; el peu continua sent la vora; el mateix rectangle als backends canvas i PDF), i el filet entre columnes es dibuixa per banda entre columnes de text adjacents, començant sota la banda que ocupa un encapçalament a amplada de pàgina al capdamunt de la pàgina (`columnRuleSegments`), amb el filet propi de la pàgina quan una secció amb estil en fixa un (`VDTPage.columnRule`, llegit amb `pageColumnRule`). L'equilibrat de columnes ignora les columnes a amplada de pàgina, les columnes laterals i les bandes d'alçada zero. Un bloc a amplada de pàgina talla directament on la banda està anivellada (inici de pàgina, just després d'un encapçalament d'obertura, d'un altre bloc a amplada de pàgina o d'una banda de flotants superior); si arriba a una banda desigual, proposa en canvi un *topall de banda* (`packages/postext/src/pipeline/bandCaps.ts`) — les columnes de la banda que obre un bloc de contingut donat s'escurcen a `ceil(Σ usat / N / retícula)` línies — i `buildDocument` repeteix la passada de col·locació amb aquest topall (fent-lo créixer línia a línia quan la banda escurçada vessa, fins a `MAX_BAND_CAP_RETRIES` = 3 vegades, i descartant-lo després, de manera que el bloc passa al capdamunt de la pàgina següent), de manera que el text omple les columnes escurçades sota totes les regles de col·locació, acaba anivellat al tall, i les columnes tancades conserven el marge que quedi com a `availableHeight` perquè l'equilibrat l'absorbeixi. El mateix mecanisme anivella la banda de *tancament* de cada capítol i del document (`headings.balancing.trailing`): una obertura de capítol, un `:::part`, un avís `placement: 'fixed'` que tanca el capítol o el final del document, si s'hi arriba amb les columnes de la banda actual desiguals, proposa un topall `kind: 'trailing'`, indexat pel bloc límit; com que un topall s'indexa pel bloc que obre la seva banda — i aquest bloc es mou cada vegada que una pàgina anterior absorbeix línies d'equilibrat —, els topalls de tancament es resolen *després* que l'equilibrat de columnes s'hagi assentat, amb els seus ajustos congelats, i una breu ronda de poliment deixa que les palanques omplin el que el tall ha deixat curt. Els avisos `placement: 'fixed'` surten del flux: la caixa s'ancora a l'àrea de contingut / caixa de tall / caixa de sang de la pàgina, les columnes de text que cobreix cedeixen aquesta zona (retallada per baix o per dalt com una banda de flotants, i passant a la pàgina següent si hi ha conflicte), i la caixa amb els seus fills va a `page.floats`.

**Pàgines verticals.** Amb `layout.writingMode: 'vertical-rl'` la passada compon una pàgina horitzontal girada un quart de volta en el sentit de les agulles del rellotge. En aquesta pàgina, la caixa de text, les columnes, els blocs, les línies, els flotants i les zones de notes a peu de pàgina estan en **coordenades de flux**, i `VDTPage.flow` porta el gir que les duu al plec: un punt (x, y) del flux cau a (amplada de pàgina − y, x). Res del que ve després no ho necessita saber: els talls, els flotants, les regles de cohesió i l'equilibrat funcionen en el marc del flux com en qualsevol pàgina, una columna del flux és un pis al plec, i cada backend aplica el gir en pintar (`flowToPage` i `pageToFlow` converteixen punts en els dos sentits). Les capçaleres, els folis, les marques de tall i el fons continuen en coordenades del plec. Les figures i les taules es componen com a blocs drets girats de tornada dins del marc, i els caràcters que van drets es giren de tornada un a un en pintar.

### Etapa 4: Col·locació de recursos

- **Acció:** Fer flotar cada recurs referenciat al primer forat lliure després de la seva primera referència — el final de la columna de la referència, el principi / el final de la columna buida següent, o una banda de la pàgina següent (`packages/postext/src/pipeline/floatPlacement.ts` planifica els flotants, `pipeline/floatSlots.ts` enumera i mesura els forats; la passada de col·locació reserva les bandes mentre recorre el contingut)
- **S'executa:** tan bon punt ha aterrat el bloc que conté la primera referència, dins del mateix recorregut; el text que es col·loca després flueix al voltant de la banda
- **Resolució de la col·locació:** Per a cada recurs, el motor resol `resource.placement` → el `resourceType.defaultPlacement` del seu tipus → el valor per defecte integrat `{ position: 'auto', span: 'column' }`

`ResourcePlacement` té més camps que aquests dos: `rotate`, `width`, `align`, `columns`, `captionSide`, `shrink`, `minScale`, `captionMeasure`, `wrap`, `wrapGap` i `citingPage`. [Configuració → Tipus de recurs](/ca/docs/configuration-resources#tipus-de-recurs) i [Format del document › Col·locació](/ca/docs/document-format#collocació) expliquen què fa cadascun.

- **Col·locació diferida:** Un flotant que no cap en cap forat de la pàgina actual espera la pàgina següent que obri el flux i, en un límit de capítol, s'aboca en pàgines obertes per davant del límit. Una imatge conserva la seva mida tret que `placement.shrink` (o `layout.floatShrink`, per a tot el document) permeti reduir-la a l'espai que té un forat. Una taula massa alta per a una pàgina nova es talla entre files i continua a les pàgines següents, amb les files de capçalera repetides (`tableStyle.overflow: 'split'`, el valor per defecte)
- **Sortida:** Recursos posicionats en bandes de pàgina (`page.floats`), amb les alçades de les columnes afectades reduïdes perquè el text flueixi al voltant de les bandes

La col·locació de recursos és on les coses es posen interessants, perquè els flotants no només ocupen espai — remodelen l'espai que els envolta. Quan s'obre una pàgina, els flotants pendents reclamen primer les seves bandes, i les columnes s'encongeixen per encaixar-hi entremig. El text flueix després per les columnes estretes sense interrupció; el lector veu la figura a la part superior o inferior de la pàgina, a prop del punt on s'esmenta al text (encara que no exactament en aquest punt). Això és pràctica habitual en la composició tipogràfica professional; els llibres ho fan constantment.

**Regles de col·locació.** Més enllà del despatx de la col·locació, els flotants segueixen restriccions editorials estrictes:

- **Regla de post-referència.** Un flotant aterra al primer forat lliure *després* de la seva primera referència al text, mai abans. El lector troba primer la referència i després veu el recurs. Si un flotant no hi cap, es difereix cap endavant a un forat o una pàgina posterior, mai cap enrere.
- **Ordre de referència dins de cada seqüència.** Els flotants pendents s'ofereixen a cada forat en ordre de primera referència, i un que no cap enlloc reté els que vénen darrere seu en la seva seqüència de numeració: la taula 3 mai no aterra després de la taula 4, la figura 12 mai abans de la figura 11. Les seqüències no es retenen entre elles — una taula en espera deixa passar una figura posterior. Perquè una taula llarga no hagi d'esperar una pàgina nova, la que rep el capdamunt d'una columna buida es talla a aquesta columna i continua al forat següent (la columna del costat, o les bandes de la pàgina següent), amb les files de capçalera repetides.
- **Barrera de capítol.** Els flotants mai no s'escapen del seu capítol. En una obertura de capítol (un nivell d'encapçalament amb `breakBefore` o `span: 'page'`), un `:::part`, un estil d'avís amb `floatBarrier: true` i el final del document, tot flotant pendent es col·loca primer — als forats lliures de la pàgina, i després en pàgines obertes per davant del límit (cadascuna força com a mínim un flotant) — abans del salt de pàgina propi del límit. Abans d'obrir aquesta pàgina, a una figura o una taula encara pendent se li tornen a oferir els forats lliures de la pàgina actual, sigui quina sigui la seva `position`: un flotant de capçal de pàgina citat a la pàgina de tancament d'un capítol ocupa el peu d'aquesta pàgina, sota les columnes equilibrades, en lloc d'una pàgina pròpia (els avisos flotants conserven la seva col·locació). Un `:::pagebreak` envia els flotants pendents a la pàgina que el segueix, després del farciment de paritat.
- **Espai mínim de text.** En una pàgina acabada d'obrir, una banda només es reserva si encara hi caben com a mínim 3 línies de cos de text a les columnes afectades — amb una excepció: un flotant sobredimensionat es pot col·locar a la força en una banda que encara és tota text, perquè una figura dominant no pugui encallar la cua indefinidament. Un forat de la pàgina actual ha de cabre en l'alçada restant de la columna; la regla de les 3 línies només s'hi aplica al costat d'una altra banda de flotants.
- **Espai de respiració.** Un buit d'una alçada de línia de cos separa cada banda del text que l'acompanya.
- **Alineació amb la retícula de base.** Les bandes superiors s'arrodoneixen *cap amunt* a un múltiple de la retícula de base (fent més gran el buit sota el flotant), de manera que cada línia desplaçada continua caient a la retícula. Els flotants inferiors s'ancoren de manera que l'última línia de base del peu quedi sobre la retícula — el peu comparteix la línia de base amb l'última línia de text de les columnes veïnes, i les pàgines acaben a la mateixa alçada entre columnes i entre pàgines afrontades.

**Numeració tipada per primera referència.** Els recursos *no* es numeren al markdown. `pipeline/resourceNumbering.ts` assigna a cada recurs el seu número la primera vegada que es referencia en ordre de lectura, fent servir el seu `ResourceType`: la `numberingTemplate` combina el comptador per tipus `{n}` amb els comptadors d'encapçalament `{h1}`..`{h6}` vigents a la referència (p. ex. `'{h1}.{n}'` → "1.7"), `resetOn` controla quan es reinicia el comptador (`'never'` o a qualsevol nivell d'encapçalament), i `counterFormat` tria numerals decimals, romans o alfabètics. Els tipus integrats *Figura* i *Taula* provenen de `defaultResourceTypes(locale)`, localitzats a la llengua del document. Com que la numeració segueix l'ordre de primera referència, inserir una figura nova a mig document renumera automàticament tot el que ve després — sense editar el contingut original.

### Etapa 5: Talls i regles de cohesió

Aquesta és l'etapa que separa un motor de composició d'un bolcador de text. Aplica les regles de qualitat editorial que els tipògrafs professionals han aplicat a mà durant segles — i que el renderitzat de text ingenu ignora del tot.

Tres mecanismes es reparteixen la feina, i cadascun actua allà on existeix la informació que necessita: una **penalització de línia curta** dins del divisor de línies, una **partició puntuada** allà on un paràgraf topa amb el final d'una columna, i **regles estructurals de cohesió** entre blocs.

#### Vídues, òrfenes i línies curtes

Les **vídues i òrfenes** són els signes més visibles d'una composició amateur:

- Una **vídua** és una sola línia d'un paràgraf que queda aïllada al final d'una columna. El paràgraf
  continua a la columna següent, però aquella línia solitària sembla abandonada (com si la columna
  acabés abans d'hora).
- Una **òrfena** és una sola línia d'un paràgraf que queda encallada a l'inici d'una columna. El
  gruix del paràgraf és a la columna anterior, però una línia ha vessat (sembla desconnectada
  del seu context).
- Una **línia curta** (*runt*, en anglès) és l'última línia d'un paràgraf quan es queda en una sola paraula curta (o dues): visualment massa curta per semblar una línia de text com cal. Estructuralment menys greu que una vídua, però igual de molesta per a un lector atent.

**Les línies curtes es resolen al divisor de línies.** Una línia curta pertany només al paràgraf: la seva última línia és igual de curta allà on caigui el paràgraf. Per això és l'única de les tres regles que veu el divisor de línies de Knuth-Plass. Quan un conjunt de talls acabaria el paràgraf en una línia amb un contingut més estret que `runtMinCharacters × normalSpaceWidth` (valor per defecte de `runtMinCharacters`: 20, és a dir, vint espais entre paraules de contingut, entre 8 i 12 lletres), el divisor suma `runtPenalty` (valor per defecte 1000) al *badness* d'aquesta línia dins de la fórmula quadràtica de demerits, i així competeix a la mateixa escala que el *badness* de línia (que se satura a 10000) en lloc de quedar-ne aixafada. La penalització conviu amb els demerits habituals (*badness*, cost de partició de mots, desajust de classe de *fitness*) en una única optimització global, i el divisor gairebé sempre troba un conjunt de talls sense línia curta. Quan no el troba, `bodyText.tightenRunts` compon el paràgraf amb una línia menys si els seus espais entre paraules, i una mica de tracking negatiu, poden absorbir la diferència. El mòdul de mesura passa la penalització al divisor (`measure/plain.ts`, `measure/rich.ts`) i `knuthPlass/breakpoints.ts` l'aplica.

**Les vídues i les òrfenes es resolen al final de la columna.** El divisor de línies parteix un paràgraf per a una amplada. No sap en quin lloc de la pàgina quedarà el paràgraf, i per tant no pot saber quines de les seves línies tancaran una columna. La passada de col·locació sí. Quan les línies d'un paràgraf no caben totes en el que queda de columna, `chooseParagraphSplit` (a `pipeline/orphanWidow.ts`) prova cada partició `k` de les línies ja tallades, de 0 al nombre de línies que hi caben: `k` línies es queden i la resta obren la columna següent. Cada candidata rep una puntuació:

- `slackWeight · slack²` per les línies que deixa buides al peu de la columna, on `slack` són les línies que hi caben menys `k` (valor per defecte de `slackWeight`: 10);
- més `widowPenalty` (valor per defecte 1000) quan deixa menys de `widowMinLines` línies al final de la columna;
- més `orphanPenalty` (valor per defecte 1000) quan en porta menys de `orphanMinLines` al capdamunt de la següent.

Guanya la partició amb la puntuació més baixa, i `k = 0` fa passar el paràgraf sencer. Les regles són toves, i els números diuen fins a quin punt: una penalització de 1000 és el cost de *slack* de deu línies buides (10 · 10² = 1000), de manera que amb els valors per defecte una partició que respecta totes dues regles guanya sempre que deixi buides menys de deu línies de la columna. Més enllà, una vídua o una òrfena pot ser l'opció més barata. La partició tria entre les línies que el divisor de línies ja havia fet; no torna a dividir el paràgraf en línies. Els ítems de llista passen per la mateixa partició mitjançant `avoidOrphansInLists` i `avoidWidowsInLists`, i reben la penalització de línia curta mitjançant `avoidRuntsInLists` (tots a `true` per defecte).

Tot això es pot afinar a `BodyTextConfig` — vegeu [Configuració → Òrfenes, vídues, *runts* i cohesió](/ca/docs/configuration-text#òrfenes-vídues-runts-i-regles-de-cohesió). Posar qualsevol `*Penalty` a `0` desactiva efectivament aquella regla.

#### Regles estructurals de cohesió (keep-together)

Algunes agrupacions són més grans que un sol paràgraf — abasten blocs adjacents i no es poden resoldre només amb la divisió de línies. La passada de col·locació les aplica a mesura que cada bloc aterra, movent grups sencers cap endavant quan altrament es partirien en un salt de columna o de pàgina:

- **Títol amb el seu primer paràgraf.** Un títol no ha d'aparèixer mai al final d'una columna si el paràgraf que introdueix començaria a la columna següent. Ho gestiona `headings.keepWithNext` (per defecte `true`): si no hi ha lloc per al títol *més* el mínim de vídues del cos (`bodyText.widowMinLines`, per defecte `2`) del bloc següent — o només una línia quan `avoidWidows` està desactivat —, el títol s'empeny cap endavant per viatjar amb el seu text.
- **Títols consecutius.** Quan apareixen diversos títols en seqüència (per exemple, un h2 seguit d'un h3 seguit d'un paràgraf), tot el grup ha de romandre junt. Cap dels títols no pot quedar solt al final d'una columna sense el contingut que introdueix.
- **Llistes introduïdes amb dos punts.** Quan un paràgraf acaba amb dos punts que introdueixen directament una llista, la línia que porta els dos punts s'ha de quedar amb l'inici de la llista. Ho gestiona `bodyText.keepColonWithList` (per defecte `true`): si col·locar el paràgraf no deixés lloc perquè comenci el primer ítem de la llista (tot ell quan les regles d'òrfenes i vídues de les llistes el mantenen sencer; una línia amb `bodyText.colonListRoom: 'line'`, com fins a postext 1.4), l'última línia amb els dos punts (o el paràgraf sencer, si és d'una sola línia) es mou endavant juntament amb la llista. Sempre que aquesta regla hagi d'empènyer el paràgraf complet i just abans hi hagi una seqüència de títols a la columna, aquests títols també s'arrosseguen cap endavant per no violar silenciosament `keepWithNext`; l'única excepció és quan la columna conté només el títol (o títols) que un moviment anterior ja havia dut endavant, i en aquest cas el motor deixa el paràgraf al costat del títol i accepta la separació més lleu entre els dos punts i la llista per evitar un bucle.
- **Figura amb el seu peu.** Una figura i el seu peu de figura són una unitat inseparable. Sempre es mouen junts.

Quan es detecta una violació de cohesió, el motor empeny tot el grup a la columna o la pàgina següent. La columna que ha deixat acaba llavors curta, en les línies que el grup hi hauria ocupat. Omplir-la és feina de l'[Equilibrat de columnes](#equilibrat-de-columnes).

Aquestes correccions són invisibles quan es fan bé (un lector no les hauria de notar mai). Però la seva *absència* salta a la vista de qualsevol que llegeixi amb atenció: aquella línia incòmoda a l'inici d'una columna, aquells buits desiguals on el motor va renunciar a intentar ajustar el text. Les editorials professionals tenen guies d'estil senceres dedicades a prevenir exactament aquests problemes. Postext els automatitza.

      <td>Equilibrat de columnes una vegada més, sobre la composició amb el topall, amb segments nous</td>
      <td>10 intents per segment i 30 passades, comptats de nou</td>
    </tr>
  </tbody>
</table>

Les rondes 3 a 8 s'executen l'una darrere l'altra dins d'un mateix build (`buildDocumentBalanced`). Les rondes 1 i 2 en queden fora: una ronda de continguts o de números de nota és un build sencer, amb les seves pròpies rondes 3 a 8. No hi ha cap límit per al build en conjunt, només aquests.

**Cada repetició és una col·locació completa.** Una indicació no apedaça l'arbre de la passada anterior. La passada torna a col·locar el document amb la indicació en vigor, de manera que un encapçalament amb dues línies més al damunt, o una banda tallada sis línies més amunt, passa per les mateixes regles de tall i de cohesió que tota la resta. Després el controlador comprova el resultat: un topall de banda la caixa del qual no ha aterrat al tall creix o es descarta, i una passada d'equilibrat que no ha millorat un segment es descarta per a aquest segment. El que retorna el controlador està fet de pàgines que ha col·locat una passada: una passada sencera o, després de l'equilibrat de columnes, les pàgines de cada segment preses de la millor passada que ha tingut aquest segment.

**Què diu el document.** `doc.iterationCount` compta les passades de col·locació que hi ha darrere de la composició retornada: la primera i les de les rondes de topalls de banda, d'equilibrat i de bandes de tancament. Les passades de peus laterals i de flotants a la pàgina que els cita no hi entren, ni tampoc els builds anteriors d'una ronda de continguts o de números de nota; `BuildDocumentOptions.onPass` es crida per a cada passada, amb el temps que ha trigat. `doc.converged` parla només de l'equilibrat de columnes. Val `true` quan tots els segments han acabat sense cap línia buida a les seves columnes equilibrables o sense cap palanca per proposar, i `false` quan un segment s'ha aturat en una passada que no el millorava, o ha esgotat els intents, amb un buit encara obert. Amb l'equilibrat desactivat val `true`. Un document amb `converged: false` està complet: conté la millor composició que ha trobat el controlador, i alguna de les seves columnes acaba curta.

### Equilibrat de columnes

- **S'executa:** com a rondes 6 i 8 del controlador (activat per defecte; `headings.balancing.enabled: false` el desactiva, i està desactivat per defecte en text vertical i en una retícula de caràcters, vegeu [Configuració → Equilibratge de columnes](/ca/docs/configuration-text#equilibratge-de-columnes))
- **Entrada:** La millor composició fins al moment i les línies de retícula buides al peu de cada columna equilibrable (`collectColumnGaps`, a `pipeline/columnBalancing.ts`)
- **Acció:** Proposar palanques que omplin in situ cada columna curta, executar la passada de col·locació amb elles i conservar el resultat per a un segment quan la seva puntuació de buits ha baixat
- **Sortida:** Columnes que acaben a l'última línia de retícula de la pàgina, amb cada palanca registrada al bloc on s'ha aplicat (`VDTBlock.balancing`)

Les columnes desequilibrades es noten immediatament. Les regles de tall en deixen contínuament: un encapçalament que ha passat endavant per quedar-se amb el seu text, un paràgraf que ha passat sencer per evitar una vídua, una figura que no hi cabia. Una columna que s'atura dues línies per damunt de la del costat sembla inacabada — com si la maquetació s'hagués rendit a mig camí.

Cap bloc no canvia de columna per arreglar-ho. Un salt de columna va lligat a l'element que no hi cabia: el bloc que obre la columna següent era massa alt per a l'espai que quedava, i continua sent massa alt per a un espai més petit. Així doncs, una columna curta es pot omplir des de dins, com a màxim en la mida del seu buit, i res no travessa cap a la columna següent. L'ajust és local, que és el que fa un maquetista a mà: afegir una línia d'espai allà on l'ull l'accepta. Una columna és equilibrable quan el contingut ha continuat més enllà d'ella cap a una columna posterior de la mateixa pàgina o, per a l'última columna d'una pàgina, quan la pàgina flueix cap a la següent. L'última pàgina d'un capítol pot acabar curta; la seva banda de tancament la talla a nivell un topall de tancament (vegeu l'[Etapa 3](#etapa-3-collocació-en-pàgines-i-columnes)).

Per a cada buit les palanques es proposen en ordre de prioritat editorial, el mateix ordre en què les dona [Configuració → Equilibratge de columnes](/ca/docs/configuration-text#equilibratge-de-columnes):

1. **Una caixa que tanca la columna** pren l'espai que queda sota el seu peu com a espai al damunt, de manera que el seu peu cau a l'última línia de retícula de la pàgina, a nivell amb l'última línia de la columna contigua. Es registra com a `trailingCallout`.
2. **Les imatges amb zona segura** (`Resource.safeArea`), col·locades en línia a la columna o flotades al seu cap o al seu peu i només sobre ella, creixen en línies senceres de retícula, retallades dins de la zona segura. Una imatge més alta no deixa cap forat a la pàgina, així que aquesta palanca actua abans d'afegir cap espai. Es registra com a `flexFigure`.
3. **Els encapçalaments** prenen línies senceres de retícula al damunt, una línia cada vegada i per torns, començant per l'encapçalament més important (el de nivell més baix), que així en rep la part més gran. Un encapçalament al capdamunt mateix d'una columna no en pren cap, de manera que les columnes continuen començant a la part superior de la pàgina. Un encapçalament només pren així les seves primeres línies abans que es provin les palanques següents, i més, fins al seu màxim, quan aquestes ja no poden donar res més. Es registra com a `heading`.
4. **Els finals de llista** prenen una línia de retícula on acaba una llista. Es registra com a `listEnd`.
5. **Sota fórmules, caixes i figures** va una línia de retícula: sota una fórmula destacada o una caixa d'avís després de la qual segueix el text (`afterDisplay`), i entre una figura o taula que encapçala la columna i el text de sota (`afterFloat`).
6. **Els paràgrafs correguts** són l'últim recurs. Els paràgrafs de la columna, els més llargs primer, es recomponen cadascun amb una línia més (el `\looseness=+1` de TeX, a través de l'opció `looseness` del divisor Knuth-Plass), i la composició més llarga només s'accepta mentre totes les línies queden dins de `bodyText.maxWordSpacing`. Quan amb l'espaiat entre paraules no n'hi ha prou per guanyar la línia, el paràgraf pot prendre a més el menor tracking positiu que ho aconsegueixi, amb un límit. Es registra com a `looseParagraph`.

Els màxims, els interruptors i les excepcions (una retícula de caràcters, les pàgines de tancament, un flotant sobre diverses columnes) són claus de `headings.balancing`. La pàgina de Configuració les enumera i es manté al dia amb elles; aquesta pàgina no les repeteix.

Una proposta es comprova col·locant-la. La passada que aplica les palanques és una col·locació completa, i de tant en tant una palanca sí que acaba movent contingut a través d'un salt de columna: un paràgraf partit el cap del qual ja no hi cap, un flotant que ha perdut el seu forat. Les pàgines posteriors a aquest punt flueixen d'una altra manera i s'obren buits en altres llocs. El controlador ho veu a la puntuació, descarta la passada per a aquest segment i veta les palanques acabades d'aplicar a la primera columna que ha canviat, de manera que la proposta següent conserva les palanques que han funcionat i deixa fora la que ha provocat la cascada.

**L'equilibrat convergeix per segments.** Les pàgines entre salts explícits — l'obertura d'un capítol, un `:::pagebreak` — es maqueten independentment les unes de les altres: res no flueix a través d'un salt així, de manera que una palanca d'equilibrat dins d'una tanda de pàgines mai no pot moure una línia d'una altra. Per això el bucle d'equilibrat de columnes jutja cada *segment* per separat. La seva puntuació de buits és el nombre de línies de retícula buides al peu de les seves columnes equilibrables. Una passada continua col·locant el document sencer, però cada segment conserva o rebutja la seva part de les palanques segons la seva pròpia puntuació de buits, veta les seves pròpies cascades, s'estanca pel seu compte i gasta el seu propi pressupost d'intents; un segment el reintent del qual ha empitjorat recupera les seves pàgines de la millor passada que tenia mentre els altres continuen avançant. Així, un llibre de trenta capítols s'equilibra exactament igual que els seus capítols un per un — el PDF del llibre complet i el PDF del capítol solt són idèntics — en lloc que una cascada en qualsevol lloc costi una passada a totes les pàgines del llibre.

Els límits són una vàlvula de seguretat. Algunes columnes no es poden tancar: una que només conté paràgrafs curts no té cap palanca per accionar, i una en què cada palanca empeny un bloc a través del salt de columna no en té cap que es pugui conservar. El motor es queda la millor composició que ha trobat i deixa curta aquesta columna. Com que les palanques queden registrades als blocs, una prova d'impremta o un test poden enumerar les columnes que no ha tancat res (vegeu [Configuració → Quina palanca ha actuat](/ca/docs/configuration-text#quina-palanca-ha-actuat)).


## Sistema de ritme vertical

Agafa un llibre ben compost i posa'l a contrallum. Les línies de la pàgina esquerra s'alineen amb les de la dreta. La línia de base de la línia 5 a la columna 1 és exactament a la mateixa posició vertical que la línia de base de la línia 5 a la columna 2. Això és el ritme vertical, i és una de les primeres coses que un ull entrenat comprova en avaluar la qualitat tipogràfica. També és un dels diferenciadors clau de Postext.

Quan totes dues columnes contenen només text de cos a la mateixa mida, l'alineació és trivial — cada línia té la mateixa alçada, així que les línies de base s'alineen de manera natural. El repte apareix en el moment en què una columna conté un encapçalament amb una mida de font més gran, una imatge amb una alçada arbitrària en píxels, o espaiat extra al voltant d'una cita. Aquests elements "trenquen" la retícula: el contingut que hi ha a sota es desplaça una quantitat que no és múltiple de l'increment de línia de base, i de sobte les línies de base d'aquesta columna es desincronitzen de la columna adjacent. L'harmonia visual desapareix.

L'objectiu és recuperar-la: les línies de base del text de cos en columnes adjacents s'han d'alinear horitzontalment, fins i tot quan hi ha encapçalaments, imatges o altres elements amb alçades no estàndard en una columna però no en l'altra.

### Retícula de línies de base

Tot s'ancora a un sol nombre. El document defineix un valor `baselineGrid` derivat del line-height del text de cos — per exemple, text de cos a `16px` amb un `line-height` de `1.5` produeix una retícula de línies de base de `24px`. Cada línia de base del text de cos hauria de caure en un múltiple d'aquest valor. Aquest és el contracte.

### Elements que trenquen la retícula

Alguns elements trenquen la retícula perquè la seva alçada no és múltiple de `baselineGrid`:

- **Encapçalaments:** mida de font més gran, line-height diferent
- **Imatges:** alçada arbitrària en píxels
- **Taules:** alçada variable
- **Cites:** poden fer servir una mida de font o un padding diferent
- **Àrees de notes a peu de pàgina:** les notes a peu de pàgina d'una columna i el seu filet; l'àrea de text de la columna acaba a sobre

La retícula es manté en col·locar, bloc a bloc. Cap passada posterior no recorre les columnes buscant desviacions. Les línies de cos fan una línia de retícula d'alçada, de manera que una tirada de text de cos que comença sobre la retícula s'hi manté. Quan la passada de col·locació ha compost un bloc que pot sortir de la retícula, arrodoneix l'alçada usada a la columna fins a la línia de retícula següent abans que comenci el bloc següent. Els blocs que s'ajusten així són:

- l'últim encapçalament d'una sèrie d'encapçalaments (els encapçalaments consecutius se succeeixen sense ajust, i l'últim torna a alinear el text que els segueix);
- l'últim ítem d'una llista, sigui quin sigui l'espaiat entre ítems;
- una fórmula destacada;
- una caixa d'avís, un llistat de codi, i una figura o taula incrustada en línia;
- l'últim paràgraf d'un contenidor `:::paragraphs` i un poema `:::verse`, que tenen interlínia pròpia.

L'espai sota el bloc (`marginBottom`) es compta abans de l'arrodoniment, de manera que el marge és un mínim i la retícula decideix la resta. A la figura, la columna 1 conté un encapçalament de 36px d'alçada sobre una retícula de 24px, sense marge inferior. El seu peu cau 12px més enllà d'una línia de retícula, l'ajust afegeix 12px, i la línia de cos següent comença sobre la retícula, a nivell amb la línia que té al costat a la columna 2. Amb un `marginBottom` de 16px el peu quedaria a 52px, i l'ajust l'arrodoniria fins a 72px.

Les bandes de flotants mantenen la retícula a la seva manera, descrita a l'[Etapa 4](#etapa-4-collocació-de-recursos): una banda superior s'arrodoneix cap amunt a línies de retícula senceres, i un flotant inferior s'ancora de manera que l'última línia de base del seu peu quedi sobre la retícula. L'equilibrat de columnes afegeix el seu espai en línies de retícula senceres, de manera que també la manté.

Res no compara una columna amb una altra. Cada columna comença sobre la retícula i cada ajust hi torna, de manera que les línies de columnes adjacents, i de pàgines enfrontades, coincideixen sense una segona passada.

**Renunciar-hi.** `snapToGrid: false` manté en canvi l'espai exacte sota un bloc. Es pot fixar a `headings` (per a tots els nivells, per a un nivell o per a un estil d'encapçalament), en un estil de paràgraf, en un estil d'avís i a `codeStyle`. El text que segueix un bloc així pot quedar fora de la retícula fins al bloc següent que s'ajusti. El text de dins d'una caixa d'avís segueix la interlínia pròpia de la caixa i no té retícula.


## Interfície del backend

Hi ha exactament una font de veritat per a la mesura de text — el mòdul de mesura sobre les mètriques de font del canvas de Pretext — i tots els backends renderitzen a partir del mateix VDT acabat que aquest ha produït.

És una decisió deliberada, i existeix per una raó crítica: **la manera com mesures el text ha de coincidir exactament amb la manera com el renderitzes.** Suposa que la mesura fes servir mètriques de font del canvas, però un backend de renderitzat fes servir una biblioteca PDF amb taules de kerning lleugerament diferents. La composició no coincidiria amb la sortida. Línies que el motor ha mesurat com a ajustades a 320px podrien desbordar-se o quedar-se curtes en renderitzar-les. Cada píxel de desviació és una mentida. Si es mesura una sola vegada i es renderitza sempre des de la geometria resultant, els backends no poden discrepar: els salts de línia, les alçades de columna i la col·locació de recursos queden congelats al VDT abans que s'executi cap backend.

Per això el backend de PDF, per exemple, no torna a mesurar el text: consumeix un VDT acabat i tradueix les seves coordenades en píxels a punts PDF. Les mètriques del canvas són la font de veritat; PDF és un transport. Els usuaris de `renderToPdf` (del paquet `postext-pdf`) passen el mateix VDT que passarien a `renderToCanvas` o `renderToHtml`, i es garanteix que les tres sortides coincideixen.

### Superfície d'API

Els backends són funcions planes sobre `VDTDocument`, no una jerarquia de classes. No hi ha cap interfície `PostextBackend` — només els punts d'entrada de renderitzat de cada sortida i els helpers que necessita:

```typescript
// Canvas (des de 'postext')
renderToCanvas(doc, options?): HTMLCanvasElement[];     // un canvas per pàgina
renderPage(page, doc, options?): HTMLCanvasElement;     // una sola pàgina
renderPageToCanvas(page, doc, canvas, options?): void;  // dibuixa en un canvas existent

// Registre d'imatges de recurs del canvas — imatges descodificades per fileId
registerResourceImage(fileId, image, options?): void;   // options: { vector?, singleInk? }
unregisterResourceImage(fileId): void;
clearResourceImages(): void;

// HTML (des de 'postext')
renderToHtml(doc, options?): string;
renderToHtmlIndexed(doc, options?): HtmlRenderIndex;    // desglossament per pàgina / per bloc

// PDF (des de 'postext-pdf')
renderToPdf(doc, options): Promise<Uint8Array>;

// EPUB (des de 'postext-epub'), els capítols d'un llibre en ordre
renderToEpub(docs, options): Promise<Uint8Array>;
```

Com que els payloads binaris dels recursos viuen fora de banda, cada backend resol els `fileId` a la seva manera. El backend de canvas manté un registre de `CanvasImageSource` descodificats — l'aplicació amfitriona registra cada bitmap o SVG una vegada amb `registerResourceImage(fileId, image)` i el renderitzador el consulta en dibuixar. El backend HTML accepta un resolutor `resourceImageUrl(fileId)` a les seves opcions i emet etiquetes `<img>` que apunten a les URL (object URLs, data URIs, rutes de CDN) que retorni l'amfitrió. El backend PDF rep un proveïdor `resourceBytes` i incrusta els bytes reals; l'escriptor EPUB també en rep un i desa cada imatge una sola vegada com a fitxer del llibre. Un recurs de vídeo es dibuixa com la seva portada, un bitmap com qualsevol altre; el backend HTML també accepta un resolutor `resourceVideoUrl(fileId)` per als fitxers de vídeo que reprodueix, i l'escriptor EPUB desa aquests fitxers a `media/`. El backend PDF dibuixa la marca de reproducció i el codi QR com a traçats vectorials sobre la portada i, amb `video.linkPoster` activat, hi posa a sobre una anotació d'enllaç URI que obre `video.link`; en un PDF etiquetat l'enllaç s'uneix a la `Figure` de la portada, el text alternatiu de la qual comença pel nom del tipus (*Vídeo: …*). Els recursos de taula no necessiten res d'això — el seu model viatja en línia, i tots els backends dibuixen les cel·les a partir de la geometria de taula del VDT.

`renderToHtmlIndexed` mereix una nota: a més de la cadena HTML completa, retorna un desglossament per pàgina i per bloc (`HtmlRenderIndex`) perquè qui el crida pugui comparar-lo amb un render anterior i apedaçar només els subarbres del DOM l'HTML dels quals ha canviat de debò — la ruta de previsualització en viu del sandbox.

Els quatre backends disponibles consumeixen el mateix `VDTDocument`. La divisió entre `postext` (que exporta els backends de canvas i HTML) i `postext-pdf` (que exporta el backend de PDF) és purament una qüestió de dependències: el camí PDF arrossega `pdf-lib` i `@pdf-lib/fontkit`, i la majoria d'integracions web no els necessiten. Instal·la `postext-pdf` només quan de debò vulguis emetre bytes PDF. `postext-epub` és un paquet a part per la mateixa raó, i només cal per a llibres electrònics. La línia d'ordres no és un cinquè backend: `postext-cli` executa aquests mateixos generadors on no hi ha navegador.

**On s'executa la composició:** El motor mesura el text en un canvas, de manera que funciona allà on se li'n dona un. En un navegador, el pipeline es pot executar tant al fil principal (`buildDocument`) com dins d'un Web Worker dedicat (`createLayoutWorker` des de `postext/worker`) — la ruta del worker és la integració recomanada per a aplicacions orientades a UI perquè manté la mesura i les passades de col·locació fora del fil principal, admet cancel·lació *last-wins* mitjançant `AbortSignal`, i té la seva pròpia memòria cau de mesura i memòria cau de rasterització de matemàtiques perquè les reconstruccions successives continuïn sent barates. Consulta [Configuració → Executar la composició en un Web Worker](/ca/docs/configuration-programmatic-usage#executar-la-composició-en-un-web-worker) per al patró d'integració complet. Fora del navegador, la [línia d'ordres](/ca/docs/command-line) executa el mateix pipeline amb Skia fent de canvas del navegador, de manera que un llibre es parteix en les mateixes pàgines en un terminal, en un script o en un servidor de compilació.


## Estratègia de rendiment

La diferència entre una eina lenta i una que sembla màgica és un factor de 10x. Una composició de 500ms vol dir que l'usuari veu una estrebada visible cada vegada que canvia una paraula. Una composició de 50ms es percep instantània — com si el document sempre hagués estat allà. Aquest factor no es pot apedaçar després. Cal dissenyar-lo des del primer dia.

Pensa en allò a què s'enfronta el motor: milers de blocs de text repartits en centenars de pàgines, compostos de nou a cada edició, i diverses vegades quan la composició necessita les seves rondes. Els motors de jocs tenen la mateixa classe de problema — processar milers d'objectes (geometria, física, il·luminació, IA) 60 vegades per segon — i el resolen no repetint feina que ja han fet. Postext ho aplica al que més li costa, que és mesurar text.

### Principis

1. **Computació en memòria.** El VDT complet cap en memòria. No es llegeix el DOM durant la
   composició. El DOM només es toca al final, durant el renderitzat.

2. **Passades senceres sobre mesures a la memòria cau.** Una repetició de la passada de col·locació
   no busca què ha canviat: torna a col·locar el document des del primer bloc. Això és assumible perquè
   mesurar, la part costosa, es desa a la memòria cau per paràgraf (principi 5). Una passada que no
   canvia res del text, les fonts o l'amplada d'un paràgraf en llegeix les línies de la memòria cau.

3. **Rondes acotades.** Cada mena de repetició té un límit fix (vegeu
   [El controlador de la passada](#el-controlador-de-la-passada)), i l'equilibrat de columnes en té un
   per document a més d'un per segment, de manera que un llibre de molts capítols no pot gastar passades
   sense fi. El cost d'un build es pot mesurar passada a passada: `BuildDocumentOptions.onPass` informa
   de cada passada i del temps que ha trigat.


4. **Velocitat de Pretext.** La mesura de text a 300–600x la velocitat del DOM vol dir que el
   motor es pot permetre tornar a mesurar text de manera especulativa (provant diferents amplades de columna,
   punts de partició de mots, ajustos de tracking) sense bloquejar el fil principal.

5. **Memòria cau de mesura per capes.** El mòdul de mesura (`packages/postext/src/measure/`) manté
   una memòria cau de mesura explícita la clau de la qual inclou el text, les fonts, l'amplada i cada opció
   que afecta la composició, per damunt de la memòria cau pròpia de `prepare()` de Pretext i d'una
   memòria cau crua d'amplades de text. Tornar a mesurar un paràgraf sense canvis costa una consulta a un mapa.
   Quan canvien les cares d'una família, el motor descarta les amplades d'aquella família i la
   memòria cau de Pretext, i una memòria cau de mesura descarta els blocs compostos en aquella
   família a la consulta següent (porta la generació amb què es va omplir), de manera que les
   amplades de glif són correctes després de la càrrega de fonts sense que l'amfitrió hagi de
   cridar res; `clearMeasurementCache()` descarta totes les famílies.

6. **Divisió de línies a la ruta calenta.** La gestió de nodes actius de Knuth-Plass es va
   reescriure per velocitat: el conjunt actiu es compacta in situ a mesura que els nodes es
   retiren, i els candidats es dedupliquen per (línia, classe de *fitness*), de manera que només
   sobreviu el node amb menys demerits per clau. Els resultats algorísmics són idèntics —
   els mateixos conjunts de talls, calculats més de pressa.

7. **Builds fora del fil principal.** El punt d'entrada `postext/worker` executa el pipeline
   complet dins d'un Web Worker dedicat. El fil principal publica `{ content, config }` i un
   `AbortSignal`; el worker registra les fonts (transferides com a `ArrayBuffer`s), executa les passades
   de col·locació i publica de tornada el `VDTDocument` acabat. Una nova crida a `build()`
   cancel·la cooperativament l'anterior — el worker executa `buildDocumentAsync`, que consulta un hook
   de cancel·lació una vegada per bloc i entre passades i llança `BuildCancelledError`, de manera que un usuari que escriu en un editor
   mai no espera una composició ja obsoleta. El worker també manté la seva pròpia memòria cau persistent
   de mesura i una memòria cau de rasterització de matemàtiques amb clau per contingut, de manera que els
   objectes `MathRender` clonats estructuralment sobreviuen a les reconstruccions sense tornar-se a rasteritzar.

8. **VDT de doble accés.** L'arbre (`pages > columns > blocks`) proporciona accés jeràrquic per a
   la feina que va pàgina per pàgina o columna per columna (l'equilibrat de columnes mesura el buit
   al peu de cada columna). Un array pla paral·lel `blocks[]` dona accés directe a cada bloc sigui on
   sigui (la ronda de números de nota hi llegeix la crida que ha imprès cada nota). Totes dues vistes
   referencien els mateixos objectes bloc (no hi ha duplicació, només dues maneres de recórrer les
   mateixes dades).

### Tornar a compondre

No hi ha cap punt d'entrada incremental: cap crida no pren un VDT acabat i l'actualitza. Quan canvia el contingut o la configuració (una pulsació de tecla, una altra mida de pàgina), l'amfitrió torna a cridar `buildDocument` i obté un document nou.

El que es conserva d'un build al següent és la mesura. Crea una `MeasurementCache` una sola vegada amb `createMeasurementCache()` i passa-la com a tercer argument de cada crida a `buildDocument`. Un paràgraf el text, les fonts, l'amplada i les opcions de partició del qual no han canviat s'hi llegeix, de manera que un editor que compon el document a cada pulsació només mesura el paràgraf on s'està escrivint. Un canvi de mida de pàgina o de nombre de columnes canvia les amplades, i aquests paràgrafs es tornen a mesurar; els resultats de `prepare()` de Pretext continuen sent vàlids, perquè depenen de la font i del text i no de l'amplada, de manera que només s'executa l'aritmètica barata de `layout()`. L'anàlisi també es memoritza.

Per a un editor en viu, `createLayoutWorker` (de `postext/worker`) fa tot això fora del fil principal: el worker té una memòria cau de mesura que viu tant com ell, i un `build()` més nou cancel·la el que està en curs. Vegeu [Configuració → Memòria cau de mesures](/ca/docs/configuration-programmatic-usage#memòria-cau-de-mesures) i [Executar la composició en un Web Worker](/ca/docs/configuration-programmatic-usage#executar-la-composició-en-un-web-worker).

### Benchmarks

Hi ha dos benchmarks a `packages/postext/src/__bench__/`. `pnpm test` se'ls salta; `pnpm bench`, executat a `packages/postext`, els executa. `chapter.bench.test.ts` compon un capítol de la mida d'un llibre de text (quaranta seccions d'encapçalaments, paràgrafs i llistes) cinc vegades contra una memòria cau de mesura buida (en fred) i cinc vegades contra una de ja omplerta (en calent), i informa de totes dues medianes i del nombre de passades. `cjkChapter.bench.test.ts` compon el capítol 1 de 红楼梦 i compta els caràcters enviats a `measureText`, per mantenir el compositor CJK en un cost lineal en la longitud del paràgraf.

```typescript
// De packages/postext/src/__bench__/chapter.bench.test.ts
const cold: number[] = [];
for (let i = 0; i < ROUNDS; i++) cold.push(time(() => buildDocument({ markdown }, config, createMeasurementCache())));

const warmCache = createMeasurementCache();
buildDocument({ markdown }, config, warmCache);
const warm: number[] = [];
for (let i = 0; i < ROUNDS; i++) warm.push(time(() => buildDocument({ markdown }, config, warmCache)));

const passes: BuildPassInfo[] = [];
const doc = buildDocument({ markdown }, config, createMeasurementCache(), { onPass: (p) => passes.push(p) });
// [bench] chapter: … pages, … passes (… ms), iterationCount=…; cold median … ms, warm median … ms (5 rounds)
```

Una salvetat, per honestedat: a Node no hi ha canvas, de manera que tots dos benchmarks simulen la mesura de text i els seus temps absoluts no són els del navegador. La proporció entre fred i calent i el nombre de passades sí que són els del navegador, i una regressió en qualsevol dels dos es veu aquí abans que al sandbox. El benchmark del capítol informa de números i no trenca el build; el xinès comprova que els caràcters mesurats es mantenen per sota del triple de la longitud del paràgraf més llarg. Cap dels dos s'executa a CI: les regressions es detecten comparant els números entre execucions quan canvia una ruta calenta (com es va fer amb la reescriptura de nodes actius de Knuth-Plass). El rendiment és una funcionalitat, no una esperança — però avui la garantia és mesura i revisió, no un pipeline que falla.

## Fora d'abast

Cadascun d'aquests límits és una decisió conscient — el motor ja és prou complex per si
sol, i assumir responsabilitats que pertanyen a un altre lloc seria la manera més ràpida de no
acabar mai.

- **Edició WYSIWYG.** Postext és un motor de composició, no un editor. Entra contingut, surt geometria. Construir una superfície d'edició interactiva — gestió de cursor, selecció, desfer/refer, gestió de l'entrada — és un problema completament diferent. Postext pot servir com a backend de renderitzat per a un editor, però no proporciona capacitats d'edició per si mateix.
- **Wrapper de CSS column-count.** Postext substitueix la composició multicolumna de CSS; no l'embolcalla. Calcula geometria posicionada precisa des de zero, perquè l'algorisme de columnes del navegador no té control sobre la col·locació de recursos, la prevenció de vídues/òrfenes i les regles tipogràfiques entre columnes. Aquestes són precisament la raó de ser de Postext.
- **Gestió de breakpoints responsius.** Postext calcula la composició a una mida de pàgina donada. El consumidor decideix quan tornar a compondre (en redimensionar la finestra, en canviar l'orientació). Postext no gestiona breakpoints, media queries ni decisions de disseny responsiu. Això és cosa teva.
- **Edició col·laborativa en temps real.** Postext és un càlcul de composició sense estat — entra contingut, surt geometria — no un sistema de documents col·laboratiu amb resolució de conflictes, transformacions operacionals ni consciència multiusuari.
- **Fitxers de font.** El paquet `postext` carrega les fonts, però no les porta a dins. `prepareFonts` carrega abans de la primera composició totes les cares que demanen una configuració i el seu text, i una cara que el conjunt de fonts no ha pogut donar surt entre els avisos del document com a `fontFallback`. Els fitxers els posa qui integra el motor: una regla `@font-face` a la pàgina, o una funció `resolve` que diu on és cada cara. Vegeu [Configuració → Carregar les fonts abans de compondre](/ca/docs/configuration-programmatic-usage#carregar-les-fonts-abans-de-compondre).

### On viuen els tipus del VDT

Els tipus del VDT (`VDTDocument`, `VDTPage`, `VDTColumn`, `VDTBlock`, `VDTLine`, `VDTLineSegment`, `ResolvedResourceBlock`, `VDTResourceTableLayout`, `BoundingBox` i companyia) viuen a `packages/postext/src/vdt.ts`, al costat dels helpers de fàbrica (`createVDTDocument`, `createVDTPage`, `createVDTBlock`, …) i `computePageTextExtent`. No hi ha cap mòdul separat d'interfície de backend — els punts d'entrada de renderitzat descrits a [Interfície del backend](#interfície-del-backend) s'exporten directament des de `postext` (canvas, HTML), `postext-pdf` (PDF) i `postext-epub` (EPUB).
