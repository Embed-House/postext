# Arquitectura de Postext

Si has trabajado con React, ya conoces el truco fundamental. React construye un DOM virtual en memoria, lo compara con el anterior y solo entonces toca el DOM real del navegador. Postext hace exactamente lo mismo, pero en lugar de componentes de interfaz, construye un árbol de **páginas, columnas, bloques de texto y cajas delimitadoras**. Toda la geometría de un documento multipágina y multicolumna, calculada antes de renderizar un solo píxel. Cada párrafo, encabezado, imagen, nota al pie y cita destacada colocados en coordenadas exactas, respetando reglas tipográficas centenarias que CSS simplemente no puede expresar.

Todo esto es posible gracias a [`@chenglou/pretext`](https://github.com/chenglou/pretext), una librería de medición de texto sin DOM entre 300 y 600 veces más rápida que el reflow del navegador. Si quieres conocer la historia detrás del proyecto (una década de intentos fallidos, el cuello de botella que los frenaba a todos y la librería que finalmente lo eliminó), consulta la [Introducción](/es/docs/introduction).

## La idea central

Imagina un documento de 74 páginas a dos columnas. Un informe anual, quizá, o un libro de texto densamente ilustrado. Se lo entregas a Postext y el motor construye toda la composición en memoria: cada página, cada columna, la posición exacta y las dimensiones en píxeles de cada párrafo. ¿Quieres saber qué hay en la página 72, columna 2? La respuesta ya está ahí. Sin renderizar nada. El motor ya ha decidido dónde partir cada párrafo, dónde colocar cada imagen, cómo evitar viudas y huérfanas, y cómo alinear las líneas base entre columnas adyacentes.

Y aquí viene lo importante.

Las reglas tipográficas son profunda y desesperantemente interdependientes. Corriges una viuda en la página 5 — esa línea solitaria varada al final de una columna — retrayéndola a la columna anterior. Perfecto. Pero ese cambio acorta la columna de la página 5, lo que desplaza contenido hacia adelante, lo que podría crear una huérfana en la página 6. Una primera línea empujada a una nueva columna, desconectada de su párrafo. Para siquiera *detectar* que has creado un nuevo problema, necesitas la composición completa del documento disponible para inspección. Y para *corregirlo* sin crear otro problema en otro sitio, necesitas poder ajustar, re-medir y re-verificar todo.

Esa es la filosofía de "calcular todo primero, renderizar después". No es un truco de rendimiento. Es la única forma de aplicar las decenas de reglas tipográficas interconectadas que los tipógrafos profesionales llevan siglos usando.

**Este es el recorrido de tu contenido a través del motor:**

1. El **parser** lee el markdown enriquecido y lo convierte en una lista plana de bloques de contenido tipados: contenido y estructura, todavía sin posiciones
2. Una **pasada de colocación** recorre esa lista una vez y construye el VDT. Mide cada bloque a través de Pretext al ancho de la columna en la que va a entrar, coloca el texto, los flotados y las cajas en páginas y columnas, y aplica sobre la marcha las reglas de corte y de cohesión
3. El **controlador** (`buildDocument`) repite la pasada cuando una decisión necesita el resultado de una composición entera: un índice que imprime números de página, una caja a ancho de página que tiene que cortar a nivel las columnas de encima, una columna que quedó corta. Cada repetición recibe indicaciones de la pasada anterior, y cada tipo de repetición tiene su propio límite
4. El **VDT final** es la geometría completa de la composición: cada elemento conoce su número de página, su columna asignada, su posición y su caja delimitadora. El documento está completamente "compuesto" antes de que ocurra ningún renderizado
5. Un **backend** recorre el VDT terminado y lo renderiza al formato destino: un bitmap rasterizado sobre canvas, un árbol DOM de elementos HTML posicionados, un documento PDF con fuentes incrustadas o un EPUB. El mismo VDT alimenta a los cuatro; elegir backend es puramente una decisión de salida


## Capa de entrada

### Modelo de contenido

El modelo de contenido es tanto una filosofía como una estructura de datos. Tú describes *qué* decir, no *cómo* componerlo. Las decisiones de composición las toma el motor.

El motor resuelve las referencias en línea :ref y los embebidos ::resource por ID y produce el VDT.", "caption": "El markdown aporta el orden de lectura; los recursos aportan los datos visuales.", "contentTitle": "PostextContent", "markdown": "markdown", "markdownSub": "orden de lectura + :ref / ::resource por id", "resources": "resources[]", "resourcesSub": "bitmaps, SVGs, tablas", "notes": "metadata", "notesSub": "título, autoría, fechas", "resolveMarker": "resuelto por id: :ref{id=…}, ::resource{id=…}", "engineLabel": "motor", "vdtLabel": "VDT"}' />

```typescript
// packages/postext/src/types.ts

interface PostextContent {
  markdown: string;            // markdown enriquecido con marcadores :ref / ::resource
  metadata?: DocumentMetadata; // título, subtítulo, autoría, fecha de publicación, …
  resources?: Resource[];      // bitmaps, SVGs, tablas, vídeos — referenciados por id
  notes?: PostextNote[];       // no se lee: las notas al pie se escriben como [^id] en el markdown
}

interface Resource {
  id: string;                  // id estable, referenciado por los :ref en línea
  typeId: string;              // ResourceType al que pertenece ('figure', 'table', …)
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  caption?: string;            // el prefijo del tipo + número se calculan, no se escriben aquí
  altText?: string;
  createdAt: number;
  updatedAt: number;
  // Exactamente un payload específico del kind:
  bitmap?: { fileId: string; format: string; width: number; height: number };
  svg?: { fileId: string; width?: number; height?: number };
  table?: { model: TableModel };
  video?: ResourceVideo;       // de dónde se reproduce; en la página se dibuja su póster
  placement?: ResourcePlacement; // sobrescritura opcional de flotado por recurso
  safeArea?: ResourceSafeArea;  // bitmap / svg: { x, y, width, height } en fracciones, la parte que siempre se ve
}
```

Los **recursos** llevan los datos visuales: pies, texto alternativo y un payload específico de su `kind`. Los payloads binarios (bitmaps, SVGs) viven *fuera de banda* — el recurso solo guarda un `fileId`, y el renderizador lo resuelve en el momento de dibujar (el sandbox guarda los bytes en IndexedDB). Las tablas son la excepción: su `TableModel` (una cuadrícula de celdas con fusiones y alineación) viaja en línea, porque son datos estructurados, no bytes.
Las **notas** se escriben en el markdown: una llamada `[^id]` donde se cita la nota y una definición `[^id]:`, un párrafo propio en cualquier lugar del capítulo. El motor las numera en el orden en que se citan por primera vez y compone cada una al pie de la columna que contiene la línea que la cita, bajo un filete corto, o tras el último bloque del capítulo con `footnotes.placement: 'chapterEnd'` (ver [Notas al pie](/es/docs/document-format#notas-al-pie) y [Configuración → Notas al pie](/es/docs/configuration-notes-references#notas-al-pie)). El modelo de contenido sigue aceptando un array `notes`, pero ninguna etapa del pipeline lo lee.

Esta separación es una decisión de diseño deliberada, y tiene más importancia de lo que parece. El markdown es dueño del *orden de lectura* y la *estructura semántica* — qué va primero, qué es un encabezado, dónde se cita una nota al pie y qué dice. El array de recursos es dueño de los *datos visuales* — dimensiones de imagen, texto de pies de foto, celdas de tabla. Al mantenerlos separados, el mismo markdown puede componerse de formas completamente distintas simplemente cambiando la configuración. Una maquetación académica a dos columnas y un artículo de blog a columna única pueden compartir el mismo contenido fuente. Y el motor puede tomar decisiones de colocación — como diferir una imagen a la siguiente columna porque aquí no cabe — sin tocar jamás tu contenido original.

```typescript
// Ejemplo: un artículo sencillo con una figura referenciada
const content: PostextContent = {
  markdown: `
# El arte de la tipografía

La historia de la tipografía comienza con los tipos
móviles de Gutenberg, mostrados en :ref{id="imprenta"}.
Su invención transformó la producción de libros.

La técnica se extendió rápidamente por Europa, llegando
a Italia en 1465 y a Francia en 1470.
  `,
  resources: [
    {
      id: 'imprenta',
      typeId: 'figure',
      kind: 'bitmap',
      caption: 'Una reconstrucción de la imprenta original.',
      altText: 'Reconstrucción de la imprenta de Gutenberg',
      createdAt: 1765379100000,
      updatedAt: 1765379100000,
      bitmap: { fileId: 'foto-imprenta', format: 'jpeg', width: 600, height: 400 },
    },
  ],
};
```

Los recursos se conectan a la prosa por id, y **referenciar uno basta para incorporarlo**. El `:ref{id="imprenta"}` en línea hace dos trabajos a la vez: renderiza el número calculado del recurso en el texto corrido ("Fig. 1") y — en la primera referencia en orden de lectura — *flota* el recurso a la página, reservando una banda en la parte superior o inferior cercana a esa referencia, exactamente como haría un tipógrafo de imprenta. La figura nunca se coloca una segunda vez. Para el recurso ocasional que debe quedar en un punto exacto del flujo, `::resource{id="…"}` en su propia línea es un embebido de bloque opcional: solo se renderiza en línea cuando el `placement.position` resuelto del recurso es `'here'` (que lo excluye del flotado); para un recurso flotado se trata simplemente como una referencia más. El autor nunca tiene que pensar en la colocación. De eso se encarga el motor.

### Estrategia de análisis

El análisis es deliberadamente el paso más simple de todo el pipeline. El markdown entra y sale convertido en una lista plana de bloques de contenido tipados (`ContentBlock`, en `packages/postext/src/parse/`): un encabezado, un párrafo con sus tramos en línea, un ítem de lista, una directiva. El resultado se memoiza (`parseMarkdownMemo`), de modo que las pasadas de una composición analizan el texto una sola vez, y lo mismo hace una composición posterior del mismo texto. Las referencias a recursos se resuelven contra el array `resources[]` por ID al principio de cada pasada de colocación. Las definiciones de notas al pie (párrafos que empiezan por `[^id]:`) salen del flujo también ahí y se guardan por id para las llamadas que las citan; el array `notes[]` no se lee.

Piensa en ello como un manifiesto: "hay un encabezado, luego un párrafo de 200 palabras, luego una referencia a una figura, luego otro párrafo." Sin mediciones. Sin posicionamiento. Sin ninguna decisión de composición. Un `VDTBlock` solo existe cuando la pasada de colocación ha medido un bloque y le ha dado un sitio.


## Árbol Virtual del Documento (VDT)

Imagina que le pides a un tipógrafo profesional que componga un libro entero, pero en lugar de entregarte páginas impresas, te entrega una hoja de cálculo. Cada fila es un elemento. Cada celda es una medida precisa: "el encabezado está en (40, 30), el primer párrafo empieza en (40, 78) y mide 144px de alto, la imagen va en la parte superior de la columna 2 en la página 3..." Esa hoja de cálculo es el VDT.

El Árbol Virtual del Documento es la estructura de datos central de Postext — un árbol mutable, modificado in-place, que representa cada página, columna, bloque y línea, cada uno con una caja delimitadora precisa. Una vez que `buildDocument` termina, el VDT *es* la respuesta. Puedes consultar "¿qué hay en la página 72, columna 2?" sin renderizar un solo píxel.

### Por qué mutable

Es el mismo enfoque que usan los pipelines de renderizado de motores de juegos, donde un estado mutable compartido del mundo es actualizado por sistemas sucesivos en un bucle cerrado. Y por la misma razón.

Una pasada de colocación rellena el árbol in situ. Abre una página, le añade columnas, descuenta la altura de un bloque del `availableHeight` de la columna en la que cae y cierra las columnas de una banda allí donde la corta una caja a ancho de página. Un libro tiene miles de bloques, y un árbol inmutable (como el DOM virtual de React) asignaría un objeto nuevo en cada uno de esos pasos. Por eso los nodos son objetos planos y la pasada escribe en ellos.

Una pasada terminada no se parchea. Cuando `buildDocument` necesita otro intento (un tope de banda, una palanca de equilibrado), repite la pasada desde el contenido y obtiene un árbol nuevo. El árbol de la pasada anterior queda como estaba, y así el controlador puede comparar los dos, quedarse con el mejor o tomar unas páginas de cada uno. La caché de medición hace asumible la repetición: un párrafo cuyo texto, fuentes y ancho no han cambiado se lee de la caché en lugar de medirse otra vez.

### Definiciones de tipos

Las formas de abajo están **simplificadas para la exposición** — las definiciones reales en `packages/postext/src/vdt.ts` llevan muchos más campos orientados al renderizado (cadenas de fuente, colores, viñetas de lista, renders matemáticos, slots de diseño). Lo que importa aquí es la estructura:

```typescript
// Simplificado — véase packages/postext/src/vdt.ts para las definiciones completas

// La raíz del Árbol Virtual del Documento
interface VDTDocument {
  pages: VDTPage[];
  blocks: VDTBlock[];         // vista plana de los mismos objetos bloque
  config: ResolvedConfig;     // cada sub-config resuelta a no-opcional
  baselineGrid: number;       // incremento de línea base en px (p. ej. 24 para 16px/1.5)
  converged: boolean;         // cada segmento de equilibrado terminó a ras o sin palancas
  iterationCount: number;     // pasadas de colocación tras esta composición (ver El controlador de pasadas)
  metadata: DocumentMetadata;
}

// Una página física
interface VDTPage {
  index: number;
  width: number;
  height: number;
  columns: VDTColumn[];
  header?: VDTDesignSlot;     // cabecera (slot de diseño)
  footer?: VDTDesignSlot;     // pie / número de página
  floats?: VDTBlock[];        // bandas de recursos flotados arriba/abajo de esta página
  pageNumberValue: number;
  pageLabel: string;          // etiqueta renderizada ('iv', '7', 'A', …)
}

// Una columna dentro de una página
interface VDTColumn {
  index: number;
  bbox: BoundingBox;          // posición dentro de la página
  blocks: VDTBlock[];
  availableHeight: number;    // espacio vertical restante
  baselineOffset: number;     // posición y actual de la línea base
  band?: number;              // banda de columnas (0 salvo que un bloque a ancho de página parta la página)
  kind?: 'text' | 'span' | 'side'; // 'span' = columna a todo el ancho con un bloque a ancho de página,
                              // 'side' = la columna lateral solo para flotados de una disposición de columna y media
}

// Un bloque de contenido (párrafo, encabezado, recurso, etc.)
type VDTBlockType =
  | 'paragraph' | 'heading' | 'resource' | 'blockquote'
  | 'listItem' | 'footnoteRef' | 'mathDisplay' | 'callout' | 'code';

interface VDTBlock {
  id: string;
  type: VDTBlockType;
  bbox: BoundingBox;
  lines: VDTLine[];           // para bloques de texto: las líneas medidas
  resourceBlock?: ResolvedResourceBlock; // para bloques de recurso
  pageIndex: number;
  columnIndex: number;
  dirty: boolean;             // sin uso: se borra al colocar el bloque y nada lo lee
  snappedToGrid: boolean;     // el flujo volvió a la rejilla base bajo este bloque
  balancing?: VDTBalancing;   // las palancas de equilibrado de columnas aplicadas a este bloque
}

// Una línea de texto medida
interface VDTLine {
  text: string;
  bbox: BoundingBox;            // ancho natural: una línea justificada se pinta hasta el borde derecho de su bloque
  baseline: number;             // posición y de la línea base del texto
  hyphenated: boolean;          // la línea termina dentro de una palabra, o tras una raya sin espacios («I.—» | «Que»)
  hardHyphen?: boolean;         // …tras un guion del propio texto («físico-» | «química»): no se añade nada
  repeatedHyphen?: boolean;     // empieza con ese guion repetido («léxico-» | «-semántico»), que no está en la fuente
  segments?: VDTLineSegment[];  // tramos palabra/espacio/matemática para justificar
  isLastLine?: boolean;         // última línea de su párrafo
  justifiedSpaceRatio?: number; // ancho al que se pinta cada espacio ÷ espacio de la redonda
  justifiedSpaceLimitRatio?: number; // el espaciado que acotan los límites, cuando los espacios de la línea no son de redonda (lineWordSpacing lee los dos)
  sourceStart?: number;         // mapa al markdown original (offsets de carácter; una línea que empieza por `\$` empieza en la barra)
  sourceEnd?: number;
  plainStart?: number;          // mapa al texto plano del bloque
  plainEnd?: number;
}

// Un embebido de recurso medido y listo para colocar (bitmap / svg / tabla / vídeo)
interface ResolvedResourceBlock {
  resource: Resource;
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  number: string;             // número calculado, p. ej. "1.7"
  captionPrefix: string;      // p. ej. "Figura"
  bodyRect: BoundingBox;      // el área de la imagen / tabla
  bodySource?: ResourceSafeArea; // la parte de la imagen que se ve en bodyRect cuando se recorta a su zona segura
  bodyFlex?: { shrink: number; grow: number; delta: number }; // px que el cuerpo aún puede encoger / crecer, px aplicados
  fileId?: string;            // binario fuera de banda (bitmap / svg)
  captionLines: VDTLine[];    // pie medido, con prefijo + número incluidos
  table?: VDTResourceTableLayout; // geometría de celdas para recursos tabla
}

// Caja delimitadora — todos los valores en px, relativos al origen de la página
interface BoundingBox {
  x: number;
  y: number;
  width: number;
  height: number;
}
```

Algunos de estos campos merecen una nota:

- **`isLastLine`** gobierna el renderizado justificado: las líneas finales se renderizan en bandera incluso cuando el párrafo está justificado — excepto las líneas finales *desbordadas*, cuyos espacios entre palabras se comprimen para caber en la medida (semántica de ajuste de glue de TeX).
- **`sourceStart`/`sourceEnd` y `plainStart`/`plainEnd`** son mapas desde cada línea hacia el markdown original y hacia el texto plano del bloque — alimentan la sincronización de cursor y selección en integraciones de editor.
- **`VDTResourceTableLayout`** (con sus entradas `VDTResourceTableCell`) lleva la geometría completa de una tabla compuesta: los bordes x de las columnas, los bordes y de las filas y los rectángulos por celda con sus líneas de contenido medidas, de modo que todos los backends dibujan la misma tabla.
- **`dirty` y `snappedToGrid`** se escriben al colocar un bloque y no los lee ninguna etapa ni ningún backend. `dirty` nace a `true` en un bloque nuevo y pasa a `false` cuando el bloque se coloca; el motor no lleva la cuenta de los cambios del árbol, repite la pasada de colocación (ver [El controlador de pasadas](#el-controlador-de-pasadas)). `snappedToGrid` es `true` en la primera parte de un bloque de texto tras el que el flujo vuelve a la rejilla (ver [Sistema de ritmo vertical](#sistema-de-ritmo-vertical)).
- **`balancing`** dice qué palancas del equilibrado de columnas movieron o estiraron el bloque; un bloque que el equilibrado dejó como estaba no lo lleva (ver [Equilibrado de columnas](#equilibrado-de-columnas)).
- **`computePageTextExtent(page)`** es un pequeño helper público que devuelve la extensión vertical realmente cubierta por texto en una página (incluyendo los pies de los flotados). Las superposiciones de depuración lo usan para que las líneas de la rejilla base abarquen solo texto real, no el final vacío de la página.


## Pipeline de composición

Una sola pasada de colocación, repetida tantas veces como necesite la composición. Ese es todo el pipeline de composición.

La pasada (`placeDocumentPass`, en `packages/postext/src/pipeline/build.ts`) recorre el contenido del primer bloque al último. Con cada bloque hace todo lo necesario para componerlo: medirlo al ancho de la columna en la que va a entrar, ver si cabe, partirlo o pasarlo a la columna siguiente según las reglas de corte y de cohesión, ofrecer un hueco a los flotados que cita y devolver el flujo a la rejilla base (ver [Sistema de ritmo vertical](#sistema-de-ritmo-vertical)). Los flotados, las viudas y la rejilla no tienen pasada propia: se resuelven a medida que cae cada bloque.

Algunas decisiones no se pueden tomar dentro de un solo recorrido, porque dependen de dónde acaba: los números de página que imprime un índice, la altura a la que una caja a ancho de página corta las columnas de encima, las líneas que aún le faltan a una columna corta. Para esas, `buildDocument` repite la pasada con *indicaciones* sacadas del resultado de la anterior. Las cinco etapas siguientes acompañan a un bloque a lo largo de la pasada; [El controlador de pasadas](#el-controlador-de-pasadas) y [Equilibrado de columnas](#equilibrado-de-columnas) tratan las repeticiones.

### Etapa 1: Estructuración del contenido

- **Entrada:** `PostextContent` sin procesar
- **Acción:** Analizar el markdown en bloques de contenido, resolver las referencias a recursos contra `resources[]` por ID, sacar del flujo las definiciones de notas al pie (`[^id]:`) y numerar sus llamadas en orden de cita, numerar los encabezados y planificar los flotados: qué recursos flotan y tras qué bloque (`notes[]` no se lee)
- **Salida:** Una lista plana de bloques de contenido (tipados y con contenido, pero sin asignación de página ni columna) y el plan de flotados
- **Se ejecuta:** al principio de cada pasada de colocación. El análisis se lee de su memo a partir de la segunda pasada; lo demás se calcula de nuevo

### Etapa 2: Medición de texto

- **Entrada:** Un bloque de contenido con texto y el ancho de la columna en la que va a entrar
- **Acción:** Medir las líneas del bloque a ese ancho a través del **módulo de medida** dedicado (`packages/postext/src/measure/`), que añade separación silábica, justificación, tramos enriquecidos en línea y división de líneas Knuth-Plass por encima de Pretext. El resultado son las `VDTLine[]` del bloque y su altura total
- **Detalle clave:** La medición se cachea. `cachedMeasureBlock` / `cachedMeasureRichBlock` (en `measure/cache.ts`) usan como clave el texto, las fuentes, el ancho y cada opción que afecta a la composición, de modo que re-medir un párrafo sin cambios es una consulta a un mapa
- **Salida:** Las líneas del bloque, con dimensiones precisas en píxeles
- **Se ejecuta:** cuando el recorrido llega al bloque, no antes, porque el ancho depende de dónde cae: una columna junto a una columna lateral, las líneas que corren junto a una figura rodeada de texto, las subcolumnas de un grupo `:::columns`. Un bloque que pasa a una columna de otro ancho se mide otra vez a ese ancho

El módulo se reparte limpiamente por responsabilidad: `plain.ts` mide tramos planos, `rich.ts` mide tramos mixtos de negrita/cursiva/matemáticas, `font.ts` construye las cadenas de fuente y gobierna el ciclo de vida de las cachés, y `canvas.ts` envuelve las primitivas crudas de anchura de texto del canvas. Un detalle de ciclo de vida importa en la práctica: las anchuras de glifo medidas contra una fuente de respaldo no deben sobrevivir a la llegada de la fuente real. `canvas.ts` guarda sus anchuras por cadena de fuente junto con una generación de medida; `evictFontFamilies` (al que llaman un build que descubre que han cambiado las caras de una familia, `watchFonts`, `prepareFonts` y `loadBundleFonts`) descarta las anchuras de esas familias y vacía la caché de Pretext, y una `MeasurementCache` llenada en una generación anterior descarta sus bloques en esas familias en su siguiente consulta. `clearMeasurementCache()` hace lo mismo con todas las familias. Las propias caras se cargan antes de componer en `fonts/prepare.ts` (`prepareFonts`), y `fonts/faces.ts` recupera las caras que usó un documento compuesto, para los avisos `fontFallback`.

Los párrafos en chino, japonés y coreano siguen otro camino dentro del mismo módulo. Un párrafo con más caracteres CJK que espacios entre palabras pasa al **compositor CJK** (`cjkCompose.ts`). Divide el texto en unidades (un carácter, un tramo de texto latino, una raya o unos puntos suspensivos de dos cuadratines, una caja indivisible como una etiqueta o una llamada de nota), mide cada unidad una sola vez y llena las líneas por orden, con las reglas de principio y final de línea de `cjkClasses.ts`: una línea admite un signo que no puede abrir la siguiente cediendo blanco de la puntuación (`cjkPunctuation.ts`) antes de bajar un carácter. Después, una línea justificada se ensancha entre sus caracteres. El resultado son `VDTLine` normales cuyos segmentos llevan lo que los renderizadores necesitan para pintarlos tal como se midieron: `tracking` (píxeles tras cada carácter, ya incluidos en el ancho del segmento), `inkOffset` para un signo que cedió blanco, `hangs`, los espacios entre chino y latín como segmentos `autospace`, y las marcas, las lecturas ruby y las filas warichu de las anotaciones chinas. En un documento japonés el mismo compositor sigue JLReq: las clases de kinsoku de los niveles japoneses se leen, en el momento del corte, de los caracteres de los extremos de cada unidad, los blancos de la puntuación se comprimen y se devuelven en el orden de JLReq, `rubyJis.ts` dispone los furigana (espaciado 1:2:1, desborde sobre kana, palabras jukugo) y las marcas de kanbun ensanchan la unidad de su carácter. El coste es lineal en la longitud del párrafo: el capítulo 1 de 紅樓夢 (6949 caracteres) se compone midiendo 1298 caracteres, una vez cada carácter distinto, donde medir prefijos del párrafo costaba 636 948. Véase [Composición china](/es/docs/chinese-layout).

Por debajo, aquí es donde Pretext demuestra su valor. La llamada a `prepare()` es la parte costosa — analiza el texto usando el motor de fuentes del canvas y cachea el resultado. ¿Pero la llamada a `layout()`? Aritmética pura, prácticamente gratis. Esa división lo cambia todo. Una vez que el texto está preparado, el motor puede volver a partirlo con un coste insignificante: a otro ancho, para un párrafo que continúa en una columna más estrecha, o con una línea más, para un párrafo que el equilibrado de columnas compone corrido. Preparar una vez, componer tantas veces como haga falta.

```typescript
// Simplificado: cómo usa pretext el módulo de medida internamente
const prepared = prepare(paragraphText, '16px/1.5 Inter');
const { height } = layout(prepared, columnWidth, 24); // line-height de 24px
// => "Este párrafo mide 168px de alto a 320px de ancho de columna — son 7 líneas."
```

### Etapa 3: Colocación en páginas y columnas

- **Entrada:** Un bloque medido
- **Acción:** Componer el bloque en la columna actual. Crear nodos `VDTPage` y `VDTColumn` a medida que el flujo los necesita. Registrar `availableHeight` por columna. Cuando un bloque no cabe, partirlo (Etapa 5) o avanzar a la siguiente columna o página
- **Estrategia:** Colocación greedy de primer ajuste. Los saltos de columna y página siguen la asignación válida más simple
- **Salida:** El bloque tiene `pageIndex`, `columnIndex` y `bbox` asignados

Este es el momento en que el VDT se convierte en un documento de verdad. Antes de esta etapa, un bloque es una entrada de una lista plana, sin dirección. La colocación asigna cada uno a una página y columna, como verter agua en una cuadrícula de recipientes: llenar la columna 1 hasta que se desborde, pasar a la columna 2, y cuando la página esté llena empezar una nueva.

Antes de que aterrice ningún bloque de contenido en una página, la pasada reserva espacio para elementos estructurales — cabeceras y pies de página (compuestos como slots de diseño a partir de `config.header` / `config.footer`) y las bandas de flotados ya pendientes para la página recién abierta. Estas reservas reducen el `availableHeight` de cada columna, así que cuando los bloques de contenido empiezan a fluir, el motor ya sabe exactamente cuánto espacio hay disponible.

**Bandas de columnas y columnas a ancho de página.** `page.columns` es un array plano en orden de lectura, pero una página no siempre es una única fila de columnas. En una disposición multicolumna, un bloque en línea a ancho de página corta la página en *bandas* apiladas. Cuentan como tal cuatro cosas: un `:::callout` cuyo estilo o cuya valla fija `span: 'page'`, un grupo `:::columns{span="page"}` en el texto corrido, un `::resource` en línea cuya colocación se resuelve a `{ position: 'here', span: 'page' }` y una tira de cómic compuesta a lo ancho de la página allí donde está escrita (`:::strip{span=page}`). Los tres últimos se envuelven, antes de colocarlos, en una caja a ancho de página sin marco (`pipeline/flowColumns.ts`, `pipeline/spanEmbeds.ts`), de modo que un solo mecanismo compone los cuatro. En el corte, las columnas de texto de la banda actual se cierran en la línea de corte (su altura se recorta y `availableHeight` queda a cero), el bloque recibe su propia columna a todo el ancho con `kind: 'span'`, y debajo se añade una banda nueva de columnas de texto (`band + 1`, con la misma x y anchura y el mismo fondo que la banda a la que sustituye). Las columnas solo se añaden al final, así que `columnIndex` sigue apuntando a `page.columns[i]`, y los renderizadores no necesitan ningún trazado especial: cada columna recorta a su propio bbox (ensanchado por `columnClipRect`: 2pt para la tinta de los glifos más lo que sobresalgan por los lados de la columna sus diseños superpuestos, como la pestaña de un título o el distintivo de un recuadro, y lo que suba por encima de su parte alta el diseño de un encabezado; el pie sigue siendo el borde; el mismo rectángulo en los backends canvas y PDF), y el filete entre columnas se dibuja por banda entre columnas de texto adyacentes, empezando bajo la banda que ocupa un encabezado a ancho de página en la cabeza de la página (`columnRuleSegments`), con el filete propio de la página cuando una sección con estilo fija uno (`VDTPage.columnRule`, leído con `pageColumnRule`). El equilibrado de columnas ignora las columnas a ancho de página, las columnas laterales y las bandas de altura cero. Un bloque a ancho de página corta directamente donde la banda está nivelada (inicio de página, justo después de un encabezado de apertura, de otro bloque a ancho de página o de una banda de flotantes superior); si llega a una banda desigual propone en su lugar un *tope de banda* (`packages/postext/src/pipeline/bandCaps.ts`) — las columnas de la banda que abre un bloque de contenido dado se acortan a `ceil(Σ usado / N / rejilla)` líneas — y `buildDocument` repite la pasada de colocación con ese tope (agrandándolo línea a línea cuando la banda acortada desborda, hasta `MAX_BAND_CAP_RETRIES` = 3 veces, y descartándolo después, con lo que el bloque pasa a la cabeza de la página siguiente), de modo que el texto llena las columnas acortadas bajo todas las reglas de colocación, termina nivelado en el corte, y las columnas cerradas conservan la holgura que quede como `availableHeight` para que el equilibrado la absorba. El mismo mecanismo nivela la banda de *cierre* de cada capítulo y del documento (`headings.balancing.trailing`): una apertura de capítulo, un `:::part`, un aviso `placement: 'fixed'` que cierra el capítulo o el final del documento alcanzado con las columnas de la banda actual desiguales propone un tope `kind: 'trailing'`, indexado por el bloque límite; como un tope se indexa por el bloque que abre su banda — y ese bloque se mueve cada vez que una página anterior absorbe líneas de equilibrado —, los topes de cierre se resuelven *después* de que el equilibrado de columnas se haya asentado, con sus ajustes congelados, y una breve ronda de pulido deja que las palancas rellenen lo que el corte dejó corto. Los avisos `placement: 'fixed'` salen del flujo: la caja se ancla al área de contenido / caja de corte / caja de sangre de la página, las columnas de texto que cubre ceden esa zona (recortada por abajo o por arriba como una banda de flotantes, pasando a la página siguiente si hay conflicto), y la caja con sus hijos va a `page.floats`.

**Páginas verticales.** Con `layout.writingMode: 'vertical-rl'` la pasada compone una página horizontal girada un cuarto de vuelta en el sentido de las agujas del reloj. En esa página, la caja de texto, las columnas, los bloques, las líneas, los flotantes y las zonas de notas al pie están en **coordenadas de flujo**, y `VDTPage.flow` lleva el giro que las lleva al pliego: un punto (x, y) del flujo cae en (ancho de página − y, x). Nada de lo que viene después necesita saberlo: los cortes, los flotantes, las reglas de cohesión y el equilibrado funcionan en el marco del flujo como en cualquier página, una columna del flujo es un piso en el pliego, y cada backend aplica el giro al pintar (`flowToPage` y `pageToFlow` convierten puntos en los dos sentidos). Las cabeceras, los folios, las marcas de corte y el fondo siguen en coordenadas del pliego. Las figuras y las tablas se componen como bloques derechos girados de vuelta dentro del marco, y los caracteres que van de pie se giran de vuelta uno a uno al pintar.

### Etapa 4: Colocación de recursos

- **Entrada:** El plan de flotados de la Etapa 1 y las páginas tal como están colocadas hasta ese momento
- **Acción:** Flotar cada recurso referenciado al primer hueco libre tras su primera referencia — el final de la columna de la referencia, el principio / el final de la siguiente columna vacía, o una banda de la página siguiente (`packages/postext/src/pipeline/floatPlacement.ts` planifica los flotados, `pipeline/floatSlots.ts` enumera y mide los huecos; la pasada de colocación reserva las bandas a medida que avanza)
- **Se ejecuta:** en cuanto ha caído el bloque que contiene la primera referencia, dentro del mismo recorrido; el texto que se coloca después fluye junto a la banda
- **Resolución de la colocación:** Por recurso, el motor resuelve `resource.placement` → el `resourceType.defaultPlacement` de su tipo → el valor por defecto integrado `{ position: 'auto', span: 'column' }`

`ResourcePlacement` tiene más campos que estos dos: `rotate`, `width`, `align`, `columns`, `captionSide`, `shrink`, `minScale`, `captionMeasure`, `wrap`, `wrapGap` y `citingPage`. [Configuración → Tipos de recurso](/es/docs/configuration-resources#tipos-de-recurso) y [Formato del documento › Colocación](/es/docs/document-format#colocación) explican qué hace cada uno.

- **Colocación diferida:** Un flotado que no cabe en ningún hueco de la página actual espera a la siguiente página que abra el flujo y, en un límite de capítulo, se vuelca en páginas abiertas por delante del límite. Una imagen conserva su tamaño salvo que `placement.shrink` (o `layout.floatShrink`, para todo el documento) permita reducirla al sitio que tiene un hueco. Una tabla demasiado alta para una página nueva se corta entre filas y continúa en las páginas siguientes, con sus filas de cabecera repetidas (`tableStyle.overflow: 'split'`, el valor por defecto)
- **Salida:** Recursos posicionados en bandas de página (`page.floats`), con las alturas de las columnas afectadas reducidas para que el texto fluya alrededor de las bandas

La colocación de recursos es donde las cosas se ponen interesantes, porque los flotados no solo ocupan espacio — remodelan el espacio a su alrededor. Cuando se abre una página, los flotados pendientes reclaman primero sus bandas, y las columnas se encogen para encajar entre ellas. El texto fluye después por las columnas estrechadas sin interrupción; el lector ve la figura en la parte superior o inferior de la página, cerca del punto donde se menciona en el texto (aunque no exactamente en él). Esto es práctica estándar en la composición tipográfica profesional; los libros lo hacen constantemente.

**Reglas de colocación.** Más allá del despacho de la colocación, los flotados siguen restricciones editoriales estrictas:

- **Regla de post-referencia.** Un flotado aterriza en el primer hueco libre *después* de su primera referencia en el texto, nunca antes. El lector encuentra la referencia primero y luego ve el recurso. Si un flotado no cabe, se difiere hacia adelante a un hueco o página posterior, nunca hacia atrás.
- **Orden de referencia dentro de cada secuencia.** Los flotados pendientes se ofrecen a cada hueco en orden de primera referencia, y uno que no cabe en ninguna parte retiene a los que vienen detrás en su secuencia de numeración: la tabla 3 nunca aterriza después de la tabla 4, la figura 12 nunca antes que la figura 11. Las secuencias no se retienen entre sí — una tabla en espera deja pasar a una figura posterior. Para que una tabla larga no tenga que esperar a una página nueva, la que recibe la cabecera de una columna vacía se corta a esa columna y continúa en el siguiente hueco (la columna de al lado, o las bandas de la página siguiente), con sus filas de cabecera repetidas.
- **Barrera de capítulo.** Los flotados nunca escapan de su capítulo. En una apertura de capítulo (un nivel de encabezado con `breakBefore` o `span: 'page'`), un `:::part`, un estilo de aviso con `floatBarrier: true` y el final del documento, todo flotado pendiente se coloca primero — en los huecos libres de la página, y después en páginas abiertas por delante del límite (cada una fuerza al menos un flotado) — antes del salto de página propio del límite. Antes de abrir esa página, a una figura o tabla aún pendiente se le ofrecen otra vez los huecos libres de la página actual sea cual sea su `position`: un flotado de cabeza de página citado en la página de cierre de un capítulo ocupa el pie de esa página, bajo las columnas equilibradas, en lugar de una página propia (los avisos flotantes conservan su colocación). Un `:::pagebreak` envía los flotados pendientes a la página que le sigue, tras el relleno de paridad.
- **Espacio mínimo de texto.** En una página recién abierta, una banda solo se reserva si todavía caben al menos 3 líneas de cuerpo de texto en las columnas afectadas — con una excepción: un flotado sobredimensionado puede colocarse a la fuerza en una banda que aún es todo texto, para que una figura dominante no pueda atascar la cola indefinidamente. Un hueco de la página actual debe caber en la altura restante de la columna; la regla de las 3 líneas solo se aplica ahí junto a otra banda de flotantes.
- **Espacio de respiración.** Un hueco de una altura de línea de cuerpo separa cada banda del texto que la acompaña.
- **Alineación con la rejilla base.** Las bandas superiores se redondean *hacia arriba* a un múltiplo de la rejilla base (agrandando el hueco bajo el flotado), de modo que cada línea desplazada sigue cayendo en la rejilla. Los flotados inferiores se anclan de forma que la última línea base del pie quede sobre la rejilla — el pie comparte su línea base con la última línea de texto de las columnas vecinas, y las páginas terminan a la misma altura entre columnas y entre páginas enfrentadas.

**Numeración tipada por primera referencia.** Los recursos *no* se numeran en el markdown. `pipeline/resourceNumbering.ts` asigna a cada recurso su número la primera vez que se referencia en orden de lectura, usando su `ResourceType`: la `numberingTemplate` combina el contador por tipo `{n}` con los contadores de encabezado `{h1}`..`{h6}` vigentes en la referencia (p. ej. `'{h1}.{n}'` → "1.7"), `resetOn` controla cuándo se reinicia el contador (`'never'` o en cualquier nivel de encabezado), y `counterFormat` elige numerales decimales, romanos o alfabéticos. Los tipos integrados *Figura* y *Tabla* provienen de `defaultResourceTypes(locale)`, localizados al idioma del documento. Como la numeración sigue el orden de primera referencia, insertar una figura nueva a mitad del documento renumera automáticamente todo lo posterior — sin editar el contenido original.

### Etapa 5: Cortes y reglas de cohesión

Esta es la etapa que separa un motor de composición de un volcador de texto. Aplica las reglas de calidad editorial que los tipógrafos profesionales han aplicado a mano durante siglos — y que el renderizado de texto ingenuo ignora por completo.

Tres mecanismos se reparten el trabajo, y cada uno actúa allí donde existe la información que necesita: una **penalización de línea corta** dentro del divisor de líneas, una **partición puntuada** donde un párrafo se encuentra con el final de una columna, y **reglas estructurales de cohesión** entre bloques.

#### Viudas, huérfanas y líneas cortas

Las **viudas y huérfanas** son los signos más visibles de una composición amateur:

- Una **viuda** es una sola línea de un párrafo que queda aislada al final de una columna. El párrafo
  continúa en la columna siguiente, pero esa línea solitaria parece abandonada (como si la columna
  terminara prematuramente).
- Una **huérfana** es una sola línea de un párrafo que queda varada al inicio de una columna. El
  grueso del párrafo está en la columna anterior, pero una línea se desbordó (parece desconectada
  de su contexto).
- Una **línea corta** (*runt*, en inglés) es la última línea de un párrafo cuando se queda en una sola palabra corta (o dos): visualmente demasiado corta para sentirse como una línea de texto en condiciones. Menos grave estructuralmente que una viuda, pero igual de molesta para un lector atento.

**Las líneas cortas se resuelven en el divisor de líneas.** Una línea corta es cosa del párrafo y de nada más: su última línea es igual de corta caiga donde caiga el párrafo. Por eso es la única de las tres reglas que ve el divisor de líneas de Knuth-Plass. Cuando un conjunto de cortes terminaría el párrafo en una línea cuyo contenido es más estrecho que `runtMinCharacters × normalSpaceWidth` (valor por defecto de `runtMinCharacters`: 20, es decir, un contenido tan ancho como veinte espacios entre palabras, de 8 a 12 letras más o menos), el divisor suma `runtPenalty` (valor por defecto 1000) al *badness* de esa línea dentro de la fórmula cuadrática de demerits, y así compite en la misma escala que el *badness* de línea (que satura en 10000) en vez de quedar aplastado por él. La penalización convive con los demerits habituales (*badness*, coste de separación silábica, desajuste de clase de *fitness*) en una única optimización global, y el divisor encuentra casi siempre un conjunto de cortes sin línea corta. Cuando no lo encuentra, `bodyText.tightenRunts` compone el párrafo con una línea menos si sus espacios entre palabras, y un poco de tracking negativo, pueden absorber la diferencia. El módulo de medida entrega la penalización al divisor (`measure/plain.ts`, `measure/rich.ts`) y `knuthPlass/breakpoints.ts` la aplica.

**Las viudas y las huérfanas se resuelven al final de la columna.** El divisor de líneas parte un párrafo para un ancho. No sabe en qué lugar de la página quedará el párrafo, así que no puede saber cuáles de sus líneas cerrarán una columna. La pasada de colocación sí lo sabe. Cuando las líneas de un párrafo no caben todas en lo que queda de columna, `chooseParagraphSplit` (en `pipeline/orphanWidow.ts`) prueba todas las particiones `k` de las líneas ya cortadas, de 0 al número de líneas que caben: `k` líneas se quedan y el resto abre la columna siguiente. Cada candidata recibe una puntuación:

- `slackWeight · slack²` por las líneas que deja vacías al pie de la columna, siendo `slack` las líneas que caben menos `k` (valor por defecto de `slackWeight`: 10);
- más `widowPenalty` (valor por defecto 1000) cuando deja menos de `widowMinLines` líneas al final de la columna;
- más `orphanPenalty` (valor por defecto 1000) cuando lleva menos de `orphanMinLines` líneas al inicio de la siguiente.

Gana la partición con la puntuación más baja, y `k = 0` pasa el párrafo entero. Las reglas son blandas, y los números dicen cuánto: una penalización de 1000 es el coste de *slack* de diez líneas vacías (10 · 10² = 1000), así que con los valores por defecto una partición que cumple las dos reglas gana siempre que deje vacías menos de diez líneas de la columna. Más allá, una viuda o una huérfana puede salir más barata. La partición elige entre las líneas que el divisor de líneas ya hizo; no vuelve a cortar el párrafo. Los ítems de lista pasan por la misma partición mediante `avoidOrphansInLists` y `avoidWidowsInLists`, y reciben la penalización de línea corta mediante `avoidRuntsInLists` (todos a `true` por defecto).

Todo esto se puede afinar en `BodyTextConfig` — véase [Configuración → Huérfanas, viudas, *runts* y cohesión](/es/docs/configuration-text#huérfanas-viudas-runts-y-reglas-de-cohesión). Ajustar cualquier `*Penalty` a `0` desactiva efectivamente esa regla.

#### Reglas estructurales de cohesión (keep-together)

Algunas agrupaciones son mayores que un solo párrafo — abarcan bloques adyacentes y no pueden resolverse solo con la división de líneas. La pasada de colocación las aplica a medida que cae cada bloque, moviendo grupos enteros hacia adelante cuando de otro modo se partirían en un salto de columna o de página:

- **Título con su primer párrafo.** Un título nunca debe aparecer al final de una columna si el párrafo que introduce empezaría en la columna siguiente. Lo gestiona `headings.keepWithNext` (por defecto `true`): si no hay sitio para el título *más* el mínimo de viudas del cuerpo (`bodyText.widowMinLines`, por defecto `2`) del bloque siguiente — o solo una línea cuando `avoidWidows` está desactivado —, el título se empuja hacia adelante para viajar con su texto.
- **Títulos consecutivos.** Cuando aparecen varios títulos en secuencia (por ejemplo, un h2 seguido de un h3 seguido de un párrafo), todo el grupo debe permanecer junto. Ninguno de los títulos puede quedar suelto al final de una columna sin el contenido que introducen.
- **Listas introducidas con dos puntos.** Cuando un párrafo termina con dos puntos que introducen directamente una lista, la línea que lleva los dos puntos debe quedarse con el inicio de la lista. Lo gestiona `bodyText.keepColonWithList` (por defecto `true`): si colocar el párrafo no dejaría sitio para que empiece el primer ítem de la lista (todo él cuando las reglas de huérfanas y viudas de las listas lo mantienen entero; una línea con `bodyText.colonListRoom: 'line'`, como hasta postext 1.4), la última línea con los dos puntos (o el párrafo entero, si es de una sola línea) se mueve adelante junto con la lista. Siempre que esta regla tenga que empujar el párrafo completo y justo antes haya una secuencia de títulos en la columna, esos títulos también se arrastran hacia adelante para no violar silenciosamente `keepWithNext`; la única excepción es cuando la columna contiene solo el título (o títulos) que un movimiento anterior ya adelantó, en cuyo caso el motor deja el párrafo junto al título y acepta la separación más leve entre dos puntos y lista para evitar un bucle.
- **Figura con su pie.** Una figura y su pie de figura son una unidad inseparable. Siempre se mueven juntos.

Cuando se detecta una violación de cohesión, el motor empuja todo el grupo a la siguiente columna o página. La columna que deja termina entonces corta, en las líneas que habría ocupado el grupo. Rellenarla es tarea del [Equilibrado de columnas](#equilibrado-de-columnas).

Estas correcciones son invisibles cuando se hacen bien (un lector nunca debería notarlas). Pero su *ausencia* salta a la vista de cualquiera que lea con atención: esa línea incómoda al inicio de una columna, esos huecos desiguales donde el motor renunció a intentar ajustar el texto. Las editoriales profesionales tienen guías de estilo enteras dedicadas a prevenir exactamente estos problemas. Postext los automatiza.

Las rondas 3 a 8 se ejecutan una tras otra dentro de una misma composición (`buildDocumentBalanced`). Las rondas 1 y 2 quedan fuera: una ronda de índice o de números de nota es una composición entera, con sus propias rondas 3 a 8. No hay un límite para la composición en su conjunto, solo estos.

**Cada repetición es una colocación completa.** Una indicación no parchea el árbol de la pasada anterior. La pasada coloca el documento de nuevo con la indicación en vigor, de modo que un encabezado con dos líneas más encima, o una banda cortada seis líneas más arriba, pasa por las mismas reglas de corte y de cohesión que todo lo demás. El controlador comprueba después el resultado: un tope de banda cuya caja no cayó en el corte se agranda o se descarta, y una pasada de equilibrado que no mejoró un segmento se descarta para ese segmento. Lo que devuelve el controlador está hecho de páginas que colocó una pasada: una pasada entera o, tras el equilibrado de columnas, las páginas de cada segmento tomadas de la mejor pasada que tuvo ese segmento.

**Lo que dice el documento.** `doc.iterationCount` cuenta las pasadas de colocación que hay detrás de la composición devuelta: la primera y las de las rondas de topes de banda, de equilibrado y de bandas de cierre. Las pasadas de pies laterales y de página de la cita no entran en la cuenta, ni tampoco las composiciones anteriores de una ronda de índice o de números de nota; a `BuildDocumentOptions.onPass` se le llama en cada pasada, con lo que ha tardado. `doc.converged` habla solo del equilibrado de columnas. Es `true` cuando todos los segmentos terminaron sin ninguna línea vacía en sus columnas equilibrables o sin ninguna palanca que proponer, y `false` cuando un segmento se detuvo en una pasada que no lo mejoró, o agotó sus intentos, con un hueco todavía abierto. Con el equilibrado desactivado es `true`. Un documento con `converged: false` está completo: contiene la mejor composición que encontró el controlador, y alguna de sus columnas termina corta.

### Equilibrado de columnas

- **Se ejecuta:** como rondas 6 y 8 del controlador (activado por defecto; `headings.balancing.enabled: false` lo desactiva, y está desactivado por defecto en texto vertical y en una retícula de caracteres, ver [Configuración → Equilibrado de columnas](/es/docs/configuration-text#equilibrado-de-columnas))
- **Entrada:** La mejor composición hasta el momento y las líneas de rejilla vacías al pie de cada columna equilibrable (`collectColumnGaps`, en `pipeline/columnBalancing.ts`)
- **Acción:** Proponer palancas que rellenan cada columna corta en su sitio, ejecutar la pasada de colocación con ellas y conservar el resultado para un segmento cuando su puntuación de huecos ha bajado
- **Salida:** Columnas que terminan en la última línea de rejilla de la página, con cada palanca anotada en el bloque al que se aplicó (`VDTBlock.balancing`)

Las columnas desequilibradas se notan inmediatamente. Las reglas de corte las dejan constantemente: un encabezado que pasó a la columna siguiente para quedarse con su texto, un párrafo que pasó entero para evitar una viuda, una figura que no cabía. Una columna que se detiene dos líneas por encima de la de al lado parece inacabada — como si la maquetación se hubiera rendido a mitad de camino.

Ningún bloque cambia de columna para arreglarlo. Un salto de columna está ligado al elemento que no cabía: el bloque que abre la columna siguiente era demasiado alto para el sitio que quedaba, y lo sigue siendo para un sitio menor. Así que una columna corta se puede rellenar desde dentro, como mucho en lo que mide su hueco, y nada cruza a la columna siguiente. El ajuste es local, que es lo que hace a mano un maquetista: añadir una línea de espacio allí donde el ojo la acepta. Una columna es equilibrable cuando el contenido siguió más allá de ella hacia una columna posterior de la misma página o, en el caso de la última columna de una página, cuando la página fluye hacia la siguiente. La última página de un capítulo puede terminar corta; su banda de cierre la corta a nivel un tope de cierre (ver [Etapa 3](#etapa-3-colocación-en-páginas-y-columnas)).

Para cada hueco, las palancas se proponen en orden de prioridad editorial, el mismo orden en que las da [Configuración → Equilibrado de columnas](/es/docs/configuration-text#equilibrado-de-columnas):

1. **Una caja que cierra la columna** toma como espacio superior el sitio que queda bajo su pie, de modo que su pie cae en la última línea de rejilla de la página, a nivel con la última línea de la columna contigua. Se anota como `trailingCallout`.
2. **Una imagen con zona segura** (`Resource.safeArea`), colocada en línea en la columna o flotada en su cabeza o su pie y solo sobre ella, crece en líneas enteras de rejilla, recortada dentro de su zona segura. Una imagen más alta no deja ningún hueco en la página, así que actúa antes de añadir ningún espacio. Se anota como `flexFigure`.
3. **Los encabezados** toman líneas enteras de rejilla por encima, de una en una y por turnos, empezando por el encabezado más importante (el de nivel más bajo), que se lleva así la mayor parte. Un encabezado al principio de una columna no toma ninguna, de modo que las columnas siguen empezando en la parte superior de la página. Un encabezado solo toma así sus primeras líneas antes de probar las palancas siguientes, y las demás, hasta su máximo, cuando estas ya no pueden dar más. Se anota como `heading`.
4. **Los finales de lista** toman una línea de rejilla donde termina una lista. Se anota como `listEnd`.
5. **Bajo fórmulas, cajas y figuras** va una línea de rejilla: bajo una fórmula destacada o una caja tras la que sigue el texto (`afterDisplay`), y entre una figura o tabla que encabeza la columna y el texto de debajo (`afterFloat`).
6. **Los párrafos corridos** son el último recurso. Los párrafos de la columna, los más largos primero, se recomponen cada uno con una línea más (el `\looseness=+1` de TeX, a través de la opción `looseness` del divisor de Knuth-Plass), y la composición más larga solo se acepta mientras todas las líneas se mantienen dentro de `bodyText.maxWordSpacing`. Cuando el espaciado entre palabras no basta para ganar la línea, el párrafo puede tomar además el menor tracking positivo que lo consiga, hasta un máximo. Se anota como `looseParagraph`.

Los máximos, los interruptores y las excepciones (una retícula de caracteres, las páginas de cierre, un flotado sobre varias columnas) son claves de `headings.balancing`. La página de Configuración las enumera y se mantiene al día con ellas; esta página no las repite.

Una propuesta se comprueba colocándola. La pasada que aplica las palancas es una colocación completa, y de vez en cuando una palanca sí acaba moviendo contenido a través de un salto de columna: un párrafo partido cuya cabeza ya no cabe, un flotado que perdió su hueco. Las páginas posteriores a ese punto fluyen de otra manera y se abren huecos en otros sitios. El controlador lo ve en la puntuación, descarta la pasada para ese segmento y veta las palancas recién aplicadas en la primera columna que cambió, de modo que la propuesta siguiente conserva las palancas que funcionaron y deja fuera la que provocó la cascada.

**El equilibrado converge por segmentos.** Las páginas entre saltos explícitos — la apertura de un capítulo, un `:::pagebreak` — se maquetan con independencia unas de otras: nada fluye a través de un salto así, de modo que una palanca de equilibrado dentro de una tanda de páginas nunca puede mover una línea de otra. El bucle de equilibrado de columnas juzga por eso cada *segmento* por separado. Su puntuación de huecos es el número de líneas de rejilla vacías al pie de sus columnas equilibrables. Una pasada sigue colocando el documento entero, pero cada segmento conserva o rechaza su parte de las palancas según su propia puntuación de huecos, veta sus propias cascadas, se estanca por su cuenta y gasta su propio presupuesto de intentos; un segmento cuyo reintento empeoró recupera sus páginas de la mejor pasada que tenía mientras los demás siguen avanzando. Un libro de treinta capítulos se equilibra así exactamente igual que sus capítulos uno a uno — el PDF del libro completo y el PDF del capítulo suelto son idénticos — en lugar de que una cascada en cualquier parte cueste una pasada a todas las páginas del libro.

Los límites son una válvula de seguridad. Algunas columnas no se pueden cerrar: una que solo contiene párrafos cortos no tiene palanca de la que tirar, y una cuyas palancas empujan cada una un bloque al otro lado del salto de columna no tiene ninguna que se pueda conservar. El motor se queda con la mejor composición que encontró y deja corta esa columna. Como las palancas quedan anotadas en los bloques, una hoja de pruebas o un test puede enumerar las columnas que nada cerró (ver [Configuración → Qué palanca actuó](/es/docs/configuration-text#qué-palanca-actuó)).


## Sistema de ritmo vertical

Coge un libro bien compuesto y ponlo a contraluz. Las líneas de la página izquierda se alinean con las de la derecha. La línea base de la línea 5 en la columna 1 está exactamente en la misma posición vertical que la línea base de la línea 5 en la columna 2. Eso es el ritmo vertical, y es una de las primeras cosas que un ojo entrenado comprueba al evaluar la calidad tipográfica. También es uno de los diferenciadores clave de Postext.

Cuando ambas columnas contienen solo texto de cuerpo al mismo tamaño, la alineación es trivial — cada línea tiene la misma altura, así que las líneas base se alinean naturalmente. El desafío aparece en el momento en que una columna contiene un encabezado con un tamaño de fuente mayor, una imagen con una altura arbitraria en píxeles, o espaciado extra alrededor de una cita. Estos elementos "rompen" la rejilla: el contenido por debajo se desplaza una cantidad que no es múltiplo del incremento de línea base, y de repente las líneas base en esa columna se desincronizan con la columna adyacente. La armonía visual desaparece.

El objetivo es recuperarla: las líneas base del texto de cuerpo en columnas adyacentes deben alinearse horizontalmente, incluso cuando encabezados, imágenes u otros elementos con alturas no estándar aparezcan en una columna pero no en la otra.

### Rejilla de líneas base

Todo se ancla a un solo número. El documento define un valor `baselineGrid` derivado del line-height del texto de cuerpo — por ejemplo, texto de cuerpo a `16px` con un `line-height` de `1.5` produce una rejilla de líneas base de `24px`. Cada línea base del texto de cuerpo debería caer en un múltiplo de este valor. Ese es el contrato.

### Elementos que rompen la rejilla

Algunos elementos rompen la rejilla porque su altura no es múltiplo de `baselineGrid`:

- **Encabezados:** tamaño de fuente mayor, line-height diferente
- **Imágenes:** altura arbitraria en píxeles
- **Tablas:** altura variable
- **Citas:** pueden usar tamaño de fuente o padding diferente
- **Áreas de notas al pie:** las notas al pie de una columna y su filete; el área de texto de la columna termina encima

La rejilla se mantiene en la colocación, bloque a bloque. Ninguna pasada posterior recorre las columnas buscando desviaciones. Las líneas de cuerpo miden una línea de rejilla, así que una tirada de texto de cuerpo que empieza en la rejilla sigue en ella. Cuando la pasada de colocación ha compuesto un bloque que puede salirse de la rejilla, redondea la altura usada en la columna hasta la siguiente línea de rejilla antes de que empiece el bloque siguiente. Los bloques que se ajustan así son:

- el último encabezado de una serie de encabezados (los encabezados consecutivos se siguen unos a otros sin ajuste, y el último realinea el texto que viene detrás);
- el último ítem de una lista, sea cual sea el espaciado entre ítems;
- una fórmula destacada;
- un aviso, un listado de código, y una figura o tabla embebida en línea;
- el último párrafo de un contenedor `:::paragraphs` y un poema `:::verse`, que tienen su propio interlineado.

El espacio inferior del bloque (`marginBottom`) se cuenta antes del redondeo, de modo que el margen es un mínimo y la rejilla decide el resto. En la figura, la columna 1 tiene un encabezado de 36px de alto sobre una rejilla de 24px, sin margen inferior. Su pie cae 12px más allá de una línea de rejilla, el ajuste añade 12px, y la siguiente línea de cuerpo empieza en la rejilla, a nivel con la línea que tiene al lado en la columna 2. Con un `marginBottom` de 16px el pie estaría en 52px, y el ajuste lo redondearía a 72px.

Las bandas de flotados mantienen la rejilla a su manera, descrita en la [Etapa 4](#etapa-4-colocación-de-recursos): una banda superior se redondea hacia arriba a líneas enteras de rejilla, y un flotado inferior se ancla de forma que la última línea base de su pie quede sobre la rejilla. El equilibrado de columnas añade su espacio en líneas enteras de rejilla, así que también la mantiene.

Nada compara una columna con otra. Todas las columnas empiezan en la rejilla y todos los ajustes vuelven a ella, de modo que las líneas de columnas adyacentes, y de páginas enfrentadas, coinciden sin una segunda pasada.

**Renunciar al ajuste.** `snapToGrid: false` conserva en su lugar el espacio exacto bajo un bloque. Se puede fijar en `headings` (para todos los niveles, para un nivel o para un estilo de encabezado), en un estilo de párrafo, en un estilo de aviso y en `codeStyle`. El texto que sigue a un bloque así puede quedar fuera de la rejilla hasta el siguiente bloque que se ajusta. El texto de dentro de un aviso sigue el interlineado propio de la caja y no tiene rejilla.


## Interfaz del backend

Hay exactamente una fuente de verdad para la medición de texto — el módulo de medida sobre las métricas de fuente del canvas de Pretext — y todos los backends renderizan a partir del mismo VDT terminado que esta produjo.

Es una decisión deliberada, y existe por una razón crítica: **la forma en que mides el texto debe coincidir exactamente con la forma en que lo renderizas.** Imagina que la medición usara métricas de fuente del canvas, pero un backend de renderizado usara una librería PDF con tablas de kerning ligeramente diferentes. La composición no coincidiría con la salida. Líneas que el motor midió como ajustadas en 320px podrían desbordarse o quedarse cortas al renderizar. Cada píxel de desviación es una mentira. Al medir una sola vez y renderizar siempre desde la geometría resultante, los backends no pueden discrepar: los saltos de línea, las alturas de columna y la colocación de recursos quedan congelados en el VDT antes de que ningún backend se ejecute.

Por eso el backend de PDF, por ejemplo, no vuelve a medir el texto: consume un VDT terminado y traduce sus coordenadas en píxeles a puntos PDF. Las métricas del canvas son la fuente de verdad; PDF es un transporte. Los usuarios de `renderToPdf` (del paquete `postext-pdf`) pasan el mismo VDT que pasarían a `renderToCanvas` o `renderToHtml`, y se garantiza que las tres salidas coinciden.

### Superficie de API

Los backends son funciones planas sobre `VDTDocument`, no una jerarquía de clases. No existe una interfaz `PostextBackend` — solo los puntos de entrada de renderizado de cada salida y los helpers que necesita:

```typescript
// Canvas (desde 'postext')
renderToCanvas(doc, options?): HTMLCanvasElement[];     // un canvas por página
renderPage(page, doc, options?): HTMLCanvasElement;     // una sola página
renderPageToCanvas(page, doc, canvas, options?): void;  // dibuja en un canvas existente

// Registro de imágenes de recurso del canvas — imágenes decodificadas por fileId
registerResourceImage(fileId, image, options?): void;   // options: { vector?, singleInk? }
unregisterResourceImage(fileId): void;
clearResourceImages(): void;

// HTML (desde 'postext')
renderToHtml(doc, options?): string;
renderToHtmlIndexed(doc, options?): HtmlRenderIndex;    // desglose por página / por bloque

// PDF (desde 'postext-pdf')
renderToPdf(doc, options): Promise<Uint8Array>;

// EPUB (desde 'postext-epub'), los capítulos de un libro en orden
renderToEpub(docs, options): Promise<Uint8Array>;
```

Como los payloads binarios de los recursos viven fuera de banda, cada backend resuelve los `fileId` a su manera. El backend de canvas mantiene un registro de `CanvasImageSource` decodificados — la aplicación anfitriona registra cada bitmap o SVG una vez con `registerResourceImage(fileId, image)` y el renderizador lo consulta al dibujar. El backend HTML acepta un resolutor `resourceImageUrl(fileId)` en sus opciones y emite etiquetas `<img>` apuntando a las URLs (object URLs, data URIs, rutas de CDN) que devuelva el anfitrión. El backend PDF recibe un proveedor `resourceBytes` y embebe los bytes reales; el escritor EPUB también recibe uno y guarda cada imagen una sola vez como archivo del libro. Un recurso de vídeo se dibuja como su portada, un bitmap más; el backend HTML recibe además un resolutor `resourceVideoUrl(fileId)` para los archivos de vídeo que reproduce, y el escritor EPUB guarda esos archivos en `media/`. El backend PDF dibuja la marca de reproducción y el código QR como trazados vectoriales sobre la portada y, con `video.linkPoster` activado, le pone encima una anotación de enlace URI que abre `video.link`; en un PDF etiquetado el enlace se une a la `Figure` de la portada, cuyo texto alternativo empieza por el nombre del tipo (*Vídeo: …*). Los recursos de tabla no necesitan nada de esto — su modelo viaja en línea, y todos los backends dibujan las celdas a partir de la geometría de tabla del VDT.

`renderToHtmlIndexed` merece una nota: además de la cadena HTML completa, devuelve un desglose por página y por bloque (`HtmlRenderIndex`) para que quien lo llama pueda comparar con un render anterior y parchear solo los subárboles del DOM cuyo HTML cambió de verdad — la ruta de previsualización en vivo del sandbox.

Fuera del navegador, la [línea de comandos](/es/docs/command-line) ejecuta el mismo pipeline con Skia en el papel del canvas del navegador, de modo que un libro se parte en las mismas páginas en un terminal, en un script o en un servidor de compilación.


## Estrategia de rendimiento

La diferencia entre una herramienta lenta y una que parece mágica es un factor de 10x. Una composición de 500ms significa que el usuario ve un tirón visible cada vez que cambia una palabra. Una composición de 50ms se siente instantánea — como si el documento siempre hubiera estado ahí. Ese factor no se puede parchear después. Hay que diseñarlo desde el primer día.

Piensa a qué se enfrenta el motor: miles de bloques de texto repartidos en cientos de páginas, compuestos de nuevo en cada edición, y varias veces seguidas cuando la composición necesita sus rondas. Los motores de juegos se enfrentan a la misma clase de problema — procesar miles de objetos (geometría, física, iluminación, IA) 60 veces por segundo — y lo resuelven no repitiendo el trabajo que ya han hecho. Postext aplica esa idea a lo que más le cuesta, que es medir texto.

### Principios

1. **Computación en memoria.** El VDT completo cabe en memoria. No se lee el DOM durante la
   composición. El DOM solo se toca al final, durante el renderizado.

2. **Pasadas enteras sobre medidas en caché.** Una repetición de la pasada de colocación no busca
   qué ha cambiado: coloca el documento de nuevo desde el primer bloque. Es asumible porque medir,
   que es la parte cara, se cachea por párrafo (principio 5). Una pasada que no cambia nada del
   texto, las fuentes o el ancho de un párrafo lee sus líneas de la caché.

3. **Rondas acotadas.** Cada tipo de repetición tiene un límite fijo (ver
   [El controlador de pasadas](#el-controlador-de-pasadas)), y el equilibrado de columnas tiene
   uno por documento además de uno por segmento, de modo que un libro de muchos capítulos no puede
   gastar pasadas sin fin. El coste de una composición se puede medir pasada a pasada:
   `BuildDocumentOptions.onPass` informa de cada pasada y de lo que ha tardado.

4. **Velocidad de Pretext.** La medición de texto a 300–600x la velocidad del DOM significa que el
   motor puede permitirse re-medir texto de forma especulativa (probando diferentes anchos de columna,
   puntos de separación silábica, ajustes de tracking) sin bloquear el hilo principal.

5. **Caché de medición por capas.** El módulo de medida (`packages/postext/src/measure/`) mantiene
   una caché de medición explícita cuya clave incluye el texto, las fuentes, el ancho y cada opción
   que afecta a la composición, por encima de la caché propia de `prepare()` de Pretext y de una
   caché cruda de anchuras de texto. Re-medir un párrafo sin cambios cuesta una consulta a un mapa.
   Cuando cambian las caras de una familia, el motor descarta las anchuras de esa familia y la
   caché de Pretext, y una caché de medición descarta los bloques compuestos en ella en su
   siguiente consulta (lleva la generación con la que se llenó), de modo que las anchuras de
   glifo son correctas tras la carga de fuentes sin que el anfitrión tenga que llamar a nada;
   `clearMeasurementCache()` descarta todas las familias.

6. **División de líneas en la ruta caliente.** La gestión de nodos activos de Knuth-Plass se
   reescribió por velocidad: el conjunto activo se compacta in situ a medida que los nodos se
   retiran, y los candidatos se deduplican por (línea, clase de *fitness*), de modo que solo
   sobrevive el nodo de menores demerits por clave. Los resultados algorítmicos son idénticos —
   los mismos conjuntos de cortes, calculados más rápido.

7. **Builds fuera del hilo principal.** El punto de entrada `postext/worker` ejecuta el pipeline
   completo dentro de un Web Worker dedicado. El hilo principal publica `{ content, config }` y un
   `AbortSignal`; el worker registra las fuentes (transferidas como `ArrayBuffer`s), ejecuta las
   pasadas de colocación y publica de vuelta el `VDTDocument` terminado. Una nueva llamada a
   `build()` cancela cooperativamente la anterior — el worker ejecuta `buildDocumentAsync`, que
   consulta un hook de cancelación una vez por bloque y entre pasadas y lanza
   `BuildCancelledError`, de modo que un usuario escribiendo en un editor
   nunca espera por una composición ya obsoleta. El worker también mantiene su propia caché persistente
   de medición y una caché de rasterización de matemáticas con clave por contenido, de modo que los
   objetos `MathRender` clonados estructuralmente sobreviven a las reconstrucciones sin re-rasterizarse.

8. **VDT de doble acceso.** El árbol (`pages > columns > blocks`) proporciona acceso jerárquico para
   el trabajo que va página por página o columna por columna (el equilibrado de columnas mide el
   hueco al pie de cada columna). Un array plano paralelo `blocks[]` da acceso directo a todos los
   bloques estén donde estén (la ronda de números de nota lee de él la llamada que imprimió cada
   nota). Ambas vistas referencian los mismos objetos bloque (no hay duplicación, solo dos formas
   de recorrer los mismos datos).

### Volver a componer

No hay un punto de entrada incremental: ninguna llamada toma un VDT terminado y lo actualiza. Cuando cambia el contenido o la configuración (una pulsación de tecla, otro tamaño de página), el anfitrión llama otra vez a `buildDocument` y recibe un documento nuevo.

Lo que pasa de una composición a la siguiente es la medición. Crea una `MeasurementCache` una sola vez con `createMeasurementCache()` y pásala como tercer argumento en cada llamada a `buildDocument`. Un párrafo cuyo texto, fuentes, ancho y opciones de corte no han cambiado se lee de ella, de modo que un editor que recompone el documento en cada pulsación solo mide el párrafo en el que se está escribiendo. Un cambio de tamaño de página o de número de columnas cambia los anchos, y esos párrafos se miden de nuevo; los resultados de `prepare()` de Pretext siguen valiendo, porque dependen de la fuente y del texto y no del ancho, así que solo se ejecuta la aritmética barata de `layout()`. El análisis del markdown también se memoiza.

Para un editor en vivo, `createLayoutWorker` (desde `postext/worker`) hace todo esto fuera del hilo principal: el worker tiene una caché de medición que dura lo que dura él, y un `build()` más reciente cancela el que está en curso. Ver [Configuración → Caché de medidas](/es/docs/configuration-programmatic-usage#caché-de-medidas) y [Ejecutar la composición en un Web Worker](/es/docs/configuration-programmatic-usage#ejecutar-la-composición-en-un-web-worker).

### Benchmarks

En `packages/postext/src/__bench__/` hay dos benchmarks. `pnpm test` se los salta; `pnpm bench`, lanzado en `packages/postext`, los ejecuta. `chapter.bench.test.ts` compone un capítulo del tamaño de los de un libro de texto (cuarenta secciones de encabezados, párrafos y listas) cinco veces contra una caché de medición vacía y cinco contra una ya llena, e informa de las dos medianas y del número de pasadas. `cjkChapter.bench.test.ts` compone el capítulo 1 de 红楼梦 y cuenta los caracteres enviados a `measureText`, para mantener el compositor CJK en un coste lineal respecto a la longitud del párrafo.

```typescript
const warmCache = createMeasurementCache();

const warm: number[] = [];
for (let i = 0; i < ROUNDS; i++) warm.push(time(() => buildDocument({ markdown }, config, warmCache)));

// [bench] chapter: … pages, … passes (… ms), iterationCount=…; cold median … ms, warm median … ms (5 rounds)
```

Una salvedad, en aras de la honestidad: en Node no hay canvas, así que los dos benchmarks simulan la medición de texto y sus tiempos absolutos no son los del navegador. La proporción entre caché vacía y caché llena y el número de pasadas sí lo son, y una regresión en cualquiera de los dos se ve aquí antes que en el sandbox. El benchmark del capítulo reporta números y no rompe el build; el chino comprueba que los caracteres medidos se quedan por debajo de tres veces la longitud del párrafo más largo. Ninguno se ejecuta en CI: las regresiones se detectan comparando los números entre ejecuciones cuando cambia una ruta caliente (como se hizo con la reescritura de nodos activos de Knuth-Plass). El rendimiento es una funcionalidad, no una esperanza — pero hoy la garantía es medición y revisión, no un pipeline que falla.

## Fuera de alcance

Cada uno de estos límites es una decisión consciente — el motor es lo bastante complejo por sí
solo, y asumir responsabilidades que pertenecen a otro lugar sería la forma más rápida de no
terminar nunca.

- **Edición WYSIWYG.** Postext es un motor de composición, no un editor. Contenido entra, geometría sale. Construir una superficie de edición interactiva — gestión de cursor, selección, deshacer/rehacer, manejo de entrada — es un problema completamente diferente. Postext puede servir como backend de renderizado para un editor, pero no proporciona capacidades de edición por sí mismo.
- **Wrapper de CSS column-count.** Postext reemplaza la composición multicolumna de CSS; no la envuelve. Calcula geometría posicionada precisa desde cero, porque el algoritmo de columnas del navegador carece de control sobre la colocación de recursos, la prevención de viudas/huérfanas y las reglas tipográficas entre columnas. Esas son precisamente la razón de ser de Postext.
- **Gestión de breakpoints responsivos.** Postext calcula la composición a un tamaño de página dado. El consumidor decide cuándo re-componer (al redimensionar la ventana, al cambiar la orientación). Postext no gestiona breakpoints, media queries ni decisiones de diseño responsivo. Eso es cosa tuya.
- **Edición colaborativa en tiempo real.** Postext es un cálculo de composición sin estado — contenido entra, geometría sale — no un sistema de documentos colaborativo con resolución de conflictos, transformaciones operacionales ni consciencia multiusuario.
- **Archivos de fuente.** El paquete `postext` carga las fuentes, pero no las trae consigo. `prepareFonts` carga antes de la primera composición todas las caras que piden una configuración y su texto, y una cara que el conjunto de fuentes no pudo dar figura entre los avisos del documento como `fontFallback`. Los archivos los pone quien integra el motor: una regla `@font-face` en la página, o una función `resolve` que dice dónde está cada cara. Ver [Configuración → Cargar las fuentes antes de componer](/es/docs/configuration-programmatic-usage#cargar-las-fuentes-antes-de-componer).

### Dónde viven los tipos del VDT

Los tipos del VDT (`VDTDocument`, `VDTPage`, `VDTColumn`, `VDTBlock`, `VDTLine`, `VDTLineSegment`, `ResolvedResourceBlock`, `VDTResourceTableLayout`, `BoundingBox` y compañía) viven en `packages/postext/src/vdt.ts`, junto a los helpers de fábrica (`createVDTDocument`, `createVDTPage`, `createVDTBlock`, …) y `computePageTextExtent`. No existe un módulo separado de interfaz de backend — los puntos de entrada de renderizado descritos en [Interfaz del backend](#interfaz-del-backend) se exportan directamente desde `postext` (canvas, HTML), `postext-pdf` (PDF) y `postext-epub` (EPUB).
