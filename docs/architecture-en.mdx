# Postext Architecture

If you have ever worked with React, you already understand the core trick. React builds a virtual DOM in memory, diffs it, and only then touches the real browser DOM. Postext does the same thing — but instead of UI components, it builds a tree of **pages, columns, text blocks, and bounding boxes**. The entire geometry of a multi-page, multi-column document, computed before a single pixel is rendered. Every paragraph, heading, image, footnote, and pull quote placed at exact coordinates, respecting centuries-old typographic rules that CSS simply cannot express.

All of this is possible thanks to [`@chenglou/pretext`](https://github.com/chenglou/pretext), a DOM-free text measurement library that is 300–600x faster than browser layout reflow. For the story behind the project (a decade of failed attempts, the bottleneck that blocked them all, and the library that finally removed it), see the [Introduction](/en/docs/introduction).

## The Core Idea

Picture a 74-page, two-column document. A company annual report, maybe, or a densely illustrated textbook. You hand it to Postext, and the engine constructs the entire layout in memory — every page, every column, every paragraph's exact position and pixel dimensions. Want to know what sits on page 72, column 2? The answer is already there. No rendering required. The engine has already decided where to break every paragraph, where to place every image, how to avoid widows and orphans, and how to align baselines across adjacent columns.

Now here is why that matters so much.

Typographic rules are deeply, maddeningly interdependent. You fix a widow on page 5 — a lonely last line stranded at the bottom of a column — by pulling it back into the previous column. Great. But that change shortens page 5's column, which shifts content forward, which might just create an orphan on page 6. A single first line pushed onto a new column, disconnected from its paragraph. To even *detect* that you have created a new problem, you need the entire document layout available for inspection. And to *fix* it without creating yet another problem somewhere else, you need to be able to adjust, re-measure, and re-check the whole thing.

That is the "compute everything first, render later" philosophy. It is not a performance trick. It is the only way to apply the dozens of interconnected typographic rules that professional typesetters have used for centuries.

## System Architecture

**Here is the journey your content takes through the engine:**

1. The **parser** reads your enriched markdown and turns it into a flat list of typed content blocks: content and structure, no positions yet
2. A **placement pass** walks that list once and builds the VDT. It measures each block through Pretext at the width of the column the block is about to enter, places text, floats and boxes into pages and columns, and applies the break and keep rules as it goes
3. The **driver** (`buildDocument`) runs the pass again when a decision needs the result of a whole layout: a table of contents that prints page numbers, a page-span box that has to cut the columns above it level, a column that ended short. Each re-run takes hints from the pass before it, and each kind of re-run has its own limit
4. The **final VDT** is the complete layout geometry: every element knows its page number, column assignment, position, and bounding box. The document is fully "typeset" before any rendering happens
5. A **backend** walks the finished VDT and renders it to the target format: a rasterized canvas bitmap, a DOM tree of positioned HTML elements, a PDF document with embedded fonts, or an EPUB. The same VDT feeds all four; picking a backend is purely an output decision


## Input Layer

### Content Model

The content model is a philosophy as much as it is a data structure. You describe *what* to say, not *how* to lay it out. The engine makes the layout decisions.

<Illustration name="ContentModel" data='{"title": "Content model: markdown, resources, notes", "desc": "The input to Postext separates markdown (reading order and semantic structure) from resources (bitmaps, SVGs, tables) and notes. The engine resolves inline :ref references and ::resource embeds by ID and produces the VDT.", "caption": "Markdown owns the reading order; resources own the visual data.", "contentTitle": "PostextContent", "markdown": "markdown", "markdownSub": "reading order + :ref / ::resource by id", "resources": "resources[]", "resourcesSub": "bitmaps, SVGs, tables", "notes": "metadata", "notesSub": "title, author, dates", "resolveMarker": "resolved by id: :ref{id=…}, ::resource{id=…}", "engineLabel": "engine", "vdtLabel": "VDT"}' />

```typescript
// packages/postext/src/types.ts

interface PostextContent {
  markdown: string;            // enriched markdown with :ref / ::resource markers
  metadata?: DocumentMetadata; // title, subtitle, author, publishDate, …
  resources?: Resource[];      // bitmaps, SVGs, tables, videos — referenced by id
  notes?: PostextNote[];       // not read: footnotes are written as [^id] in the markdown
}

interface Resource {
  id: string;                  // stable id, referenced by inline :refs
  typeId: string;              // ResourceType this resource belongs to ('figure', 'table', …)
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  caption?: string;            // the type prefix + number are computed, not written here
  altText?: string;
  createdAt: number;
  updatedAt: number;
  // Exactly one kind-specific payload:
  bitmap?: { fileId: string; format: string; width: number; height: number };
  svg?: { fileId: string; width?: number; height?: number };
  table?: { model: TableModel };
  video?: ResourceVideo;       // where it plays from; drawn on the page as its poster
  placement?: ResourcePlacement; // optional per-resource float override
  safeArea?: ResourceSafeArea;  // bitmap / svg: { x, y, width, height } in fractions, the part always shown
}
```

**Resources** carry the visual data: captions, alt text, and a kind-specific payload. Binary payloads (bitmaps, SVGs) live *out-of-band* — the resource only stores a `fileId`, and the renderer resolves it at draw time (the sandbox keeps the bytes in IndexedDB). Table resources are the exception: their `TableModel` (a grid of cells with spans and alignment) travels inline, because it is structured data, not bytes.
**Notes** are written in the markdown: a `[^id]` marker where the note is cited and a `[^id]:` definition, a paragraph of its own anywhere in the chapter. The engine numbers the notes in the order they are first cited and sets each one at the foot of the column that holds the line citing it, under a short rule, or after the chapter's last block with `footnotes.placement: 'chapterEnd'` (see [Footnotes](/en/docs/document-format#footnotes) and [Configuration → Footnotes](/en/docs/configuration-notes-references#footnotes)). The content model still accepts a `notes` array, but no stage of the pipeline reads it.

This separation is an opinionated design choice, and it matters more than it looks. The markdown owns the *reading order* and *semantic structure* — what comes first, what is a heading, where a footnote is cited and what it says. The resources array owns the *visual data* — image dimensions, caption text, table cells. By keeping them apart, the same markdown can be laid out in completely different ways just by changing the configuration. A two-column academic layout and a single-column blog post can share the same source content. And the engine can make placement decisions — like deferring an image to the next column because it does not fit here — without ever touching your source content.

```typescript
// Example: a simple article with a referenced figure
const content: PostextContent = {
  markdown: `
# The Art of Typography

The history of typography begins with Gutenberg's
movable type, shown in :ref{id="printing-press"}.
His invention transformed the production of books.

The technique spread rapidly across Europe, reaching
Italy by 1465 and France by 1470.
  `,
  resources: [
    {
      id: 'printing-press',
      typeId: 'figure',
      kind: 'bitmap',
      caption: 'A reconstruction of the original press.',
      altText: "Reconstruction of Gutenberg's printing press",
      createdAt: 1765379100000,
      updatedAt: 1765379100000,
      bitmap: { fileId: 'press-photo', format: 'jpeg', width: 600, height: 400 },
    },
  ],
};
```

Resources are connected to the prose by id, and **referencing one is enough to incorporate it**. The inline `:ref{id="printing-press"}` does two jobs at once: it renders the resource's computed number in the running text ("Fig. 1"), and — at the first reference in reading order — it *floats* the resource onto the page, reserving a band at the top or bottom near that reference, exactly as a print typesetter would. You never place the figure a second time. For the occasional resource that must sit at an exact point in the flow, `::resource{id="…"}` on its own line is an optional block embed: it only renders inline when the resource's resolved `placement.position` is `'here'` (which opts it out of floating); for a floated resource it is treated as just another reference. The author never has to think about placement. The engine does.

### Parsing Strategy

Parsing is deliberately the simplest step in the pipeline. Markdown goes in and comes out as a flat list of typed content blocks (`ContentBlock`, in `packages/postext/src/parse/`): a heading, a paragraph with its inline spans, a list item, a directive. The result is memoized (`parseMarkdownMemo`), so the passes of one build parse once, and so does a later build of the same text. Resource references are resolved against the `resources[]` array by ID at the start of each placement pass. Footnote definitions (paragraphs that open with `[^id]:`) leave the flow there too and are kept by id for the markers that cite them; the `notes[]` array is not read.

Think of it as a manifest: "there is a heading, then a paragraph with 200 words, then a figure reference, then another paragraph." No measurements. No positioning. No layout decisions at all. A `VDTBlock` exists only once the placement pass has measured a block and given it a place.


## Virtual Document Tree (VDT)

Imagine you asked a professional typesetter to lay out an entire book, but instead of handing you printed pages, they handed you a spreadsheet. Every row is an element. Every cell is a precise measurement: "the heading is at (40, 30), the first paragraph starts at (40, 78) and is 144px tall, the image goes at the top of column 2 on page 3..." That spreadsheet is the VDT.

The Virtual Document Tree is the central data structure of Postext — a mutable, in-place tree representing every page, column, block, and line, each carrying a precise bounding box. Once `buildDocument` returns, the VDT *is* the answer. You can query "what is on page 72, column 2?" without rendering a single pixel.

### Why Mutable

This is the same approach used in game engine render pipelines, where a shared mutable world state is updated by successive systems on a tight loop. And for the same reason.

A placement pass fills the tree in place. It opens a page, appends columns to it, takes a block's height off the `availableHeight` of the column the block lands in, and closes the columns of a band where a page-span box cuts it. A book has thousands of blocks, and an immutable tree (like React's virtual DOM) would allocate a new object for every one of those steps. So the nodes are plain objects and the pass writes to them.

A finished pass is not patched. When `buildDocument` needs another attempt (a band cap, a balancing lever), it runs the pass again from the content and gets a new tree. The tree of the pass before is left as it was, so the driver can compare the two, keep the better one, or take some pages from each. The measurement cache makes the re-run affordable: a paragraph whose text, fonts and width did not change is read from the cache instead of being measured again.

### Type Definitions

The shapes below are **simplified for exposition** — the real definitions in `packages/postext/src/vdt.ts` carry many more rendering-oriented fields (font strings, colours, list bullets, math renders, design slots). The structure is what matters here:

```typescript
// Simplified — see packages/postext/src/vdt.ts for the full definitions

// The root of the Virtual Document Tree
interface VDTDocument {
  pages: VDTPage[];
  blocks: VDTBlock[];         // flat view of the same block objects
  config: ResolvedConfig;     // every sub-config resolved to non-optional
  baselineGrid: number;       // baseline increment in px (e.g. 24 for 16px/1.5)
  converged: boolean;         // every balancing segment ended flush or out of levers
  iterationCount: number;     // placement passes behind this layout (see The Pass Driver)
  metadata: DocumentMetadata;
}

// A physical page
interface VDTPage {
  index: number;
  width: number;
  height: number;
  columns: VDTColumn[];
  header?: VDTDesignSlot;     // running header (design slot)
  footer?: VDTDesignSlot;     // running footer / page number
  floats?: VDTBlock[];        // resource bands floated to the top/bottom of this page
  pageNumberValue: number;
  pageLabel: string;          // rendered label ('iv', '7', 'A', …)
}

// A column within a page
interface VDTColumn {
  index: number;
  bbox: BoundingBox;          // position within the page
  blocks: VDTBlock[];
  availableHeight: number;    // remaining vertical space
  baselineOffset: number;     // current baseline y-position
  band?: number;              // column band (0 unless a span block split the page)
  kind?: 'text' | 'span' | 'side'; // 'span' = full-width column holding a page-span block,
                              // 'side' = the float-only side column of a one-and-a-half layout
}

// A content block (paragraph, heading, resource, etc.)
type VDTBlockType =
  | 'paragraph' | 'heading' | 'resource' | 'blockquote'
  | 'listItem' | 'footnoteRef' | 'mathDisplay' | 'callout' | 'code';

interface VDTBlock {
  id: string;
  type: VDTBlockType;
  bbox: BoundingBox;
  lines: VDTLine[];           // for text blocks: the measured lines
  resourceBlock?: ResolvedResourceBlock; // for resource blocks
  pageIndex: number;
  columnIndex: number;
  dirty: boolean;             // not used: cleared when the block is placed, read by nothing
  snappedToGrid: boolean;     // the flow went back to the baseline grid under this block
  balancing?: VDTBalancing;   // the column-balancing levers applied to this block
}

// A measured line of text
interface VDTLine {
  text: string;
  bbox: BoundingBox;            // natural width: a justified line is painted to its block's right edge
  baseline: number;             // y-position of the text baseline
  hyphenated: boolean;          // line ends inside a word, or after a closed dash ("say—" | "that’s")
  hardHyphen?: boolean;         // …after a hyphen the text carries ("well-" | "known"): nothing added
  repeatedHyphen?: boolean;     // opens with that hyphen repeated ("vencer-" | "-se"), not in the source
  segments?: VDTLineSegment[];  // word/space/math runs for justified rendering
  isLastLine?: boolean;         // last line of its paragraph
  justifiedSpaceRatio?: number; // width every space is painted at ÷ the regular face's space
  justifiedSpaceLimitRatio?: number; // the spacing the limits bound, when the line's own spaces are not regular (lineWordSpacing reads both)
  sourceStart?: number;         // markdown source map (char offsets; a line opening with `\$` starts at the backslash)
  sourceEnd?: number;
  plainStart?: number;          // plain-text source map
  plainEnd?: number;
}

// A measured, placement-ready resource embed (bitmap / svg / table / video)
interface ResolvedResourceBlock {
  resource: Resource;
  kind: 'bitmap' | 'svg' | 'table' | 'video';
  number: string;             // computed number, e.g. "1.7"
  captionPrefix: string;      // e.g. "Figure"
  bodyRect: BoundingBox;      // the image / table area
  bodySource?: ResourceSafeArea; // the part of the picture shown in bodyRect when cropped to its safe area
  bodyFlex?: { shrink: number; grow: number; delta: number }; // px the body can still shrink / grow, px applied
  fileId?: string;            // out-of-band binary (bitmap / svg)
  captionLines: VDTLine[];    // measured caption, prefix + number included
  table?: VDTResourceTableLayout; // cell geometry for table resources
}

// Bounding box — all values in px, relative to page origin
interface BoundingBox {
  x: number;
  y: number;
  width: number;
  height: number;
}
```

A few of these fields deserve a note:

- **`isLastLine`** drives justified rendering: final lines render ragged even when the paragraph is justified — except *overfull* final lines, whose inter-word spaces compress to fit the measure (TeX glue-setting semantics).
- **`sourceStart`/`sourceEnd` and `plainStart`/`plainEnd`** are source maps from each line back to the original markdown and to the block's plain text — they power cursor and selection sync in editor integrations.
- **`VDTResourceTableLayout`** (with its `VDTResourceTableCell` entries) carries the full laid-out geometry of a table resource: column x-edges, row y-edges, and per-cell rects with their measured content lines, so every backend draws the same table.
- **`dirty` and `snappedToGrid`** are written when a block is placed and read by no stage and no backend. `dirty` starts `true` on a new block and is set to `false` as the block is placed; the engine does not track changes on the tree, it runs the placement pass again (see [The Pass Driver](#the-pass-driver)). `snappedToGrid` is `true` on the first part of a text block that the flow returns to the grid after (see [Vertical Rhythm System](#vertical-rhythm-system)).
- **`balancing`** says which column-balancing levers moved or stretched the block; a block the balancing left alone has none (see [Column Balancing](#column-balancing)).
- **`computePageTextExtent(page)`** is a small public helper that returns the vertical extent actually covered by text on a page (including float captions). Debug overlays use it so the baseline-grid lines span only real text, not empty page bottom.


## Layout Pipeline

One placement pass, run as many times as the layout needs. That is the entire layout pipeline.

The pass (`placeDocumentPass`, in `packages/postext/src/pipeline/build.ts`) walks the content from the first block to the last. For each block it does everything it takes to set it: measure it at the width of the column it is about to enter, see whether it fits, split it or move it on under the break and keep rules, offer the floats it cites a slot, and put the flow back on the baseline grid (see [Vertical Rhythm System](#vertical-rhythm-system)). Floats, widows and the grid have no pass of their own: they are settled as each block lands.

Some decisions cannot be taken inside one walk, because they depend on where the walk ends up: the page numbers a table of contents prints, the height at which a page-span box cuts the columns above it, the lines a short column still needs. For those, `buildDocument` runs the pass again with *hints* taken from the result of the pass before. The five stages below follow a block through the pass; [The Pass Driver](#the-pass-driver) and [Column Balancing](#column-balancing) cover the re-runs.

### Stage 1: Content Structuring

- **Input:** Raw `PostextContent`
- **Action:** Parse the markdown into content blocks, resolve resource references against `resources[]` by ID, take the footnote definitions (`[^id]:`) out of the flow and number their markers in citation order, number the headings, and plan the floats: which resources float, and after which block (`notes[]` is not read)
- **Output:** A flat list of content blocks (typed and content-filled, but with no page or column assignment) and the float plan
- **Runs:** at the start of every placement pass. The parse is read from its memo after the first pass; the rest is worked out again

### Stage 2: Text Measurement

- **Input:** A content block with text, and the width of the column it is about to enter
- **Action:** Measure the block's lines at that width through the dedicated **measure module** (`packages/postext/src/measure/`), which layers hyphenation, justification, rich inline runs, and Knuth-Plass line breaking on top of Pretext. The result is the block's `VDTLine[]` and its total height
- **Key detail:** Measurement is cached. `cachedMeasureBlock` / `cachedMeasureRichBlock` (in `measure/cache.ts`) key on the text, fonts, width, and every layout-affecting option, so re-measuring an unchanged paragraph is a map lookup
- **Output:** The block's lines, with precise pixel dimensions
- **Runs:** as the walk reaches the block, not ahead of it, because the width depends on where the block lands: a column beside a side column, the lines beside a wrapped figure, the sub-columns of a `:::columns` group. A block that moves on to a column of another width is measured again at that width

The module splits cleanly by responsibility: `plain.ts` measures plain runs, `rich.ts` measures mixed bold/italic/math spans, `font.ts` builds font strings and owns cache lifecycle, and `canvas.ts` wraps the raw canvas text-width primitives. One lifecycle detail matters in practice: glyph widths measured against a fallback font must not outlive the real font's arrival. `canvas.ts` keeps its widths per font string and a measurement generation; `evictFontFamilies` (called when a build finds that a family's faces changed, by `watchFonts`, `prepareFonts` and `loadBundleFonts`) drops the widths of those families and clears Pretext's cache, and a `MeasurementCache` filled under an older generation drops its blocks in those families at its next lookup. `clearMeasurementCache()` does the same for every family. The faces themselves are loaded before layout by `fonts/prepare.ts` (`prepareFonts`), and `fonts/faces.ts` reads back the faces a laid-out document used, for the `fontFallback` warnings.

Chinese, Japanese and Korean paragraphs take another route through the same module. A paragraph with more CJK characters than word spaces goes to the **CJK composer** (`cjkCompose.ts`). It cuts the text into units (a character, a run of Latin text, a two-em dash or ellipsis, an atomic box such as a chip or a note marker), measures each unit once, and fills the lines first-fit under the line-start and line-end rules of `cjkClasses.ts`: a line takes in a mark that may not open the next line by giving up punctuation blank (`cjkPunctuation.ts`) before it carries a character down. A justified line is then spread between its characters. The output is ordinary `VDTLine`s whose segments carry what the renderers need to paint them exactly as measured: `tracking` (pixels after each character, already in the segment's width), `inkOffset` for a mark that gave up blank, `hangs`, the Han–Latin spaces as `autospace` segments, and the marks, ruby readings and warichu rows of Chinese annotations. In a Japanese document the same composer follows JLReq: the kinsoku classes of the Japanese levels are read from the edge characters of each unit at break time, the punctuation blanks are compressed and given back in the JLReq order, furigana are laid out by `rubyJis.ts` (1:2:1 spacing, overhang onto kana, jukugo words), and kanbun marks widen the unit of their character. The cost is linear in the paragraph's length: chapter 1 of 紅樓夢 (6,949 characters) is set by measuring 1,298 characters, each distinct character once, where measuring prefixes of the paragraph took 636,948. See [Chinese layout](/en/docs/chinese-layout).

Underneath, this is where Pretext earns its keep. The `prepare()` call is the expensive part — it analyzes the text using the canvas font engine and caches the result. But the `layout()` call? Pure arithmetic, nearly free. That split is everything. Once text is prepared, the engine can break it again at negligible cost: at another width, for a paragraph that continues in a narrower column, or one line longer, for a paragraph that column balancing loosens. Prepare once, layout as many times as you need.

```typescript
// Simplified: how the measure module uses pretext internally
const prepared = prepare(paragraphText, '16px/1.5 Inter');
const { height } = layout(prepared, columnWidth, 24); // 24px line-height
// => "This paragraph is 168px tall at 320px column width — that's 7 lines."
```

### Stage 3: Page and Column Placement

- **Input:** A measured block
- **Action:** Set the block in the current column. Create `VDTPage` and `VDTColumn` nodes as the flow needs them. Track `availableHeight` per column. When a block does not fit, split it (Stage 5) or advance to the next column or page
- **Strategy:** Greedy first-fit placement. Column and page breaks follow the simplest valid assignment
- **Output:** The block has `pageIndex`, `columnIndex`, and `bbox` assigned

This is the moment the VDT becomes a real document. Before this stage a block is an entry in a flat list, with no address. Placement assigns each one to a page and column, like pouring water into a grid of containers: fill column 1 until it overflows, spill into column 2, when the page is full start a new one.

Before any content blocks land on a page, the pass reserves space for structural elements — running headers and footers (laid out as design slots from `config.header` / `config.footer`) and any float bands already pending for the freshly opened page. These reservations reduce the `availableHeight` of each column, so when content blocks start flowing in, the engine already knows exactly how much room is available.

**Column bands and span columns.** `page.columns` is a flat array in reading order, but a page is not always a single row of columns. In a multi-column layout a page-span inline block cuts the page into stacked *bands*. Four things count as one: a `:::callout` whose style or fence sets `span: 'page'`, a `:::columns{span="page"}` group in the running text, an inline `::resource` whose placement resolves to `{ position: 'here', span: 'page' }`, and a comic strip set across the page where it is written (`:::strip{span=page}`). The last three are wrapped in a frameless page-span box before placement (`pipeline/flowColumns.ts`, `pipeline/spanEmbeds.ts`), so one mechanism sets all four. At the cut, the text columns of the current band are closed at the cut line (their height clamped, `availableHeight` zero), the block gets its own full-width column with `kind: 'span'`, and a fresh band of text columns (`band + 1`, same x and width, same bottom as the band it replaces) is appended below it. Columns are only ever appended, so `columnIndex` keeps addressing `page.columns[i]`, and renderers need no special drawing: each column clips to its own bbox (widened by `columnClipRect` — 2pt for glyph ink plus however far the column's design overlays, such as a heading tab or a callout badge, hang past its sides, and however far a heading's design reaches above its top; its foot stays the edge — the same rectangle in the canvas and PDF backends), and the column rule is drawn per band between adjacent text columns, starting under the band a page-span heading holds at the head of the page (`columnRuleSegments`), in the page's own rule when a styled section sets one (`VDTPage.columnRule`, read through `pageColumnRule`). Column balancing ignores span columns, side columns and zero-height bands. A span block cuts directly where the band is level (page top, right after an opener heading, another span block or a top float band); arriving in an uneven band it proposes a *band cap* instead (`packages/postext/src/pipeline/bandCaps.ts`) — the columns of the band that opens with a given content block are shortened to `ceil(Σ used / N / grid)` lines — and `buildDocument` re-runs the placement pass with the cap (growing it one line at a time when the capped band overflows, up to `MAX_BAND_CAP_RETRIES` = 3 times, then dropping it, so the block falls back to the top of the next page), so the text fills the shortened columns under every placement rule, ends level at the cut, and the closed columns keep whatever slack remains as `availableHeight` for balancing to absorb. The same mechanism levels the *closing* band of a chapter and of the document (`headings.balancing.trailing`): a chapter opener, a `:::part`, a chapter-closing `placement: 'fixed'` callout or the end of the document reached with the current band's columns uneven proposes a `kind: 'trailing'` cap, keyed by the boundary block; because a cap is keyed by the block that opens its band — and that block moves whenever an earlier page absorbs extra balancing lines — trailing caps are resolved *after* column balancing has settled, with the balancing hints frozen, and a short polish round then lets the levers fill what the cut left short. `placement: 'fixed'` callouts leave the flow: the box is anchored to the page content area / trim box / bleed box, the text columns it covers give up that zone (cut from the bottom or the top like a float band, moving to the next page on a conflict), and frame plus children go to `page.floats`.

**Vertical pages.** With `layout.writingMode: 'vertical-rl'` the pass lays out a horizontal page turned a quarter turn clockwise. On such a page the content area, columns, blocks, lines, floats and footnote areas are in **flow coordinates**, and `VDTPage.flow` carries the rotation that takes them to the sheet: a flow point (x, y) lands at (page width − y, x). Nothing downstream needs to know: breaking, floats, keep-together rules and balancing work in the flow frame as on any page, a column of the flow is a tier on the sheet, and each backend applies the rotation when it paints (`flowToPage` and `pageToFlow` map points both ways). Running heads, folios, crop marks and the background stay in sheet coordinates. Figures and tables are laid out as upright blocks turned back inside the frame, and characters that stand upright are turned back one by one at paint time.

- **Action:** Float each referenced resource into the first free slot after its first reference — the bottom of the referencing column, the top / bottom of the next empty column, or a band of the next page (`packages/postext/src/pipeline/floatPlacement.ts` plans the floats, `pipeline/floatSlots.ts` enumerates and measures the slots; the placement pass reserves the bands as it walks)
- **Runs:** as soon as the block holding the first reference has landed, inside the same walk; the text placed after that flows past the band
- **Placement resolution:** Per resource, the engine resolves `resource.placement` → the type's `resourceType.defaultPlacement` → the built-in default `{ position: 'auto', span: 'column' }`

`ResourcePlacement` has more fields than these two: `rotate`, `width`, `align`, `columns`, `captionSide`, `shrink`, `minScale`, `captionMeasure`, `wrap`, `wrapGap` and `citingPage`. [Configuration → Resource types](/en/docs/configuration-resources#resource-types) and [Document format › Placement](/en/docs/document-format#placement) say what each one does.

- **Deferred placement:** A float that fits in no slot of the current page waits for the next page the flow opens and, at a chapter boundary, is drained onto pages opened ahead of the boundary. A picture keeps its size unless `placement.shrink` (or the document's `layout.floatShrink`) lets it scale down to the room a slot has. A table too tall for a fresh page is cut between rows and continues on the following pages with its header rows repeated (`tableStyle.overflow: 'split'`, the default)
- **Output:** Resources positioned in page bands (`page.floats`), with the affected columns' heights reduced so text flows around the bands

Resource placement is where things get interesting, because floats do not just occupy space — they reshape the space around them. Once the block holding a reference has landed, the pending float is offered the free slots of the current page after it — the bottom of that column, then the top and bottom of the next empty column (a page-span float: the page bottom, when every column still has room); what fits nowhere waits for the next page, where pending floats claim their bands before any text flows in. The columns shrink to fit between the bands, the text flows through the narrowed columns uninterrupted, and the reader sees the figure near (but not exactly at) the point where it is mentioned. This is standard practice in professional typesetting; books do it constantly.

**Placement rules.** Beyond the placement dispatch, floats follow strict editorial constraints:

- **After-reference rule.** A float lands in the first free slot *after* its first reference in the text, never before it. The reader encounters the reference first, then sees the resource. If a float does not fit, it defers forward to a later slot or page, never backward.
- **Reference order within a sequence.** Pending floats are offered each slot in first-reference order, and one that fits nowhere holds up the ones behind it in its numbering sequence: table 3 never lands after table 4, figure 12 never before figure 11. The sequences do not hold each other up — a waiting table lets a later figure through. So that a long table need not wait for a fresh page, one offered the head of an empty column is cut to that column and continues in the next slot (the column beside it, or the next page's bands), with its header rows repeated.
- **Chapter barrier.** Floats never escape their chapter. At a chapter opener (a heading level with `breakBefore` or `span: 'page'`), a `:::part`, a callout style with `floatBarrier: true` and the end of the document, every pending float is placed first — in the page's free slots, then on pages opened ahead of the boundary (each force-placing at least one float) — before the boundary's own page break. Before opening such a page, a figure or table still pending is offered the current page's free slots once more whatever its `position` — a head-of-page float cited on a chapter's closing page takes the foot of that page, under the balanced columns, rather than a page of its own (floated callouts keep their placement). A `:::pagebreak` sends pending floats to the page that follows it, after any parity padding.
- **Minimum text room.** On a freshly opened page a band is only reserved if at least 3 body lines of text still fit in the affected columns — with one exception: an oversized float may be force-placed into a band that is still all-text, so a dominating figure cannot stall the queue forever. A slot on the current page must fit in the column's remaining height; the 3-line rule applies there only next to another float band.
- **Breathing room.** One body-line-height gap separates a band from the text beside it.
- **Baseline-grid alignment.** Top bands are rounded *up* to a multiple of the baseline grid (growing the gap below the float), so every displaced line still lands on the grid. Bottom floats are anchored so the caption's last baseline sits on the grid — the caption shares its baseline with the last text line of the neighbouring columns, and pages end at the same height across columns and facing pages.

**Typed first-reference numbering.** Resources are *not* numbered in the markdown. `pipeline/resourceNumbering.ts` assigns each resource its number the first time it is referenced in reading order, using the resource's `ResourceType`: the `numberingTemplate` combines the per-type counter `{n}` with the heading counters `{h1}`..`{h6}` in effect at the reference (e.g. `'{h1}.{n}'` → "1.7"), `resetOn` controls when the counter restarts (`'never'` or at any heading level), and `counterFormat` picks decimal, roman, or alphabetic numerals. The built-in *Figure* and *Table* types come from `defaultResourceTypes(locale)`, localized to the document's language. Because numbering follows first-reference order, inserting a new figure mid-document renumbers everything after it automatically — no source edits required.

### Stage 5: Breaks and Keep Rules

This is the stage that separates a layout engine from a text dumper. It enforces the editorial quality rules that professional typesetters have applied by hand for centuries — and that naive text rendering completely ignores.

Three mechanisms share the work, each acting where the information it needs exists: a **runt penalty** inside the line breaker, a **scored split** where a paragraph meets the end of a column, and **structural keep-together rules** between blocks.

#### Widows, orphans and runts

**Widows and orphans** are the most visible signs of amateur typesetting:

- A **widow** is a single line of a paragraph left alone at the bottom of a column. The paragraph
  continues in the next column, but that lone line looks stranded (as if the column ended
  prematurely).
- An **orphan** is a single line of a paragraph stranded at the top of a column. The bulk of the
  paragraph is in the previous column, but one line spilled over (it looks disconnected from its
  context).
- A **runt** is a paragraph whose last line is a single short word (or two) — visually far too short to feel like a proper line of text. Less structurally severe than a widow, but just as jarring to a careful reader.

**Runts are settled in the line breaker.** A runt belongs to the paragraph alone: its last line is as short wherever the paragraph lands. So it is the one rule of the three that the Knuth-Plass line breaker sees. When a set of breaks would end the paragraph on a line whose content is narrower than `runtMinCharacters × normalSpaceWidth` (default `runtMinCharacters` 20: twenty word spaces of content, about 8 to 12 letters), the breaker adds `runtPenalty` (default 1000) to that line's badness inside the squared demerit formula, so it competes on the same scale as line badness (which saturates at 10000) rather than being dwarfed by it. The penalty sits alongside the usual demerits (badness, hyphenation cost, fitness-class mismatch) in a single global optimisation, and the breaker almost always finds a set of breaks without a runt. Where it does not, `bodyText.tightenRunts` sets the paragraph one line shorter when its word spaces, and a little negative tracking, can take up the difference. The measure module hands the penalty to the breaker (`measure/plain.ts`, `measure/rich.ts`) and `knuthPlass/breakpoints.ts` applies it.

**Widows and orphans are settled at the column end.** The line breaker breaks a paragraph for a width. It does not know where on the page the paragraph will sit, so it cannot know which of its lines will close a column. The placement pass does. When the lines of a paragraph do not all fit in what is left of the column, `chooseParagraphSplit` (in `pipeline/orphanWidow.ts`) tries every split `k` of the lines already broken, from 0 to the number that fit: `k` lines stay and the rest open the next column. Each candidate is scored:

- `slackWeight · slack²` for the lines it leaves empty at the foot of the column, `slack` being the lines that fit minus `k` (default `slackWeight` 10);
- plus `widowPenalty` (default 1000) when it leaves fewer than `widowMinLines` lines at the bottom of the column;
- plus `orphanPenalty` (default 1000) when it carries fewer than `orphanMinLines` lines to the top of the next one.

The split with the lowest score wins, and `k = 0` moves the paragraph whole. The rules are soft, and the numbers say how soft: a penalty of 1000 is the slack cost of ten empty lines (10 · 10² = 1000), so with the defaults a split that honours both rules wins whenever it leaves fewer than ten lines of the column empty. Past that, a widow or an orphan can be the cheaper choice. The split chooses among the lines the line breaker already made; it does not break the paragraph again. List items go through the same split via `avoidOrphansInLists` and `avoidWidowsInLists`, and take the runt penalty via `avoidRuntsInLists` (all `true` by default).

All of this is tunable on `BodyTextConfig` — see [Configuration → Orphans, widows, runts, and keep-together rules](/en/docs/configuration-text#orphans-widows-runts-and-keep-together-rules). Setting any `*Penalty` to `0` effectively disables that rule.

#### Structural keep-together rules

Some groupings are bigger than a single paragraph — they span adjacent blocks and cannot be addressed by line-breaking alone. The placement pass enforces these as each block lands, moving entire groups forward when they would otherwise split across a column or page break:

- **Heading with its first paragraph.** A heading must never appear at the bottom of a column if the paragraph it introduces would start in the next column. Enforced by `headings.keepWithNext` (default `true`): if there is not room for the heading *plus* the body's widow minimum (`bodyText.widowMinLines`, default `2`) of the next block — or just one line when `avoidWidows` is off — the heading is pushed forward to travel with its text.
- **Consecutive headings.** When multiple headings appear in sequence (e.g., an h2 followed by an h3 followed by a paragraph), the entire group must stay together. None of the headings can be left stranded at the bottom of a column without the content they introduce.
- **Colon-introduced lists.** When a paragraph ends with a colon that directly introduces a list, the colon-bearing line must stay with the start of the list. Enforced by `bodyText.keepColonWithList` (default `true`): if placing the paragraph would leave no room for the first list item to start (all of it when the orphan and widow rules for lists keep it whole; one line with `bodyText.colonListRoom: 'line'`, as up to postext 1.4), the colon-bearing last line (or the whole paragraph, if it is one line) moves forward together with the list. Whenever this rule has to push the whole paragraph and a run of headings immediately precedes it in the column, those headings are pulled forward too so `keepWithNext` is not silently violated; the only exception is when the column contains just the heading(s) that an earlier move already brought forward, in which case the engine keeps the paragraph with the heading and accepts the softer colon/list separation to avoid looping.
- **Figure with its caption.** A figure and its caption are an inseparable unit. They always move together.

When a keep-together violation is detected, the engine pushes the entire group to the next column or page. The column it left then ends short, by the lines the group would have taken. Filling it is the job of [Column Balancing](#column-balancing).

These corrections are invisible when done well (a reader should never notice them). But their *absence* is immediately obvious to anyone who reads carefully: that awkward single line at the top of a column, those uneven gaps where the engine gave up trying to make text fit. Professional publishers have entire style guides about preventing exactly these problems. Postext automates them.

Rounds 3 to 8 run one after another inside one build (`buildDocumentBalanced`). Rounds 1 and 2 are outside it: a contents round or a note-number round is a whole build, with its own rounds 3 to 8. There is no limit on a build as a whole, only these.

**Every re-run is a full placement.** A hint does not patch the tree of the pass before. The pass places the document again with the hint in force, so a heading with two more lines above it, or a band cut six lines up, goes through the same break and keep rules as everything else. The driver then checks the result: a band cap whose box did not land on the cut is grown or dropped, and a balancing pass that did not improve a segment is discarded for that segment. What the driver returns is made of pages that a pass placed: the whole of one pass, or, after column balancing, the pages of each segment from the best pass that segment had.

**What the document reports.** `doc.iterationCount` counts the placement passes behind the returned layout: the first one and those of the band-cap, balancing and closing-band rounds. The side-caption and citing-page passes are not in it, and neither are the earlier builds of a contents or note-number round; `BuildDocumentOptions.onPass` is called for every pass, with its wall time. `doc.converged` is about column balancing alone. It is `true` when every segment ended with no empty line in its balanceable columns or with no lever left to propose, and `false` when a segment stopped on a pass that did not improve it, or ran out of attempts, with a gap still open. With balancing off it is `true`. A document with `converged: false` is complete: it holds the best layout the driver found, and some column of it ends short.

### Column Balancing

- **Runs:** as rounds 6 and 8 of the driver (on by default; `headings.balancing.enabled: false` turns it off, and it is off by default in vertical text and on a character grid, see [Configuration → Column balancing](/en/docs/configuration-text#column-balancing))
- **Input:** The best layout so far and the empty grid lines at the foot of each balanceable column (`collectColumnGaps`, in `pipeline/columnBalancing.ts`)
- **Action:** Propose levers that fill each short column in place, run the placement pass with them, and keep the result for a segment when its gap score fell
- **Output:** Columns that end on the last grid line of the page, with every lever recorded on the block it was applied to (`VDTBlock.balancing`)

You notice unbalanced columns immediately. Break rules leave them all the time: a heading moved on to stay with its text, a paragraph moved whole to avoid a widow, a figure that did not fit. A column that stops two lines above the one beside it looks unfinished — like the layout gave up halfway through.

No block changes column to fix that. A column break is bound to the element that did not fit: the block that opens the next column was too tall for the room that was left, and it is still too tall for a smaller room. So a short column can be filled from inside, by at most its gap, and nothing crosses into the next column. The adjustment is local, which is what a compositor does by hand: add a line of space where the eye accepts it. A column is balanceable when content flowed past it into a later column of the same page, or, for the last column of a page, when the page flows on into the next one. The last page of a chapter may end short; its closing band is cut level by a trailing cap instead (see [Stage 3](#stage-3-page-and-column-placement)).

For each gap the levers are proposed in editorial priority order, the same order [Configuration → Column balancing](/en/docs/configuration-text#column-balancing) gives them:

1. **A box closing the column** takes the room under its foot as space above it, so its foot lands on the last grid line of the page, level with the last line of the column beside it. Recorded as `trailingCallout`.
2. **A picture with a safe area** (`Resource.safeArea`), set inline in the column or floated at its head or foot over that column alone, grows by whole grid lines, cropped within its safe area. A taller picture leaves no hole on the page, so this runs before any space is added. Recorded as `flexFigure`.
3. **Headings** take whole grid lines above them, one line at a time in turn, the most important heading (the lowest level) first, so it gets the largest share. A heading at the very top of a column takes none, so columns keep starting at the page top. A heading takes only its first lines this way before the levers below are tried, and more, up to its cap, when those have nothing left to give. Recorded as `heading`.
4. **List ends** take a grid line where a list ends. Recorded as `listEnd`.
5. **Formulas, boxes and top floats** take a grid line under them: under a display formula or a callout box the text resumes after (`afterDisplay`), and between a figure or table at the head of the column and the text under it (`afterFloat`).
6. **Loose paragraphs** are the last resort. Paragraphs of the column, the longest first, are each broken one line longer (TeX's `\looseness=+1`, through the `looseness` option of the Knuth-Plass breaker), and the longer setting is accepted only while every line stays within `bodyText.maxWordSpacing`. When word spacing alone cannot gain the line, the paragraph may also take the smallest positive tracking that does, under a cap. Recorded as `looseParagraph`.

The caps, the switches and the exceptions (a character grid, the closing pages, a float over several columns) are keys of `headings.balancing`. The Configuration page lists them and is kept up to date with them; this page does not repeat them.

A proposal is checked by placing it. The pass that applies the levers is a full placement, and now and then a lever does move content across a column break after all: a split paragraph whose head no longer fits, a float that lost its slot. The pages after that point flow differently and gaps open elsewhere. The driver sees it in the score, discards the pass for that segment, and blacklists the levers newly applied in the first column that changed, so the next proposal keeps the levers that worked and leaves out the one that cascaded.

**Balancing converges per segment.** The pages between explicit breaks — a chapter opener, a `:::pagebreak` — are laid out independently of one another: nothing flows across such a break, so a balancing lever inside one run of pages can never move a line of another. The column-balancing loop therefore judges every such *segment* on its own. Its gap score is the number of empty grid lines at the foot of its balanceable columns. A pass still places the whole document, but each segment keeps or rejects its share of the levers by its own gap score, blacklists its own cascades, plateaus on its own and spends its own budget of attempts; a segment whose retry regressed gets its pages back from the best pass it had while the others move on. A book of thirty chapters thus balances exactly as its chapters would one by one — the whole-book PDF and the single-chapter PDF of the same chapter are identical — instead of one cascade anywhere costing every page of the book a pass.

The limits are a safety valve. Some columns cannot be closed: one that holds only short paragraphs has no lever to pull, and one whose levers each push a block across the column break has none that can be kept. The engine keeps the best layout it found and leaves that column short. Because the levers are recorded on the blocks, a proof sheet or a test can list the columns that nothing closed (see [Configuration → Which lever fired](/en/docs/configuration-text#which-lever-fired)).


## Vertical Rhythm System

Hold a well-typeset book up to the light. The lines on the left page align with the lines on the right. The baseline of line 5 in column 1 sits at exactly the same vertical position as the baseline of line 5 in column 2. That is vertical rhythm, and it is one of the first things a trained eye checks when evaluating typographic quality. It is also one of the key differentiators of Postext.

When both columns contain only body text at the same size, alignment is trivial — every line is the same height, so baselines naturally match. The challenge arrives the moment one column contains a heading with a larger font size, an image with an arbitrary pixel height, or extra spacing around a block quote. These elements "break" the grid: the content below them shifts by an amount that is not a multiple of the baseline increment, and suddenly the baselines in that column fall out of sync with the adjacent column. The visual harmony is gone.

The goal is to get it back: baselines of body text in adjacent columns must align horizontally, even when headings, images, or other non-standard-height elements appear in one column but not the other.

### Baseline Grid

Everything anchors to a single number. The document defines a `baselineGrid` value derived from the body text's line height — for example, body text set at `16px` with a `line-height` of `1.5` produces a baseline grid of `24px`. Every body text baseline should fall on a multiple of this value. That is the contract.

### Grid-Breaking Elements

Some elements inevitably break the grid because their height is not a multiple of `baselineGrid`:

- **Headings** (larger font size, different line-height)
- **Images** (arbitrary pixel height)
- **Tables** (variable height)
- **Block quotes** (may use different font size or padding)
- **Footnote areas** (the notes at a column's foot and their rule: the column's text area ends above them)

The grid is kept at placement, block by block. No later pass walks the columns looking for drift. Body lines are one grid line tall, so a run of body text that starts on the grid stays on it. When the placement pass has set a block that can leave the grid, it rounds the height used in the column up to the next grid line before the next block starts. The blocks that snap this way are:

- the last heading of a run of headings (consecutive headings follow each other without a snap, and the last one realigns the text after them);
- the last item of a list, whatever the spacing between items;
- a display formula;
- a callout box, a code listing, and a figure or table embedded inline;
- the last paragraph of a `:::paragraphs` container and a `:::verse` poem, whose leading is their own.

The block's space below (`marginBottom`) is counted before the rounding, so the margin is a minimum and the grid decides the rest. In the figure, column 1 holds a heading 36px tall on a 24px grid, with no margin below it. Its foot falls 12px past a grid line, the snap adds 12px, and the next body line starts on the grid, level with the line beside it in column 2. With a `marginBottom` of 16px the foot would be at 52px, and the snap would round that up to 72px.

Float bands keep the grid in their own way, described under [Stage 4](#stage-4-resource-placement): a top band is rounded up to whole grid lines, and a bottom float is anchored so the last baseline of its caption sits on the grid. Column balancing adds its space in whole grid lines, so it keeps the grid as well.

Nothing compares one column with another. Every column starts on the grid and every snap returns to it, so the lines of adjacent columns, and of facing pages, meet without a second pass.

**Opting out.** `snapToGrid: false` keeps the exact space under a block instead. It can be set on `headings` (for every level, for one level or for one heading style), on a paragraph style, on a callout style and on `codeStyle`. The text after such a block may sit off the grid until the next block that snaps. The text inside a callout box follows the box's own leading and has no grid.


## Backend Interface

There is exactly one source of truth for text measurement — the measure module over Pretext's canvas font metrics — and every backend renders from the same finished VDT it produced.

That is a deliberate choice, and it exists for a critical reason: **the way you measure text must exactly match the way you render it.** Imagine measurement used canvas font metrics, but a rendering backend used a PDF library with slightly different kerning tables. The layout would not match the output. Lines that the engine measured as fitting in 320px might overflow or underflow when rendered. Every pixel of drift is a lie. By measuring once and rendering everywhere from the resulting geometry, the backends cannot disagree: line breaks, column heights, and resource placement are frozen into the VDT before any backend runs.

This is why the PDF backend, for example, does not re-measure text: it consumes a finished VDT and translates its pixel coordinates into PDF points. The canvas metrics are the source of truth; PDF is a transport. Users of `renderToPdf` (from the `postext-pdf` package) pass the same VDT they would hand to `renderToCanvas` or `renderToHtml`, and the three outputs are guaranteed to agree.

### API Surface

The backends are plain functions over `VDTDocument`, not a class hierarchy. There is no `PostextBackend` interface — just the rendering entry points of each output and the helpers it needs:

```typescript
// Canvas (from 'postext')
renderToCanvas(doc, options?): HTMLCanvasElement[];     // one canvas per page
renderPage(page, doc, options?): HTMLCanvasElement;     // a single page
renderPageToCanvas(page, doc, canvas, options?): void;  // draw into an existing canvas

// Canvas resource-image registry — decoded images keyed by Resource fileId
registerResourceImage(fileId, image, options?): void;   // options: { vector?, singleInk? }
unregisterResourceImage(fileId): void;
clearResourceImages(): void;

// HTML (from 'postext')
renderToHtml(doc, options?): string;
renderToHtmlIndexed(doc, options?): HtmlRenderIndex;    // per-page / per-block breakdown

// PDF (from 'postext-pdf')
renderToPdf(doc, options): Promise<Uint8Array>;

// EPUB (from 'postext-epub'), a book's chapters in order
renderToEpub(docs, options): Promise<Uint8Array>;
```

Because binary resource payloads live out-of-band, each backend resolves `fileId`s its own way. The canvas backend keeps a registry of decoded `CanvasImageSource`s — the host app registers each bitmap or SVG once with `registerResourceImage(fileId, image)` and the renderer looks it up at draw time. The HTML backend takes a `resourceImageUrl(fileId)` resolver in its options and emits `<img>` tags pointing at whatever URLs (object URLs, data URIs, CDN paths) the host returns. The PDF backend receives a `resourceBytes` provider and embeds the actual bytes; the EPUB writer takes one too and stores each picture once as a file of the book. A video resource is drawn as its poster, a bitmap like any other; the HTML backend also takes a `resourceVideoUrl(fileId)` resolver for the video files it plays, and the EPUB writer stores those files under `media/`. The PDF backend draws the play mark and the QR code as vector paths over the poster and, when `video.linkPoster` is on, puts a URI link annotation over it that opens `video.link`; in a tagged PDF the link joins the poster's `Figure`, whose alternate text starts with the type's name (*Video: …*). Table resources need none of this — their model is inline, and every backend draws the cells from the VDT's table geometry.

`renderToHtmlIndexed` deserves a note: besides the full HTML string, it returns a per-page, per-block breakdown (`HtmlRenderIndex`) so callers can diff against a previous render and patch only the DOM subtrees whose HTML actually changed — the live-preview path in the sandbox.

## Performance Strategy

The difference between a sluggish tool and a magical one is about 10x. A 500ms layout means the user sees a visible stutter every time they change a word. A 50ms layout feels instantaneous — like the document was always there. That factor cannot be patched in later. It has to be designed in from day one.

Consider what the engine is up against: thousands of text blocks across hundreds of pages, laid out again on every edit, and several times over when the layout needs its rounds. Game engines face the same class of problem — processing thousands of objects (geometry, physics, lighting, AI) 60 times per second — and they solve it by not repeating work they have already done. Postext applies that to what costs it most, which is measuring text.

### Principles

1. **In-memory computation.** The entire VDT fits in memory. No DOM reads during layout. The DOM
   is only touched at the very end, during rendering.

2. **Whole passes over cached measurements.** A re-run of the placement pass does not look for
   what changed: it places the document again from the first block. That is affordable because
   measuring, the expensive part, is cached per paragraph (principle 5). A pass that changes
   nothing about a paragraph's text, fonts or width reads its lines from the cache.

3. **Bounded rounds.** Every kind of re-run has a fixed limit (see
   [The Pass Driver](#the-pass-driver)), and column balancing has one per document as well as one
   per segment, so a book of many chapters cannot spend passes without end. The cost of a build
   can be measured pass by pass: `BuildDocumentOptions.onPass` reports each pass and its wall time.


4. **Pretext speed.** Text measurement at 300–600x DOM speed means the engine can afford to
   re-measure text speculatively (trying different column widths, hyphenation points, tracking
   adjustments) without blocking the main thread.

5. **Layered measurement caching.** The measure module (`packages/postext/src/measure/`) keeps
   an explicit measurement cache keyed on text, fonts, width, and every layout-affecting option,
   on top of Pretext's own `prepare()` cache and a raw text-width cache. Re-measuring an
   unchanged paragraph costs a map lookup. When a family's faces change, the engine drops that
   family's widths and Pretext's cache, and a measurement cache drops the blocks set in it at its
   next lookup (it carries the generation it was filled under), so glyph widths are correct after
   fonts finish loading with no call from the host; `clearMeasurementCache()` drops every family.

6. **Hot-path line breaking.** The Knuth-Plass active-node handling was rewritten for speed:
   the active set is compacted in place as nodes retire, and candidates are deduplicated
   per (line, fitness class) so only the lowest-demerit node per key survives. The algorithmic
   results are identical — same break sets, just computed faster.

7. **Off-main-thread builds.** The `postext/worker` entry point runs the entire pipeline
   inside a dedicated Web Worker. The main thread posts `{ content, config }` and an
   `AbortSignal`; the worker registers fonts (transferred as `ArrayBuffer`s), runs the
   placement passes, and posts back the finished `VDTDocument`. A newer `build()` call
   cancels the previous one cooperatively — the worker runs `buildDocumentAsync`, which polls a
   cancellation hook once per block and between passes and throws `BuildCancelledError`, so a user typing into an editor
   never waits on a superseded layout. The worker also maintains its own persistent
   measurement cache and a content-keyed math raster cache so that structured-cloned
   `MathRender` objects survive across rebuilds without re-rasterising.

8. **Dual-access VDT.** The tree (`pages > columns > blocks`) gives hierarchical access for
   work that goes page by page or column by column (column balancing measures the gap at the
   foot of each column). A parallel flat `blocks[]` array gives direct access to every block
   wherever it sits (the note-number round reads the marker each note printed from it). Both
   views reference the same block objects (there is no duplication, just two ways to traverse
   the same data).

### Laying Out Again

There is no incremental entry point: no call takes a finished VDT and updates it. When the content or the configuration changes (a keystroke, another page size), the host calls `buildDocument` again and gets a new document.

What carries over from one build to the next is the measuring. Create a `MeasurementCache` once with `createMeasurementCache()` and pass it as the third argument of every `buildDocument` call. A paragraph whose text, fonts, width and breaking options did not change is read from it, so an editor that lays the document out on every keystroke measures only the paragraph being typed in. A change of page size or of column count changes the widths, and those paragraphs are measured again; Pretext's `prepare()` results still hold, since they depend on the font and the text and not on the width, so only the cheap `layout()` arithmetic runs. The parse is memoized too.

For a live editor, `createLayoutWorker` (from `postext/worker`) does all of this off the main thread: the worker owns a measurement cache that lives as long as it does, and a newer `build()` cancels the one in flight. See [Configuration → Measurement cache](/en/docs/configuration-programmatic-usage#measurement-cache) and [Running layout in a Web Worker](/en/docs/configuration-programmatic-usage#running-layout-in-a-web-worker).

### Benchmarks

Two benchmarks live in `packages/postext/src/__bench__/`. `pnpm test` skips them; `pnpm bench`, run in `packages/postext`, runs them. `chapter.bench.test.ts` lays out one textbook-sized chapter (forty sections of headings, paragraphs and lists) five times against an empty measurement cache and five times against a warm one, and reports both medians and the number of passes. `cjkChapter.bench.test.ts` lays out chapter 1 of 红楼梦 and counts the characters sent to `measureText`, to hold the CJK composer to a cost linear in the length of the paragraph.

```typescript

for (let i = 0; i < ROUNDS; i++) cold.push(time(() => buildDocument({ markdown }, config, createMeasurementCache())));

for (let i = 0; i < ROUNDS; i++) warm.push(time(() => buildDocument({ markdown }, config, warmCache)));

// [bench] chapter: … pages, … passes (… ms), iterationCount=…; cold median … ms, warm median … ms (5 rounds)
```

A caveat for honesty: there is no canvas in Node, so both benchmarks stub text measurement and their absolute times are not the browser's. The ratio of cold to warm and the number of passes are, and a regression in either shows here before it shows in the Sandbox. The chapter benchmark reports numbers and does not break the build; the Chinese one asserts that the characters measured stay under three times the length of the longest paragraph. Neither runs in CI: regressions are caught by comparing the numbers across runs when a hot path changes (as was done for the Knuth-Plass active-node rewrite). Performance is a feature, not a hope — but the enforcement today is measurement and review, not a failing pipeline.

## Non-Goals

Each of these limits is a deliberate choice — the engine is complex enough on its own, and
taking on responsibilities that belong elsewhere would be the fastest way to never finish.

- **WYSIWYG editing.** Postext is a layout engine, not an editor. Content in, geometry out. Building an interactive editing surface — cursor management, selection, undo/redo, input handling — is an entirely separate problem. Postext can serve as the rendering backend for an editor, but it does not provide editing capabilities itself.
- **CSS column-count wrapper.** Postext replaces CSS multi-column layout; it does not wrap it. It computes precise positioned geometry from scratch, because the browser's column layout algorithm lacks control over resource placement, widow/orphan prevention, and cross-column typographic rules. Those are the whole point.
- **Responsive breakpoint management.** Postext computes layout at a given page size. The consumer decides when to re-layout (on viewport resize, on orientation change). Postext does not manage breakpoints, media queries, or responsive design decisions. That is your job.
- **Real-time collaborative editing.** Postext is a stateless layout computation — content in, geometry out — not a collaborative document system with conflict resolution, operational transforms, or multi-user awareness.
- **Font files.** The `postext` package loads fonts; it does not carry them. `prepareFonts` loads every face a configuration and its text ask for before the first build, and a face the font set could not give is listed in the document's warnings as `fontFallback`. The files themselves come from the host: an `@font-face` rule on the page, or a `resolve` function that says where each face lives. See [Configuration → Loading fonts before layout](/en/docs/configuration-programmatic-usage#loading-fonts-before-layout).

### Where the VDT Types Live

The VDT types (`VDTDocument`, `VDTPage`, `VDTColumn`, `VDTBlock`, `VDTLine`, `VDTLineSegment`, `ResolvedResourceBlock`, `VDTResourceTableLayout`, `BoundingBox`, and friends) live in `packages/postext/src/vdt.ts`, alongside the factory helpers (`createVDTDocument`, `createVDTPage`, `createVDTBlock`, …) and `computePageTextExtent`. There is no separate backend interface module — the rendering entry points described in [Backend Interface](#backend-interface) are exported directly from `postext` (canvas, HTML), `postext-pdf` (PDF) and `postext-epub` (EPUB).
